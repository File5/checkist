## Реализовано и планируется

Checkist предназначен для распознавания продуктовых чеков. Реализован scaffold: Django/DRF, анонимный health API, probes Postgres/Redis/Celery, демонстрационная задача `health.ping`, CLI `check_services`, Compose и тесты; React/TypeScript/Vite SPA показывает реальные health-ответы через proxy, частичные отказы, ошибки и повтор. Клиент описан в [docs/frontend.md](docs/frontend.md).

Реализована предметная модель данных — `stores`, `catalog`, `receipts`: модели, миграции с сид-данными, нормализация, дедупликация, проверка чека и история цен. `recognition` сохраняет исходное фото/вырезки/попытки и PostgreSQL-очередь; host-команда `recognition_worker` выполняет detect → crop → recognize → validate/import через Codex CLI либо явно выбранный FakeProvider. Новые магазины/товары создаются автоматически. Данные вводятся также через admin/код; HTTP произвольного редактирования сохранённых данных нет. Описание — [docs/data-model.md](docs/data-model.md).

Подключён Django admin: `/admin/` открывается напрямую на Django (dev `http://127.0.0.1:8000/admin/`, QA — порт 18000), не через Vite. Зарегистрированы 12 моделей, `ReceiptDiscount` и `ReceiptTax` доступны только inline внутри чека; вход — пользователю с `is_staff`, суперпользователя создаёт человек командой `manage.py createsuperuser`. У чека есть обязательный владелец (при изменении только для чтения), `LoginFailure` — только чтение; оператор видит чеки всех пользователей, вход в админку в режиме `accounts` — это и вход в приложение. Статика, secure-cookie и HTTPS на сервере — по [docs/deployment.md](docs/deployment.md), на сервере не проверено. Состав, проверки форм и ограничения — в [docs/data-model.md](docs/data-model.md#админка), запуск — в [docs/development.md](docs/development.md#админка), ручная приёмка — в [docs/verification.md](docs/verification.md#ручная-приёмка-админки-человеком).

Реализован HTTP API чтения — приложение `api` без моделей и миграций, 13 GET-эндпоинтов под `/api/`: справочники, категории, обобщённые продукты, товары, история цен, сравнение альтернативных товаров между странами и валютами. В режиме `local_single` эндпоинты открыты анонимно, в `accounts` требуют входа. Курсы валют не хранятся: пересчёт только по курсам из запроса. Несопоставленные позиции чеков в API не видны. SPA вызывает каталог, карточки товаров и историю/сводку цен; сравнение альтернатив пока не подключено. Контракт — [docs/api-contract.md](docs/api-contract.md#реализовано-api-чтения-каталога-и-цен).

Новый локальный API: upload фото, списки/detail фото/jobs/receipt-images, cancel/retry и `/api/receipts/` со всеми строками, включая непривязанные товары. Доступ в `local_single` — только DEBUG + `ALLOW_LOCAL_RECOGNITION_API=1` + loopback, в `accounts` — вход и только свои объекты; CSRF обязателен для unsafe методов в обоих режимах. MEDIA раздаёт вью `accounts/media.py`: в `accounts` — только владельцу фото, в `local_single` — при DEBUG, без проверки флага API; Vite dev/preview проксирует `/api` и `/media`. `executor.state` (`idle`/`busy`/`absent`) показывает простаивающий воркер по его advisory-блокировке в `pg_locks` текущей БД, `executor.available` = `state != "absent"`; модели и миграции нет. SPA реализует загрузку, опрос/cancel/retry заданий и просмотр чеков со всеми строками; см. docs/frontend.md и сценарий И5 в docs/verification.md. Промпт v5 просит налоговые evidence: без подтверждения чтения ставка и налоговый итог не импортируются. Issues вырезки дополнены `reason`/`severity`/`context`, SPA показывает их группами в задании и чеке; fake-сценарии `tax_evidence_missing`/`tax_evidence_present` и приёмка — [И6](docs/verification.md#и6-налоговые-evidence-и-сгруппированные-замечания).

Подтверждение неполного распознавания человеком реализовано: `POST /api/recognition/receipt-images/{id}/confirm/` принимает исправленные данные вырезки `needs_review` и в одной транзакции прогоняет их через тот же импорт, что и результат OCR (`backend/recognition/review.py`); доступ и CSRF как у остальных локальных действий. Успех — вырезка `imported` / `reused` / `updated` с `receipt_id` и `confirmed_at`, задание пересчитано (`partial_succeeded` → `succeeded`, когда успешны все вырезки). Отказы ничего не сохраняют: `400 invalid_parameter` с `fields`, `409 review_invalid` с `issues`, `review_unavailable`, `review_resolved`, `review_busy`, `job_active`. Повтор — по содержимому тела (SHA-256): тот же запрос — `200` без записей, другой — `review_resolved`; заголовок `Idempotency-Key` игнорируется. Найденный существующий чек не перезаписывается, расхождения возвращаются замечаниями. Миграций нет. Клиент — форма в карточке вырезки на `/recognition/jobs/{id}` ([docs/frontend.md](docs/frontend.md#исправление-и-подтверждение-вырезки-needs_review)), правки до успеха живут только в памяти страницы. Контракт — [api-contract.md](docs/api-contract.md#подтверждение-вырезки-needs_review-человеком), эталоны — `backend/recognition/tests/fixtures/public/review-*.json`, настоящий HTTP без браузера — `node frontend/scripts/check_review_proxy.mjs dev|preview <origin>` на свежей QA-базе, [проверки и результаты](docs/verification.md#подтверждение-вырезки-needs_review-итог-интеграции); экран в браузере принимает человек по [ACCEPTANCE.md](frontend/src/features/recognition/ACCEPTANCE.md).

Облегчённая v1 по-прежнему не включает: ReceiptDraft и серверный черновик, MutationRequest/Idempotency-Key, cleanup, POSIX watchdog, WorkerSlot-модель, manual_locked/отпечаток формы, защиту stale admin POST от OCR, правку сохранённого чека через API, выбор товара каталога для строки (`product_id`), подтверждение `failed` / `cancelled` вырезок (для них retry). Неполные/противоречивые результаты сохраняются на ReceiptImage как needs_review/failed с normalized_result/issues. Повтор по SHA-256 переиспользует последний job; другое фото связывается по сильному ключу либо точному store/time/total, дополняет лишь пустые поля/непривязанные товары при совместимых строках. Уже заполненные значения не перезаписываются, уже импортированные части cancel не удаляет. Планируются API правки сохранённых чеков и сопоставления товаров, вход через внешних провайдеров, дашборд, серверные курсы и другие providers. Не выдавайте это за готовые функции и не меняйте схему/провайдера без задачи.

Слияние дублей товаров: приложение `merges` находит похожие названия одного продавца и сливает товары **предварительно** — строки и написания сразу переносятся на оставляемый товар, журнал хранит исходную принадлежность, человек подтверждает, отменяет группу либо исключает запись через локальный `/api/product-merges/` (доступ и CSRF как у recognition; коды `merge_conflict` / `merge_resolved` / `merge_changed` / `merge_busy`). Поглощённые товары скрыты из 13 GET (`merges.visibility`), их id отвечает `404`; формы ответов и число запросов прежние. Импорт и слияния идут по очереди под `IMPORT_LOCK`; поиск после импорта — только при `PRODUCT_MERGE_AUTO_DETECT=1` (по умолчанию `0`), вручную — `manage.py product_merges detect [--dry-run]`. Перед `migrate merges zero` обязателен `product_merges cancel-pending`; подтверждённое слияние средствами приложения не отменяется. `recognition/resolution.py` остаётся точным. Эталонные JSON — `backend/merges/tests/fixtures/public/`, демо только для QA — `seed_product_merge_demo`. Клиент реализован: адаптер `frontend/src/api/product-merges*.ts`, экраны `/catalog/merges` и `/catalog/merges/{id}`, пометки в каталоге и карточке товара, подсказка для слитого товара ([docs/frontend.md](docs/frontend.md)). Настоящий HTTP через Vite proxy без браузера проверяет `node frontend/scripts/check_product_merges_proxy.mjs <origin>` (меняет данные — только свежая QA-база с демо); экраны в браузере принимает человек по [ACCEPTANCE.md](frontend/src/features/merges/ACCEPTANCE.md).

Предположение категорий товаров: приложение `classification` спрашивает модель о товарах, оставшихся в служебном «Не разобрано», и **сразу** приписывает товар к предложенному обобщённому продукту и категории (существующим либо созданным) с пометкой «требует подтверждения»; журнал хранит прежнее значение и созданные записи каталога. Человек подтверждает, выбирает другой обобщённый продукт, отклоняет либо подтверждает группу через локальный `/api/product-classifications/` (9 маршрутов, доступ и CSRF как у recognition; коды `classification_resolved` / `classification_changed` / `classification_busy`). Отклонение возвращает товар в «Не разобрано», убирает созданные пустые записи каталога и запоминает отказ: тот же вариант повторно не предлагается. Автоматика меняет только товар в «Не разобрано»: содержательный или подтверждённый обобщённый продукт не трогают ни запуск, ни импорт, ни повторное фото. При подтверждении слияния дублей ожидающая запись поглощённого товара переходит к оставляемому, только если тот до слияния был в «Не разобрано» и получил предложенное значение из этого предположения (`after_merge_confirmed(..., target_generic_before)`); иначе запись закрывается `superseded` / `merged`, товар не трогается; сверка запись не переносит никогда. Своя ожидающая запись оставляемого товара закрывается так же (`superseded` / `merged`), если слитый с ним дубль имел то же значение от человека; это решает сверка по журналу слияний. Память отказов поглощённых товаров переходит к оставляемому: перед их удалением слияние вызывает `before_merge_confirmed` (строки переносятся как есть, совпавший ключ сохраняет строку оставляемого либо более раннюю), а потерянное при сбое и по слияниям, подтверждённым раньше, восстанавливает сверка из закрытых записей `rejected` / `other` и журнала слияний (`_inherit_rejections`) — вариант, отклонённый для дубля, оставляемому товару не предлагается. Отклонение и `cancel-pending` не меняют значение, которое было у товара до предположения либо выставлено человеком. Модель из HTTP не вызывается: кнопка «Предложить категории» и импорт при `PRODUCT_CLASSIFICATION_AUTO_SUGGEST=1` (по умолчанию `0`) ставят запуск в очередь PostgreSQL; импорт дописывает товары чека за курсором в уже ждущий запуск любого `scope` — и свой `products`, и ручной `all` (сверх лимита — в `remaining`), а отдельный запуск создаёт, только когда очередь пуста; исполняет запуск тот же `recognition_worker` пакетами после заданий распознавания (один текстовый вызов Codex CLI без изображения либо явный fake); сбой модели не меняет чек, задание и каталог. Вручную — `manage.py product_classifications suggest [--dry-run]`, `reconcile`, `cancel-pending`. Перед `migrate classification zero` обязателен `product_classifications cancel-pending`; подтверждённое остаётся. 13 GET сохраняют формат: меняется только состав каталога. Таблицы прежних приложений, `recognition/resolution.py`, промпт v5 и контракт слияний не менялись; в `merges/services.py` добавлены два шага подтверждения слияния: перенос памяти отказов перед удалением поглощённых товаров и шаг записей после подтверждения. Эталонные JSON — `backend/classification/tests/fixtures/public/` (40 файлов), демо только для QA — `seed_product_classification_demo`, описание — `backend/classification/README.md` и `QUEUE.md`. Клиент: адаптер `frontend/src/api/product-classifications*.ts`, экран `/catalog/classification`, пометки в каталоге и карточке ([docs/frontend.md](docs/frontend.md#категории-товаров-предположение-с-подтверждением-ф1ф2)). Настоящий HTTP через Vite proxy без браузера проверяет `node frontend/scripts/check_product_classifications_proxy.mjs <origin>` (меняет данные — только свежая QA-база с демо и `suggest --fake-scenario mixed`); экран в браузере принимает человек по [ACCEPTANCE.md](frontend/src/features/classification/ACCEPTANCE.md). На машине с `codex.exe` в PATH и выполненным входом любой запуск с `RECEIPT_OCR_PROVIDER=codex_cli`, дошедший до провайдера, делает настоящий модельный запрос: для проверок ставьте `fake`, в тестах с `codex_cli` — `RECEIPT_OCR_CODEX_EXECUTABLE="nonexistent-checkist-codex"` и подмену запуска процесса.

Статистика реализована на сервере и в клиенте. Клиент: экраны `/stats` («Траты за период»: круговая диаграмма, разбивки, drill-down по категориям) и `/stats/receipts` («Почему изменился средний чек»: сравнение двух периодов и график по времени), блок «График цен» в карточке товара; диаграммы — собственный SVG `frontend/src/lib/charts/` без зависимостей, одна валюта — один блок, всё состояние в адресе; описание — [docs/frontend.md](docs/frontend.md#статистика-траты-средний-чек-и-график-цен-ф1ф7), ручная приёмка — `frontend/src/features/stats/ACCEPTANCE.md`, настоящий HTTP без браузера — `frontend/scripts/check_stats_proxy.mjs dev|preview <origin>` ([результаты](docs/verification.md#фактические-результаты-ф7-2026-10-07)); после исправлений по проверке интерфейса (заход 2, 2026-10-07: подсказка линейного графика у правого края, флажки магазинов, прокрутка таблицы слагаемых, выделение после касания) — frontend 2239 тестов / 61 файл, backend не менялся и не запускался, вид в браузере не проверялся ([результаты](docs/verification.md#фактические-результаты-статистика-второй-заход-после-проверки-интерфейса-2026-10-07)); страницы `frontend/*-preview/index.html` — статические снимки на эталонах, не приёмка. Ограничения клиента: график цен берёт из фильтров карточки только период; список магазинов в формах — первые 50 (средний чек) и 200 (траты). Сервер. Локальные, с доступом как у `/api/receipts/`: `GET /api/stats/spending/` — траты за период по категориям, обобщённым продуктам, товарам или магазинам с drill-down по категории; `GET /api/stats/receipts/series/` — походы по времени; `GET /api/stats/receipts/compare/` — разложение изменения среднего чека между двумя периодами на количество, цены и состав (индекс Фишера по товарам, купленным в обоих периодах; допущение — индекс перенесён на всю корзину, покрытие отдаётся в ответе). Открытый, как 13 GET: `GET /api/products/{id}/prices/series/` — ряды цен товара по магазинам и похожих товаров того же обобщённого продукта по странам. Моделей, миграций и индексов нет; валюты не складываются и не пересчитываются; новых категорий нет — «Не разобрано» и несопоставленные строки показываются как есть; поглощённый слиянием товар наружу не выходит. Контракт и методика — [api-contract.md](docs/api-contract.md#реализовано-статистика-трат-походы-и-ряды-цен-серверная-часть), эталоны для схем клиента — `backend/api/tests/fixtures/stats/*.json`, демо только для QA — `seed_stats_demo`, [запуск для клиента](docs/development.md#qa-статистика-для-клиента), [проверки и замер](docs/verification.md#статистика-серверная-часть-с5): самый медленный запрос на демо — 132 мс. Тесты идут через `config.test_runner.Runner`: в тестовой БД autovacuum отключён, иначе планы запросов по большим незакоммиченным данным зависят от момента фоновой очистки.

Оформление клиента (редизайн, 2026-10-07): красная схема с золотыми акцентами вместо зелёной, тёмная тема по умолчанию и светлая по переключателю в шапке. Все цвета записаны только в `frontend/src/theme/tokens.css` переменными `--ck-*` (тёмные значения в `:root`, светлые в `:root[data-theme="light"]`); в остальных рабочих CSS hex/rgb-цветов нет и добавлять их нельзя, имена классов, селекторы, медиа-блоки и геометрию экранов редизайн не менял. Выбор темы хранится в `localStorage` под ключом `checkist.theme`, больше нигде в `frontend/src` хранилище не используется; встроенный скрипт в `frontend/index.html` ставит сохранённую тему до первой отрисовки — при строгой CSP на сервере его нужно разрешить по хэшу либо вынести в файл. Системная настройка темы не учитывается. Логотип «ЧЕКИСТ — продуктовая разведка», эмблема, favicon и шрифт заголовков Oswald лежат в репозитории (`frontend/src/assets/brand/`, `frontend/src/assets/fonts/`, `frontend/public/`); исходники `frontend/brand/logo-source.png` и `frontend/brand/emblem-source.png` в сборку не идут; подложка полного логотипа `--ck-logo-bg` равна фону его файлов `#0f0f0e`; эмблема шапки (с 2026-10-08, М5) — из отдельного исходника, прозрачная, без надписи и без подложки, `apple-touch-icon.png` — она же на непрозрачном `#0f0f0e` (`frontend/src/assets/brand/README.md`). ## Env и секреты

- Один корневой `.env`, образец — `.env.example`. Backend читает его с `override=False`: environment процесса выше файла, затем defaults кода. В Docker явно заданы внутренние адреса worker.
- `.env`, `.env.*` (кроме `.env.example`), `.venv/`, артефакты сборки и `.orca-attachments/` игнорируются. Не коммитьте секреты, пользовательские пути, реальные фото чеков или логи с паролями/DSN.
- `CHECKIST_AUTH_MODE`: в образце `local_single`; без строки действует `accounts` — вход обязателен. `local_single` при `DJANGO_DEBUG=0` — отказ загрузки настроек. Пароли учётных записей и демо не записывайте в `.env`, документы, отчёты и коммиты.
- Образец содержит публичные значения только для локальной разработки. `DJANGO_DEBUG=0` отвергает известный placeholder `DJANGO_SECRET_KEY`; это не делает конфигурацию готовой к production.
- Redis доступен без пароля только через loopback и выделенную Docker-сеть. DB 0/1/2 разделяют broker/results/cache, но не обеспечивают авторизацию пользователей.
- `VITE_API_BASE_URL` — публичный browser-префикс (`/api`); не помещайте в него секреты. Vite читает корневой `.env`, `envPrefix: []` и `define` передают только этот публичный параметр. `DEV_API_PROXY_TARGET` используется только Node-конфигурацией proxy, без переписывания `/api`.
- MEDIA_ROOT и RECEIPT_OCR_TEMP_ROOT — абсолютные непересекающиеся каталоги; API/host-worker используют одну DB и MEDIA. В QA отдельные от dev каталоги. Не коммитьте MEDIA/приватные provider payload. Auth существующего host-пользователя не меняйте; Windows worker требует native `.exe`. Настройки/команды — [development.md](docs/development.md#распознавание-запуск-для-клиента).

## API и данные

Backend владеет [контрактом](docs/api-contract.md). Точный URL — `/api/health/`; JSON-only; анонимный GET; HTTP 503 содержит валидное тело с `checks`. GET выполняет control ping, но не публикует Celery-task и не проверяет result backend. Реальную очередь/результат проверяет `check_services`; eager/local вызов не заменяет интеграцию. Клиент обязан валидировать JSON во время выполнения и сохранять `checks` при 503.

Прежний API каталога/цен: только GET. Новые локальные recognition/receipts views добавляют upload/cancel/retry, подтверждение вырезки needs_review и чтение чеков; контракт — [api-contract.md](docs/api-contract.md). Все API JSON, завершающий `/` обязателен; деньги — Decimal строками без float, цены разных валют не складываются/усредняются; ошибки — `{"error": {"code", "message", "fields?"}}` из config/exceptions.py. В ответах нет raw_text/fiscal/fiscal_key/extra, legal_name/tax_id, номеров чека/кассы/смены и provider stderr/raw payload. Query/страницы — api.params.Params/api.pagination.paginate; зависимостей django-filter нет. Число запросов не растёт с размером страницы — assertNumQueries.

Глобальная DRF permission — `IsAuthenticated`; health явно использует `AllowAny` и пустой список authentication classes, остальные вью — классы из `backend/accounts/access.py`: `SessionUserAuthentication` и `SignedIn` (13 GET), `LocalOrSignedIn` (чеки, распознавание, статистика, чтение слияний и предположений) либо `Moderator` (их POST). Новая вью не читает `request.user` и настройку режима: пользователя берёт `request_user(request)`, свои строки — `owner_q(request, prefix)`, право — `is_moderator(request)`; чужой личный объект отвечает `404` тем же телом, что несуществующий, `403` — только «действие требует права». `/admin/` — HTML-интерфейс Django, в контракт API он не входит; его сессия общая с API. При новых API установите потребителей, валидацию, доступ к объектам и границы пользователей; не раскрывайте внутренние ошибки. Изменение формата отражайте в контракте, тестах, клиенте и отчёте с перечнем несовместимости.

## Запуск и проверки

Windows: `py -3.13`, прямой `./backend/.venv/Scripts/python.exe`, `-X utf8`; не требуется `Activate.ps1`. Для frontend используйте `npm.cmd`, без изменения ExecutionPolicy. Полный запуск — [development.md](docs/development.md); `.env` предварительно создать из образца. Dev Compose project — `checkist_dev`, API 8000, Vite 5173, Postgres 15432, Redis 6379.

Все тестовые записи, миграции, публикации задач и отключения сервисов выполняйте в QA, не в dev и не на локальном Postgres. В каждом QA-терминале сначала примените весь блок environment из [verification.md](docs/verification.md): БД `checkist_qa`, Compose `-p checkist_qa`, Postgres 25432, Redis 16379, API 18000, Vite 15173. QA имеет отдельные контейнеры, сеть и тома; тестовый runner создаёт `test_checkist_qa`.

После QA-настройки:

```powershell
docker compose -p checkist_qa config --quiet
./backend/.venv/Scripts/python.exe -X utf8 -m pip check
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py check
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py makemigrations --check --dry-run
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py migrate --noinput
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py test catalog stores receipts health api recognition merges classification accounts --exclude-tag=integration --verbosity=2
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py test catalog stores receipts health api recognition merges classification accounts --tag=integration --verbosity=2
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py check_services
```

Перед тестами задайте `RECEIPT_OCR_PROVIDER=fake`, `PRODUCT_MERGE_AUTO_DETECT=0` и `PRODUCT_CLASSIFICATION_AUTO_SUGGEST=0`; два набора запускайте по очереди. Тесты идут в режиме `local_single` (его ставит `config.test_runner.Runner`), тесты режима `accounts` включают его через `override_settings(CHECKIST_AUTH_MODE="accounts")`. QA-серверу и прежним proxy-скриптам нужен `CHECKIST_AUTH_MODE=local_single` в окружении; проверка двух учётных записей идёт на отдельной пустой базе в режиме `accounts`. Тесты без тега `integration` БД не используют; с тегом — требуют QA Postgres, а `health` ещё и QA Redis. HTTP-сценарии API чтения через `curl.exe` — в [verification.md](docs/verification.md#http-api-чтения). `check_services` требует запущенный QA worker. Проверку отката миграций см. в [verification.md](docs/verification.md#модель-данных-catalog-stores-receipts).

В `frontend/`: `npm.cmd ci`, `npm.cmd run lint`, `npm.cmd run test`, `npm.cmd run build`. При запущенных QA API/Vite из корня: `node backend/scripts/check_health_proxy.mjs healthy`; stop/recovery и states `worker`, `postgres`, `redis` — по verification.md. Эта проверка использует настоящий fetch и клиентский адаптер в Node, без обхода UI. QA environment для `npm.cmd` и Node-скриптов задавайте в PowerShell: Git Bash переписывает `VITE_API_BASE_URL=/api` в путь Windows, и тесты адаптеров падают.

Проверяйте exit code каждого шага. Не продолжайте зависимые шаги после ошибки. Если Windows не достигает Docker-портов, сначала выполните ограниченную TCP-[диагностику](docs/development.md#диагностика-нет-доступа-с-windows-к-портам-docker); не повторяйте заведомо невозможный прогон. Linux-проверки из verification.md подтверждают только путь внутри контейнерной сети. Изменение WSL Mirrored и перезапуск Docker Desktop в диагностике — решение человека; агентам самостоятельно системные настройки не менять и Docker Desktop не перезапускать. После проверки остановите созданные процессы и выполните `docker compose -p checkist_qa down`; тома сохраняются, `down -v` удаляет данные.

## Отчёт и приёмка

Отчёт делите на три группы:

1. **Проверено и прошло:** точные команды, exit codes, наблюдаемые результаты, тестовая среда/БД.
2. **Проверено и не прошло:** команда, фактическая ошибка, воспроизведение и известная причина либо отметка, что причина не установлена.
3. **Не проверено и почему:** ограничения и воспроизводимые шаги для человека/следующего этапа.

Mocks проверяют контракт, сборка — сборку, статический аудит — исходники. Они не подтверждают пользовательское поведение или настоящие зависимости. Не выдумывайте скриншоты и результаты; не отключайте упавший тест, не ослабляйте ожидания и не скрывайте дефект безусловным retry. Проверки выбирайте по затронутому поведению и риску; после исправления повторяйте необходимые проверки на окончательном состоянии.

Визуальную и интерактивную приёмку UI выполняет **человек**. Не используйте автоматический обход browser UI; разрешены HTTP/CLI/unit/lint/build. Передайте ручной сценарий из verification.md — для SPA и отдельно для админки. Наличие SPA, HTTP-прогон и Node-вызов адаптера не подтверждают визуальное и интерактивное поведение React в браузере.

Самостоятельные публикация, deployment, merge и release запрещены без явного задания. Работайте в своей ветке/worktree; не переключайте ветку и не меняйте соседние worktrees. Сдача и принятие результата не означают выпуск или слияние: ими управляет workflow проекта.
