# Контракт API и Celery

## Реализовано: `GET /api/health/`

Публичный endpoint Django/DRF для состояния инфраструктуры. Канонический путь имеет завершающий `/`; клиенту следует использовать его напрямую. GET не требует body или query-параметров; неизвестные параметры, включая `format`, игнорируются. `AllowAny`, `authentication_classes=[]`: анонимный доступ без cookies/token; Authorization header не проверяется. CSRF для этого GET не требуется. Глобальная permission для будущих DRF views — `IsAuthenticated`, но пользовательский вход сейчас не реализован. Так же явно открыты эндпоинты [API чтения](#реализовано-api-чтения-каталога-и-цен).

Ответы view: `Content-Type: application/json`, `Cache-Control: no-store`. Только JSONRenderer. HEAD и OPTIONS разрешены стандартным DRF-поведением; HEAD использует GET-проверки. Запись через endpoint не разрешена.

### HTTP 200

Возвращается только при трёх успешных проверках:

```json
{
  "status": "ok",
  "checks": {
    "database": {"status": "ok"},
    "redis": {"status": "ok"},
    "celery": {"status": "ok"}
  }
}
```

### HTTP 503

При известном отказе зависимости тело остаётся валидным health-ответом. Пример остановленного worker при доступном broker:

```json
{
  "status": "degraded",
  "checks": {
    "database": {"status": "ok"},
    "redis": {"status": "ok"},
    "celery": {"status": "error", "code": "worker_unavailable"}
  },
  "error": {
    "code": "dependency_unavailable",
    "message": "Один или несколько сервисов недоступны."
  }
}
```

`status` — `ok` или `degraded`; `checks` содержит ровно `database`, `redis`, `celery`. Успешный check — `{"status":"ok"}`, неуспешный — `{"status":"error","code":"…"}`. При 503 присутствует общий `error` выше, а успешные checks сохраняются. Probes выполняются параллельно и независимо: отказ БД не отменяет остальные проверки. Неожиданное исключение реализации даёт 500 вместо достоверного health-ответа.

| Check | Код ошибки | Реальное действие / причина |
| --- | --- | --- |
| `database` | `database_unavailable` | `SELECT 1` не выполнен или вернул неожиданный результат. |
| `redis` | `redis_unavailable` | Cache set/get/delete не выполнен, значение не совпало или cleanup не удался. |
| `celery` | `broker_unavailable` | Соединение или control-публикация через broker завершились сетевой ошибкой. |
| `celery` | `worker_unavailable` | Control ping не получил ни одного ответа `{"ok":"pong"}`. |

Cache использует DB 2, уникальный `health:<uuid>`, случайное значение, TTL 5 секунд и удаление в `finally`. Celery отправляет **control ping**, а не task: достаточно одного ответа worker, это не проверка каждого worker в кластере. При отказе общей Redis-инфраструктуры обычно одновременно ошибочны `redis` (`redis_unavailable`) и `celery` (`broker_unavailable`).

### Протокольные и внутренние ошибки

| HTTP | Условие | Тело |
| --- | --- | --- |
| 405 | POST/PUT/PATCH/DELETE при совместимом Accept | `{"error":{"code":"method_not_allowed","message":"Метод не поддерживается."}}` |
| 406 | Несовместимый Accept, например `text/html` | `{"error":{"code":"not_acceptable","message":"Доступен только JSON."}}` |
| 500 | Неожиданное исключение в DRF view | `{"error":{"code":"internal_error","message":"Внутренняя ошибка сервера."}}` |

Для 405 заголовок `Allow: GET, HEAD, OPTIONS`. Ошибки 405/406 не запускают probes. Ответ 500 безопасен и при `DEBUG=1`: не содержит exception text, DSN, паролей или traceback. Формат `{"error": {"code", "message"}}` — общий для всех DRF views под `/api/`: тот же handler обслуживает [API чтения](#реализовано-api-чтения-каталога-и-цен), включая его `400` и `404`. Ответы middleware вне DRF (редирект `APPEND_SLASH`, пути вне `/api/`) этим форматом не покрыты.

### Таймауты

| Действие | Настройка в коде |
| --- | --- |
| Postgres подключение | `connect_timeout=2` секунды |
| SQL statement | `statement_timeout=2000` миллисекунд |
| Redis cache connect/socket | По 1 секунде, Redis Retry с нулём повторов |
| Celery broker connect/socket | По 1 секунде, `max_retries=0`; control-публикация также ограничивает retries |
| Celery HTTP probe reply | `inspect(timeout=1, limit=1)` |
| Docker worker healthcheck reply | `inspect --timeout=2`, отдельная проверка |

Probes запускаются параллельно, поэтому их обычные сетевые ожидания не суммируются последовательно. Общего жёсткого deadline HTTP-запроса в коде **нет**; DNS, отдельные операции и cleanup могут увеличить время. Цель при отказе — ответ не позднее 10 секунд. В Windows QA2-прогоне она выполнена: HTTP 503 при остановке worker — 1.057378 с (`worker_unavailable`), Postgres — 2.028070 с (`database_unavailable`), Redis — 2.063928 с (`redis_unavailable` + `broker_unavailable`). Это измерения конкретных сценариев, не общий deadline. Реализованный клиентский таймаут 15 секунд охватывает fetch и чтение тела; отмена запроса не отменяет серверные probes. Команды и результаты проверки через proxy — в [verification.md](verification.md#сквозная-проверка-клиента-через-vite-proxy).

### Разбор клиентом — реализованный SPA

1. Запрашивать `<VITE_API_BASE_URL>/health/` с нормализованными `/`, `Accept: application/json`, без credentials. Базовый относительный префикс — `/api`.
2. Прочитать JSON до общей обработки `response.ok`: HTTP 503 содержит полезные `checks`.
3. Проверить schema во время выполнения: три check-имени, допустимые status/code, соответствие HTTP и тела. TypeScript сам не валидирует сеть.
4. Для 200 требовать `status=ok`, все checks `ok`; для 503 — `status=degraded`, хотя бы один error и общий `dependency_unavailable`. Сохранить все checks для отображения частичного отказа.
5. Network error, abort/timeout, 500, неверный JSON/schema или несовместимая пара HTTP/body — отдельная ошибка клиента с возможностью повторить. Старый success и устаревший ответ не должны подменять новое состояние.

Адаптер `frontend/src/api/health.ts` реализует этот разбор; описание клиента — [frontend.md](frontend.md). Vite dev/preview используют same-origin proxy с сохранением `/api`. Произвольный внешний API origin и CORS не настроены. Не-JSON 502/504 от недоступного proxy upstream обрабатываются как ошибка соединения; схема Django 200/503/405/406/500 остаётся прежней.

## Реализовано: API чтения каталога и цен

13 эндпоинтов только на чтение в приложении `backend/api/` (без моделей и миграций): справочники, категории, обобщённые продукты, товары, история цен и сравнение альтернативных товаров между странами. Потребитель — будущие экраны SPA; текущая страница клиента их не вызывает.

| Эндпоинт | Что отдаёт |
| --- | --- |
| `GET /api/countries/` | Страны с магазинами, их валюты и счётчики |
| `GET /api/stores/` | Магазины |
| `GET /api/brands/` | Бренды |
| `GET /api/categories/` | Дерево категорий плоским списком |
| `GET /api/categories/{id}/` | Категория, прямые потомки, обобщённые продукты |
| `GET /api/generic-products/` | Обобщённые продукты |
| `GET /api/generic-products/{id}/` | Обобщённый продукт |
| `GET /api/products/` | Товары с последней ценой по каждой паре «страна, валюта» |
| `GET /api/products/{id}/` | Карточка товара |
| `GET /api/products/{id}/prices/` | Точки истории цен |
| `GET /api/products/{id}/prices/summary/` | Агрегаты цен по группам и интервалам |
| `GET /api/products/{id}/alternatives/` | Товар и его альтернативы по странам и валютам |
| `GET /api/generic-products/{id}/comparison/` | Сравнение всех товаров обобщённого продукта |

### Доступ и границы

- **Эндпоинты открыты анонимно на чтение**: `AllowAny`, `authentication_classes = []`, как health. Cookies, token и заголовок `Authorization` не проверяются и игнорируются. Глобальная `IsAuthenticated` остаётся для будущих API.
- **Перед любым внешним развёртыванием доступ нужно закрыть.** База покупок читается любым, кто достанет до API. Сейчас это только loopback: `DJANGO_ALLOWED_HOSTS` — `127.0.0.1,localhost`, CORS не настроен. Пользовательского входа и разграничения чеков нет: у данных нет владельца.
- Записи через API нет: `POST/PUT/PATCH/DELETE` дают `405`.
- **Несопоставленные позиции чеков в API не видны.** API показывает только товары каталога и строки, у которых заполнен `ReceiptLine.product`. Сопоставление делается только кодом, поэтому на новых данных каталог и история пусты, пока позиции не сопоставлены.
- В ответы не попадают `Receipt.raw_text`, `fiscal`, `fiscal_key`, `extra`, `Merchant.legal_name`, `tax_id`, `extra`, номера чека, смены и кассы. Из чека наружу идут только `receipt_id`, дата и момент покупки. Название магазина — `Merchant.brand_name`, иначе `Store.name`, иначе `"Магазин №<id>"`: юридическое название у предпринимателя — это ФИО.

### Общие правила

- Только `GET`, а также `HEAD` и `OPTIONS` от DRF (`OPTIONS` отдаёт стандартные метаданные DRF). Только JSON. Заголовков кеша нет, серверного кеша нет.
- Завершающий `/` обязателен. `GET` без него получает `301` на путь со слэшем (`APPEND_SLASH`), включая неизвестные пути и `/api/health`. Запись без завершающего `/` — см. [известное ограничение](#известное-ограничение-запись-без-завершающего-слэша).
- Неизвестные query-параметры игнорируются. Пустое значение (`?q=`, `?q=%20`) равно отсутствию параметра; у повторённого параметра берётся последнее значение. Известный параметр с недопустимым значением — `400`; все ошибки параметров возвращаются одним ответом.
- В читаемых query-параметрах запрещены управляющие символы Unicode Cc: `U+0000–U+001F` (C0, включая NUL, TAB, LF и CR) и `U+007F–U+009F` (DEL и C1). Проверка идёт до обрезки пробелов и разбора значения; символы не вырезаются. Ответ — `400 invalid_parameter` с `fields.<имя параметра>: ["Управляющие символы недопустимы."]`. Правило действует и для кодов, идентификаторов, дат, сортировки, перечислений и курсов; неизвестные и не используемые эндпоинтом параметры по-прежнему игнорируются.
- `q` — от 2 до 100 символов после обрезки пробелов по краям, без управляющих символов выше. Одинаковое правило действует для `products`, `stores`, `brands`, `generic-products` и `categories`. Например, `?q=%00a` даёт `400 invalid_parameter` с `fields.q` до SQL поиска, включая пустую БД; обычный UTF-8 поиск допустим.
- Не-ASCII в query передаётся в UTF-8 с percent-encoding (`?q=%D0%BC%D0%BE%D0%BB`).
- Десятичные числа — **строки**: цена за единицу с 4 знаками (`"130.5882"`), сумма и процент с 2, количество с 3; округление `ROUND_HALF_UP`. Деньги идут от БД до JSON как `Decimal`, `float` не используется. Исключение — `Product.attributes`: отдаётся как хранится, там возможны JSON-числа.
- Вычисления и сериализация покрывают весь допустимый диапазон денежных полей, количеств, фасовок и курсов. Нормализацию и SQL-агрегаты считает Postgres `numeric`; пересчёт, средние, проценты и округление в Python используют локальный Decimal-контекст с точностью 128 цифр, независимо от контекста вызывающего кода. Произведение цены на курс сохраняет все цифры до округления ответа. Например, `9999999999000000.0000 × 999999999999` отдаётся как `"9999999998990000000001000000.0000"`.
- `observed_at`, `last_observed_at` — ISO 8601 в UTC с `Z`. `purchased_on` — локальная дата магазина `ГГГГ-ММ-ДД`.
- Идентификаторы — положительные целые. Страна и валюта — коды из справочника (`DE`, `EUR`); в параметрах регистр кода не важен.
- Цены разных валют никогда не складываются и не усредняются: валюта входит в ключ каждой группы.
- **Наблюдение цены** — строка чека с `kind='product'`, положительным количеством, из чека продажи. Залог, возврат тары, услуги, чеки возврата и отрицательные количества в цены не входят. Скидка на строку входит в `paid_unit_price`; скидка на весь чек — нет.
- **Конкурентное изменение чеков:** общий снимок на весь HTTP-запрос не гарантируется (Postgres `READ COMMITTED`). Если между агрегатами и чтением последней цены группа исчезла, она пропускается в ценах товаров и загруженных предложениях сравнения; товар остаётся с пустыми ценами/предложениями, если других наблюдений нет. Ранги и сводка сравнения исключают такие предложения. Если осталось более раннее наблюдение, оно становится последним; счётчики и агрегаты могут относиться к предыдущему SQL-снимку. Итоги и интервалы `/prices/summary/` вычисляет один SQL-запрос; вспомогательные счётчики и каталог читаются отдельно. Удаление чека между запросами не вызывает `500`; повторных запросов и блокировок ради общего снимка нет.

**Пагинация** (`stores`, `brands`, `generic-products`, `products`, точки истории, сравнение): `page` (с 1) и `page_size`.

```json
{"count": 3, "page": 1, "page_size": 2, "pages": 2, "results": []}
```

| Список | `page_size` по умолчанию | Максимум |
| --- | --- | --- |
| `stores`, `brands`, `generic-products`, `products` | 50 | 200 |
| Точки истории цен | 200 | 500 |
| Сравнение и альтернативы | 50 | 100 |

Пустой набор на первой странице — `200`, `count: 0`, `pages: 0`, `results: []`. Страница дальше последней — `404 page_out_of_range`, в том числе `page=2` при пустом наборе. Ссылок `next` / `previous` нет намеренно: за proxy абсолютный URL содержал бы адрес backend. Каждый порядок заканчивается первичным ключом, поэтому стабилен. Сортировку по названию выполняет БД по своему правилу сравнения строк: в проверенной среде латиница идёт раньше кириллицы.

### Ошибки

Формат ошибок общий для всех DRF views под `/api/`, включая health: `{"error": {"code", "message"}}`; у `400` дополнительно `fields`.

| HTTP | `code` | Условие |
| --- | --- | --- |
| 400 | `invalid_parameter` | Недопустимое значение параметра; `fields` — `{"параметр": ["сообщение"]}` |
| 400 | `range_too_large` | Больше 1000 интервалов в сводке цен |
| 404 | `not_found` | Объекта нет; неизвестный путь внутри `/api/` с завершающим `/` — для любого метода |
| 404 | `page_out_of_range` | Страница за пределами |
| 405 | `method_not_allowed` | `POST/PUT/PATCH/DELETE` на существующем эндпоинте; `Allow: GET, HEAD, OPTIONS` |
| 406 | `not_acceptable` | Несовместимый `Accept`, например `text/html` |
| 500 | `internal_error` | Неожиданное исключение; без текста исключения. Сюда же попадают превышение `statement_timeout=2000` мс и справочник категорий больше 5000 узлов |

```json
{"error": {"code": "invalid_parameter", "message": "Некорректные параметры запроса.",
           "fields": {"page_size": ["Допустимо от 1 до 200."]}}}
```

В сообщения попадают только фиксированные тексты и допустимые значения, но не присланное значение. Обработчик также умеет `401 not_authenticated` и `403 permission_denied` в том же формате; текущие эндпоинты их не отдают, потому что открыты.

| Значение параметра | Ответ |
| --- | --- |
| `page` меньше 1, `page_size` вне диапазона, нечисловой идентификатор в фильтре | `400` |
| Код страны или валюты, которого нет в справочнике (`country`, `currency`, `target_currency`, коды в `rates`) | `400` |
| Несуществующий `store` в истории цен | `400`, «Магазин не найден.» |
| Несуществующие `category`, `generic`, `brand` в списках | `200` с пустым списком |
| `q` короче 2 или длиннее 100 символов | `400` |
| Дата не `ГГГГ-ММ-ДД`, `date_from > date_to` | `400` |
| `ordering`, `interval`, `group_by`, `price`, `scope`, `has_prices`, `all` вне списка допустимых | `400` |

Идентификатор в пути, которого нет в БД, нечисловой или больше `2^63 − 1`, — `404 not_found`.

#### Известное ограничение: запись без завершающего слэша

`POST`, `PUT` или `PATCH` на путь внутри `/api/` **без** завершающего `/` до DRF не доходит: его перехватывает `CommonMiddleware`. При `DJANGO_DEBUG=1` ответ — `500` с отладочной HTML-страницей Django (`RuntimeError`, с traceback), а не JSON; при `DJANGO_DEBUG=0` Django отвечает `301` на путь со слэшем. Для `/api/health` так было и раньше; запасной маршрут распространил это на любой путь `/api/…`. Обработчик ошибок DRF здесь не участвует. Клиент должен всегда использовать путь с завершающим `/`. Воспроизведение — в [verification.md](verification.md#фактические-результаты-проверки-api-чтения-2026-10-03).

### Справочники

**`GET /api/countries/`** — без пагинации, по коду. Страны, в которых есть магазины; `currencies` — валюты чеков этих магазинов; `products_count` — товары с наблюдениями цены в стране. `all=1` добавляет страны без магазинов.

```json
{"results": [{"code": "DE", "name": "Германия", "currencies": ["EUR"], "stores_count": 1, "products_count": 1}]}
```

**`GET /api/stores/`** — пагинация; фильтры `country`, `q` (вывеска, название, город; подстрока без учёта регистра); порядок — отображаемое название, затем `id`.

```json
{"id": 2, "name": "Lidl", "city": "Lindau", "address": "Kemptener Straße 17, 88131 Lindau",
 "country": "DE", "timezone": "Europe/Berlin", "receipts_count": 6}
```

**`GET /api/brands/`** — пагинация; `q` по названию; порядок `name, id`. Элемент: `{"id", "name", "manufacturer", "products_count"}`.

### Категории

**`GET /api/categories/`** — всё дерево плоским списком в порядке обхода в глубину, без пагинации. Братья идут по `name`, затем `id`; здесь строки сравнивает Python (по кодам символов), а не БД.

```json
{"results": [
  {"id": 1, "name": "Продукты питания", "parent_id": null, "depth": 0,
   "path": [{"id": 1, "name": "Продукты питания"}],
   "children_count": 1, "generic_products_count": 0, "products_count": 0, "products_total": 2},
  {"id": 2, "name": "Молочные продукты", "parent_id": 1, "depth": 1,
   "path": [{"id": 1, "name": "Продукты питания"}, {"id": 2, "name": "Молочные продукты"}],
   "children_count": 0, "generic_products_count": 1, "products_count": 2, "products_total": 2}
]}
```

- `products_count` — товары обобщённых продуктов самой категории; `products_total` — вместе с потомками.
- `q` (2–100 символов, без управляющих символов по общим правилам) оставляет узлы с совпадением в названии и их предков.
- БД не запрещает циклы. Узел, входящий в цикл, и узел с несуществующим родителем отдаются как корневые: `depth: 0`, путь из одного узла, `parent_id` — как в БД. Обход не зацикливается.
- Больше 5000 категорий — `500 internal_error`: справочнику нужен другой контракт.

**`GET /api/categories/{id}/`** — тот же объект и дополнительно `children` (прямые потомки в том же формате) и `generic_products`: `[{"id", "name", "base_unit", "products_count"}]` по `name, id`.

Пример показывает ограничение данных: у товара Lidl в образцах фасовка не задана, поэтому цены за литр нет.

**`GET /api/products/{id}/prices/summary/`** — агрегаты.

| Параметр | Значение |
| --- | --- |
| `group_by` | `country` (по умолчанию), `store`, `none` |
| `interval` | `none` (по умолчанию, один итог на группу), `day`, `week` (с понедельника), `month`; по `purchased_on` |
| `price` | `paid` (по умолчанию), `list`, `normalized` |

```json
{"product": {"id": 2, "name": "GQ EgSB H-Milch 1,5%", "base_unit": "l"},
 "price": "paid", "group_by": "country", "interval": "month",
 "groups": [
  {"country": "DE", "currency": "EUR", "unit": "pcs",
   "total": {"count": 6, "min": "1.0500", "max": "1.0900", "avg": "1.0567",
             "first": {"price": "1.0500", "purchased_on": "2026-06-02"},
             "last": {"price": "1.0900", "purchased_on": "2026-10-01"},
             "change_percent": "3.81"},
   "buckets": [
    {"period_start": "2026-06-01", "count": 4, "min": "1.0500", "max": "1.0500", "avg": "1.0500", "last": "1.0500"},
    {"period_start": "2026-07-01", "count": 1, "min": "1.0500", "max": "1.0500", "avg": "1.0500", "last": "1.0500"},
    {"period_start": "2026-10-01", "count": 1, "min": "1.0900", "max": "1.0900", "avg": "1.0900", "last": "1.0900"}
   ]}
 ]}
```

- Ключ группы всегда включает валюту и единицу цены (`unit`): для `normalized` это `normalized_unit`, для `paid` и `list` — единица строки. Разные валюты или единицы дают разные группы.
- При `group_by=store` в группе вместо `country` — полный объект `store`; при `none` — только `currency` и `unit`.
- `avg` — простое среднее по наблюдениям, не взвешенное по количеству.
- `first` / `last` — по порядку `(observed_at, receipt_id, position)`.
- `change_percent` — `(last − first) / first × 100`; `null` при одном наблюдении или `first = 0`.
- Периоды без покупок в `buckets` не включаются. `buckets` — `[]` при `interval=none`.
- При `price=normalized` наблюдения без нормализованной цены пропускаются, их число — в `skipped_without_normalized` на уровне ответа; при других `price` этого поля нет.
- Больше 1000 интервалов в ответе при `interval`, отличном от `none`, — `400 range_too_large`: сузьте даты или укрупните интервал.
- Товар без наблюдений или пустое окно дат — `200`, `groups: []`.

### Альтернативы и сравнение

Альтернатива — другой товар с тем же обобщённым продуктом. Сравнивается цена за базовую единицу обобщённого продукта (`unit`: кг, л, шт), а не цена упаковки.

**`GET /api/products/{id}/alternatives/`** — исходный товар и альтернативы. **`GET /api/generic-products/{id}/comparison/`** — все товары обобщённого продукта, `base: null`.

| Параметр | Значение |
| --- | --- |
| `scope` | Только для `/alternatives/`: `generic` (по умолчанию) или `category` — товары всех обобщённых продуктов той же категории без потомков. У `/comparison/` параметр игнорируется |
| `country` | Один или несколько кодов через запятую, не больше 20; по умолчанию все страны |
| `date_from`, `date_to` | Окно наблюдений; по умолчанию вся история |
| `target_currency`, `rates` | Пересчёт по курсам из запроса, см. ниже |
| `page`, `page_size` | По товарам; 50, максимум 100 |

```json
{"base": {"id": 1, "name": "Молоко Фермерское 2,5% 850мл пэт"},
 "generic": {"id": 1, "name": "Молоко", "base_unit": "l"},
 "unit": "l",
 "conversion": {"target_currency": "EUR", "rates": {"RUB": "0.0098"}, "source": "request"},
 "overall": {"currency": "EUR", "offers_with_price": 1, "min": "1.2798"},
 "groups": [
  {"country": "DE", "currency": "EUR", "products_with_price": 0, "min": null, "max": null, "avg": null},
  {"country": "RU", "currency": "RUB", "products_with_price": 1,
   "min": "130.5882", "max": "130.5882", "avg": "130.5882"}
 ],
 "count": 2, "page": 1, "page_size": 50, "pages": 1,
 "results": [
  {"product": {"id": 1, "name": "Молоко Фермерское 2,5% 850мл пэт", "brand": null,
               "package": {"quantity": "850.000", "unit": "ml"}, "is_base": true},
   "offers": [
    {"country": "RU", "currency": "RUB", "observations": 1,
     "last": {"normalized_price": "130.5882", "paid_unit_price": "111.0000", "purchased_on": "2026-09-28",
              "store": {"id": 1, "name": "Магазин «Елена»", "city": "Кемерово", "country": "RU"}},
     "min": "130.5882", "max": "130.5882", "avg": "130.5882",
     "rank_in_group": 1, "diff_to_base_percent": "0.00",
     "converted": {"currency": "EUR", "last": "1.2798", "min": "1.2798", "max": "1.2798", "avg": "1.2798"},
     "rank_overall": 1}
   ]},
  {"product": {"id": 2, "name": "GQ EgSB H-Milch 1,5%", "brand": null, "package": null, "is_base": false},
   "offers": [
    {"country": "DE", "currency": "EUR", "observations": 6,
     "last": {"normalized_price": null, "paid_unit_price": "1.0900", "purchased_on": "2026-10-01",
              "store": {"id": 2, "name": "Lidl", "city": "Lindau", "country": "DE"}},
     "min": null, "max": null, "avg": null,
     "rank_in_group": null, "diff_to_base_percent": null, "converted": null,
     "rank_overall": null, "not_comparable_reason": "no_package"}
   ]}
 ]}
```

- Одна запись `offers` — пара «страна, валюта». `min` / `max` / `avg` — по цене за базовую единицу в окне дат, только по сравнимым наблюдениям.
- `last` у сравнимого предложения — последнее сравнимое наблюдение, у несравнимого — последнее наблюдение группы.
- `groups` — сводка по всему набору товаров, а не по странице: `min` / `max` / `avg` последних сравнимых цен товаров пары «страна, валюта».
- `rank_in_group` — место товара по последней цене за базовую единицу среди товаров той же страны и валюты: 1 — самый дешёвый, равные цены делят место. Считается по всему набору. Это сравнение между странами без курсов.
- `diff_to_base_percent` — отклонение от последней цены исходного товара в той же валюте. Если у исходного товара цены в этой валюте нет, а курсы заданы, — от его последней пересчитанной цены. Иначе `null`; у `/comparison/` всегда `null`.
- `not_comparable_reason` у предложения: `no_package` (штучная строка, у товара не задана фасовка) или `unit_mismatch` (единица цены не равна `unit` ответа, в том числе товар с другой `base_unit` при `scope=category`). У сравнимого предложения поля нет.
- Товар без наблюдений в окне остаётся в ответе: `offers: []` и `not_comparable_reason: "no_observations"` на уровне элемента `results`.
- Порядок `results`: исходный товар, затем сравнимые по `name, id`, затем несравнимые.
- Штучный товар без фасовки несравним, даже если `base_unit` обобщённого продукта — `pcs`: нормализованная цена считается только при заданной фасовке (для штучных — `1 pcs`).

**Пересчёт по курсам из запроса.** Сервер курсы не хранит, не загружает и не проверяет.

- `target_currency=EUR&rates=RUB:0.0098,KZT:0.0018` — «1 единица валюты слева = столько единиц целевой валюты».
- Курс — положительное десятичное число в обычной записи (до 12 цифр до и после точки, без знака и экспоненты), разбирается как `Decimal`. Не больше 10 пар; код валюты не повторяется; коды должны быть в справочнике; курс самой целевой валюты не задаётся (он равен 1); `rates` без `target_currency` — ошибка. Нарушение — `400`.
- `target_currency` без `rates` допустим: пересчитанными считаются только цены в самой целевой валюте.
- При заданном пересчёте в ответе: `conversion` (иначе `null`); блок `overall` — число предложений с пересчитанной ценой и общий минимум; в каждом предложении `converted` и `rank_overall` — место по пересчитанной последней цене среди всех предложений набора. Для валюты без курса и для несравнимого предложения — `converted: null`, `rank_overall: null`. Без пересчёта блока `overall` и поля `rank_overall` нет.

### Ограничения, которые нужно показать пользователю

- **Курсы только из запроса.** Курс вводит пользователь; сервер его не проверяет, не хранит и не привязывает к дате покупки. Сравнение цен, наблюдавшихся в разные месяцы, по одному курсу — приближение.
- **Давность цен.** Последние цены в разных странах могут быть разной давности — поэтому у каждой есть `purchased_on`.
- **Налог.** Цены включают или не включают налог в зависимости от чека (`Receipt.prices_include_tax`); признак в ответах не отдаётся, цены к одному виду не приводятся.
- **Скидка на весь чек** по строкам не распределяется и в цену не входит; скидка на строку входит.
- Паритет покупательной способности не учитывается. Валюты с тремя знаками после запятой в схему не помещаются.
- Товар виден в ценах только после сопоставления позиции чека с товаром; цена за базовую единицу есть только при заданной фасовке или у весовой строки.

### Производительность и откат

Число SQL-запросов эндпоинта не зависит от размера страницы: сводка цен, последние цены и пути категорий считаются на весь набор, тесты фиксируют это через `assertNumQueries`. Поиск `icontains` идёт последовательным сканированием. На каждый запрос действует `statement_timeout=2000` мс: тяжёлая выборка завершится `500 internal_error`. Замеров на больших объёмах нет.

**Откат.** У API нет моделей и миграций, схема БД не менялась, данные API не пишет. Откат — возврат коммитов (`git revert` слияний ветки API); действий с БД и `pg_dump` не требуется. Несовместимость относительно прежнего состояния одна: ошибки `400/401/403/404` DRF views теперь идут в формате `{"error": …}` вместо `{"detail": …}`; health этих кодов не отдаёт, его ответы не изменились.

Исправление C1 дополнительно ужесточает вход: управляющие символы в читаемых query-параметрах теперь дают `400`, в том числе TAB/LF/CR на краях, которые раньше мог удалить `strip()`. NUL в `q` раньше вызывал `500` у четырёх SQL-списков и допускался у категорий. Формат успешных ответов и ошибок, доступ и схема БД не меняются. Откат C1 — возврат его коммитов без действий с БД; он возвращает прежний дефект NUL.

### Отличия реализации от проекта контракта

Проект контракта — ответ задачи `task_musm7lej6k`. Реализация уточняет его так:

- `not_comparable_reason: "no_observations"` стоит на уровне товара в `results`, а не предложения: у такого товара предложений нет.
- Формат блока `overall` и поля `rank_overall` определён кодом (см. выше); `rank_overall` присутствует в каждом предложении только при заданном пересчёте.
- Дополнительные проверки `rates`: обязательный `target_currency`, запрет курса целевой валюты и повтора кода, только обычная десятичная запись. `target_currency` без `rates` допустим.
- `page` больше 1 при пустом наборе — `404 page_out_of_range`; проект оговаривал только случай `count > 0`.
- Неизвестный путь внутри `/api/` отвечает `404 not_found` на любой метод, а не `405`.
- Несуществующие `category`, `generic`, `brand` в фильтрах списков дают пустой список; `400` за несуществующий объект — только у `store` в истории цен и у кодов стран и валют.
- Обработчик ошибок дополнительно определяет `401 not_authenticated` и `403 permission_denied`.
- Идентификаторы, даты и время в примерах — фактические из QA-прогона на образцах; в проекте они были условными.

## Реализовано: task и `check_services`

Зарегистрированная задача **`health.ping`**, без аргументов, возвращает ровно `{"message":"pong"}`. Она идемпотентна, не записывает бизнес-данные и не вызывает внешние сервисы.

`python -X utf8 manage.py check_services` (из `backend/`) делает SQL/cache probes, затем `ping.apply_async(connection=broker, retry=False, expires=10)` и `pending.get(timeout=5)` через настроенный Redis result backend. `task_always_eager=False`, JSON serializers, result TTL 60 секунд. Локальный вызов функции или inspect ping не доказывают выполнение этой цепочки.

При успехе stdout содержит JSON и команда завершается с exit 0:

```json
{"database":"ok","redis":"ok","celery_task":{"status":"ok","result":{"message":"pong"}}}
```

При отказе JSON всё равно выводится, затем `CommandError: Один или несколько сервисов недоступны.` и exit 1. `database`/`redis` — строка `ok` либо соответствующий безопасный код; `celery_task` — `{"status":"error","code":"celery_task_unavailable"}`, а при полученном неправильном результате — `unexpected_task_result`. Ошибка одного probe не отменяет другие проверки CLI. Неожиданные probe/task exceptions также скрываются за фиксированными кодами.

`get(timeout=5)` ограничивает ожидание результата, но не всю команду вместе с SQL/cache/connect. Истечение timeout не отменяет принятую task. Позднее выполнение безопасно для ping; для будущих пользовательских задач понадобится отдельное решение об идемпотентности. HTTP health не ставит task в очередь и не читает results DB 1.

## Планируется

API фото чеков, распознавания магазина/адреса и товаров/стоимостей, ввода чеков, сопоставления позиций с товарами и статистического дашборда ещё нет. К предметной модели (приложения `stores`, `catalog`, `receipts`, [data-model.md](data-model.md)) есть только [API чтения](#реализовано-api-чтения-каталога-и-цен): записи через HTTP и админки нет, данные вводятся только кодом. Хранение курсов валют на сервере не реализовано. OCR-провайдер, авторизация и контракты этих функций не выбраны. Endpoint публикации задач и получения их результатов по HTTP не входит в реализованный scaffold.
