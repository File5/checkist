# Frontend Checkist

## Каркас и навигация

`App.tsx` владеет оболочкой: тёмной шапкой (эмблема и «Чекист», переключатель темы, меню «Каталог / Чеки / Статистика / Обработка / Состояние сервисов»; гостю в меню — только «Состояние сервисов» и «Войти», вошедшему в режиме `accounts` — ещё его имя ссылкой на `/account`), единственным `h1`, document title (`Чекист — <экран>`) и содержимым текущего маршрута. Оболочка же решает, показывать ли страницу: гость на любом адресе, кроме `/health`, видит вход, а разделы «Дубли» и «Категории» открыты только модератору каталога — [вход и сессия](#вход-сессия-и-разделение-пользователей-к1). Экран входа приложение рисует один, без оболочки: свой `<main>`, а `h1#page-heading` ему передаёт оболочка ([тема, бренд и вход](#тема-бренд-и-экран-входа)). При первом открытии и смене pathname фокус переходит на `h1#page-heading` (`tabIndex=-1`); изменение только query не забирает фокус из формы. Есть ссылка «К содержимому». Каталог не запрашивает health и не зависит от его результата. F5 подключает настоящие `CatalogPage`, `CategoryPage` (F3) и `ProductPage` (F4) вместо точек подключения F2; данные загружаются адаптерами F1, runtime-mocks и вымышленных цен в UI нет.

| `/catalog/classification` | Категории товаров: предположения с подтверждением; `status` (`confirmed`, `rejected`, `superseded`, `all`; без него — ожидающие), `product`, `page` |
| `/login` | Экран входа: логотип и форма без оболочки приложения; параметров нет. Настоящий вход (`features/auth`), тот же экран, что гость видит на любом другом адресе; после входа и для уже вошедшего — каталог с заменой записи истории; в `local_single` — «Страница не найдена» |
| `/account` | Аккаунт: имя пользователя, смена пароля, выход; только в режиме `accounts`, в `local_single` — «Страница не найдена» |

`/` — алиас каталога без принудительного redirect; build создаёт `/catalog`. Один завершающий слэш допустим. ID и page — положительные safe integers, небезопасные значения не округляются. Первая страница подразумевается и при build не записывается. Поиск trim, 2–100 Unicode code points; пустое значение означает отсутствие фильтра. Коды стран/валют приводятся к верхнему регистру, проверяется их синтаксис; существование в справочнике проверяет API. Даты — настоящие календарные `YYYY-MM-DD`, нижняя граница не позже верхней. Управляющие символы в известных параметрах запрещены. Неизвестные и чужие этому маршруту параметры игнорируются, повторённый параметр берётся по последнему значению. Кодирование выполняет `URLSearchParams`; строки не склеиваются в query вручную.

Некорректный известный query даёт экран «Некорректная ссылка» со сбросом параметров через replaceState; запрос данных в этом состоянии не запускается. Положительный page сохраняется даже без знания pages: `page_out_of_range` обрабатывает экран, получивший API-ответ, со ссылкой на первую страницу. Смена фильтров в F3/F4 должна явно устанавливать `page: 1`.

Используются History API и popstate без библиотек. `Link` рендерит обычный `<a href>` и перехватывает только основной клик без модификаторов: Enter поддерживается браузером, Ctrl/Cmd/Shift/Alt, другие кнопки мыши, target, download, фрагменты и внешние ссылки сохраняют нативное поведение. Back/Forward читают маршрут и фильтры из адреса. При переходе из каталога/категории в товар исходный URL хранится в history state; история фильтров товара сохраняет этот контекст, reload читает его заново. Контекст принимается только для корректного внутреннего URL совместимого списка или связанной detail-страницы (job/receipt/product, см. раздел распознавания). При прямом входе `returnTo` отсутствует: после загрузки F4 предлагает категорию товара. При возврате в исходный список App ждёт загрузки ссылки выбранного товара и возвращает ей фокус. Если пользователь уже перевёл фокус, ожидание отменяется; если товар исчез или список не загрузился, остаётся заголовок. Уход и изменение query отключают observer. Фактический фокус и прокрутку принимает человек.

Прямые URL и reload поддерживаются SPA fallback Vite dev/preview: сервер отдаёт `index.html` для этих путей. Это проверяется HTTP, отдельно от работы React в браузере. Production hosting, reverse proxy и их fallback не настроены и не подтверждаются.

Экраны используют собственные CSS с префиксами. Общая визуальная система — красная с золотом, две темы: тёмная по умолчанию и светлая. Все цвета записаны только в `src/theme/tokens.css` переменными `--ck-*`; остальные CSS читают `var(--ck-*)` и не содержат hex/rgb-значений ([тема](#тема-бренд-и-экран-входа)). Основной текст — Segoe UI/system-ui, заголовки и вывеска — Oswald из локального файла; панели с радиусом 4–6 px, max-width 920 px, breakpoint 540 px. Красная заливка — только бренд и главное действие, золото — акцент (ссылки и активные пункты тёмной темы, декор), успех зелёный, предупреждение оранжевое, ошибка — сдвинутый от бренда оттенок и никогда только цветом. Ссылки действий, кнопки, input/select имеют высоту от 44 px и focus-visible. Вертикальной прокруткой владеет страница; глобальный overflow не скрывает ошибки. Общие компоненты статичны; движение есть только у круговой диаграммы (переходы подсветки, отключены при `prefers-reduced-motion: reduce`).

### Интерфейсы для F3/F4/F5

Все публичные функции и типы навигации экспортируются из `src/navigation/index.ts`:

```ts
type CatalogQuery = { q?: string; generic?: number; page: number }
type HistoryQuery = {
  store?: number; country?: string; currency?: string
  date_from?: string; date_to?: string; page: number
}
type NavigableRoute =
  | { kind: 'catalog'; query: CatalogQuery }
  | { kind: 'category'; categoryId: number; query: CatalogQuery }
  | { kind: 'product'; productId: number; query: HistoryQuery }
  | { kind: 'health' }
type Route = NavigableRoute
  | { kind: 'not-found'; path: string }
  | { kind: 'invalid-query'; path: string; fields: string[]; resetTo: string }
type NavigationTarget = string | NavigableRoute
type NavigateOptions = { replace?: boolean }
type NavigationSnapshot = { href: string; route: Route; returnTo?: string }

parseRoute(input: string | URL): Route
buildRoute(route: NavigableRoute): string
parseCatalogQuery(search: string | URLSearchParams): ParsedQuery<CatalogQuery>
parseHistoryQuery(search: string | URLSearchParams): ParsedQuery<HistoryQuery>
// ParsedQuery<T> = { query: T; invalidFields: string[] }
buildCatalogQuery(query: CatalogQuery): string
buildHistoryQuery(query: HistoryQuery): string
// buildQuery возвращает ведущий '?' или ''. Невалидный build бросает RangeError.
navigate(target: NavigationTarget, options?: NavigateOptions): void
useNavigation(): NavigationSnapshot
useRoute(): Route
```

`navigate` допускает только HTTP(S) этого origin, публикует snapshot сразу после push/replace (браузер сам не вызывает popstate), не добавляет дубликат текущего URL. `Link` — именованный export из navigation, default export из `navigation/Link.tsx`; props: `to: NavigationTarget`, `replace?: boolean`, остальные нативные props ссылки кроме href (включая onClick). `createNavigation(environment)` из `navigation/controller.ts` — тестируемый store с `navigate/getSnapshot/subscribe`; `NavigationEnvironment` предоставляет `getHref/getState/pushState/replaceState/listenPopState`. Импорт helpers в Node не требует window; browser hooks используются только в SPA.

`RequestState` — default export из `components/RequestState.tsx`; props — объединение:

```ts
{ kind: 'loading'; message?: string }
| { kind: 'error'; message?: string; onRetry: () => void; retryDisabled?: boolean }
| { kind: 'empty'; message: string; action?: ReactNode }
```

Loading резервирует min-height без фиксированной высоты. Все варианты используют `aria-live="polite"`, `aria-busy` true только при loading. Error по умолчанию показывает локальный безопасный текст и «Повторить»; message должен быть собственным переводом UI, серверные message/fields/исключения передавать запрещено. Пустое состояние допускает действие (обычно Link). Успешное содержимое рендерит владелец запроса; запросы, отмена, гонки и соответствующие блоки aria-busy остаются у feature-экрана.

`Pagination` — default export из `components/Pagination.tsx`; props:

```ts
{ page: number; pages: number; buildPageHref: (page: number) => NavigationTarget; label?: string }
```

`buildPageHref` меняет только page и сохраняет текущие фильтры. Default label — «Страницы результатов». Навигация — нативные ссылки, ровно одна имеет `aria-current="page"`; предыдущая/следующая скрываются на границах. При pages 0/1 либо некорректных счётчиках компонент не рендерит навигацию; выход за диапазон обрабатывает экран. На больших наборах остаются первая/последняя и окно около текущей страницы (до семи ссылок страниц), без создания тысяч элементов.

Ожидаемые props экранов экспортированы из `src/pages/types.ts`:

```ts
CatalogPageProps = { query: CatalogQuery }
CategoryPageProps = { categoryId: number; query: CatalogQuery }
ProductPageProps = { productId: number; query: HistoryQuery; returnTo?: string }
```

Feature-экраны рендерятся под общим h1, собственный h1/main/shell не создают; имена категории/товара используют h2. Они владеют формами и запросами, используют native label/input/select, самостоятельные inline-сообщения. Новых систем состояния, оверлеев, уведомлений или локализации не добавлено; UI русский, форматирование принадлежит F1. F3/F4 могут импортировать общие компоненты, навигацию и props без правок файлов F2.

## Тема, бренд и экран входа

Редизайн клиента: красная схема с золотыми акцентами вместо зелёной, тёмная тема по умолчанию и светлая по переключателю, логотип «ЧЕКИСТ — продуктовая разведка», экран входа `/login`. Имена классов, селекторы, медиа-блоки и геометрия экранов не менялись — заменены только значения цветов, радиусов и шрифтов. Вид в браузере принимает человек по [frontend/REDESIGN_ACCEPTANCE.md](../frontend/REDESIGN_ACCEPTANCE.md).

### Токены

`frontend/src/theme/tokens.css` — единственный файл проекта с цветами. Тёмные значения записаны в `:root`, светлые — в `:root[data-theme="light"]`; светлый блок переопределяет только цвета. Шапка (`--ck-header-*`) и подложка логотипа (`--ck-logo-bg`) одинаковы в обеих темах. В начале файла — справочник токенов, соответствие прежних зелёных значений и посчитанные контрасты (4,5:1 для текста, 3:1 для рамок полей и кольца фокуса).

| Группа | Токены |
| --- | --- |
| Поверхности и текст | `--ck-bg`, `--ck-surface`, `--ck-surface-raised`, `--ck-text`, `--ck-text-muted` |
| Бренд (красная заливка) | `--ck-brand`, `--ck-brand-hover`, `--ck-brand-active`, `--ck-on-brand` |
| Акцент (золото) и ссылки | `--ck-accent`, `--ck-on-accent`, `--ck-accent-text`, `--ck-accent-bg`, `--ck-link`, `--ck-link-hover` |
| Линии и фокус | `--ck-border`, `--ck-border-field`, `--ck-divider`, `--ck-focus` |
| Состояния | `--ck-<состояние>-text` / `-bg` / `-border` для `error`, `success`, `warning`, `info`, `neutral` |
| Недоступное, всплывающее | `--ck-disabled-*`, `--ck-popover-border`, `--ck-popover-shadow`, `--ck-panel-shadow` |
| Шапка и логотип | `--ck-header-*`, `--ck-logo-bg` |
| Геометрия и шрифты | `--ck-radius-sm` (4 px), `--ck-radius` (6 px), `--ck-font-body`, `--ck-font-display` |
| Графики | `--ck-series-1` … `--ck-series-8`, `--ck-series-other`, `--ck-series-special`, `--ck-plot-grid`, `--ck-plot-axis`; имена `--ck-chart-*` остаются в `Charts.css` и ссылаются на них |

Правила смысла: красным текстом в тёмной теме не пишут ничего (красный — заливка под `--ck-on-brand`); золотой текст — только `--ck-accent-text` / `--ck-link` (в светлой теме там тёмная охра и тёмно-красная ссылка); ошибка — коралловая в тёмной и малиновая в светлой теме, всегда вместе с текстом, значком, рамкой или полосой. Новый цвет добавляется токеном в оба блока `tokens.css`; hex/rgb вне этого файла в рабочих CSS запрещены (`theme/theme.test.ts`, `features/auth/auth-css.test.ts`, `features/classification/classification-css.test.ts` читают текст правил). `--ck-logo-bg` равен измеренному фону файлов логотипа `#0f0f0e` (`src/assets/brand/README.md`); менять их только вместе.

Кнопки. Правило `button` в `App.css` — главная кнопка: красная заливка `--ck-brand` с текстом `--ck-on-brand`. Контурную кнопку экран задаёт своим классом (`*-secondary`, `.ck-catalog-reset`, кнопки пагинации): фон `--ck-surface`, рамка `--ck-border-field` либо `--ck-link`, текст `--ck-link`, наведение — `--ck-surface-raised`. Состояния наведения и нажатия главной кнопки записаны через `:where()` и весят как `button`: класс контурной кнопки всегда сильнее, поэтому при наведении и нажатии она не получает заливку бренда. Новому классу контурной кнопки задавайте и фон, и `border-color` — без него рамка унаследует цвет бренда.

### Переключение и хранение

- Тема — атрибут `data-theme="light"` на `<html>`; без атрибута действует тёмная. Системная настройка `prefers-color-scheme` не учитывается.
- Выбор хранится в `localStorage` под ключом **`checkist.theme`**: значение `light` — светлая, любое другое, отсутствие ключа или недоступное хранилище — тёмная. Больше нигде в `src/` `localStorage` не используется.
- `src/theme/theme.ts`: `createThemeStore` (все обращения к хранилищу и документу защищены от исключений), `useTheme()`, `applyThemeToDocument` — ставит атрибут и цвет `<meta name="theme-color">`. Событие `storage` переносит выбор в другие открытые вкладки.
- `ThemeToggle` — обычная кнопка с подписью текущей темы («Тема: тёмная» / «Тема: светлая»); нажатие меняет тему сразу и не трогает фокус. `placement="header"` берёт цвета шапки; на узком экране (≤ 540 px) в шапке видна только иконка, подпись остаётся именем кнопки.
- **Встроенный скрипт в `index.html`** выполняется до первой отрисовки: читает `checkist.theme` и для `light` ставит атрибут и `theme-color`, поэтому сохранённая светлая тема не мигает тёмной при загрузке, в том числе на медленной сети. **Оговорка для развёртывания:** при строгой Content-Security-Policy на сервере (без `'unsafe-inline'` в `script-src`) встроенный скрипт будет заблокирован — его нужно разрешить по хэшу (`'sha256-…'` от точного текста скрипта; пересчитывать при любой его правке) либо вынести в отдельный файл, подключённый в `<head>` без `defer` и `type="module"`. Без скрипта приложение работает, но светлая тема включается только после запуска React — со вспышкой тёмной. Сейчас CSP не настроена: production-развёртывания нет.

### Границы данных

- Runtime-схемы сохраняют `position=0`: позиция строки — неотрицательное безопасное целое, ID — положительное. История использует ключ `receipt_id:position`, без проверки позиции на truthiness. Невалидная обязательная запись даёт ошибку всего блока, строки молча не отбрасываются.
- Нулевые счётчики каталога, магазинов и пустых страниц допустимы (`page=1`, `count=pages=0`). `observations` внутри существующей группы/магазина товара, `total.count` и `buckets[].count` положительны: backend строит эти группы только из наблюдений. `skipped_without_normalized` может быть нулём. Размер массива страницы ограничен `page_size`, но не счётчиком `count`: COUNT и выборка могут видеть разные SQL-снимки при конкурентном вводе.
- В ответах коды стран/валют принимаются как непустые строки длиной до 2/3 Unicode-символов: модели справочников не проверяют ISO-синтаксис и сериализация их не меняет. Значения сохраняются без изменения регистра. Фильтры query по-прежнему требуют ISO-синтаксис; введённый через админку нестандартный код может отображаться, но backend не принимает его как фильтр. `model`, `gtin`, город, адрес и названия-сопоставления могут быть пустыми; `attributes` остаётся произвольным JSON. Decimal принимаются строками с фиксированной точностью, со знаком и нулём; календарные даты и UTC-моменты с `Z` проверяются отдельно.
- Аудит R3 со ссылками на фактические ограничения backend, регрессиями и сценарием ручной приёмки — [frontend/R3_ACCEPTANCE.md](../frontend/R3_ACCEPTANCE.md).

- Это **наблюдения покупок из чеков**, не текущие предложения магазина. Отображаются только сопоставленные товарные позиции продаж; возвраты, залог и услуги в историю не входят.
- Валюты и фактические единицы не смешиваются. Нормализованная цена подписана своей единицей; `comparable` означает совместимость единиц, не налоговой базы. Налоги неизвестны, скидка всего чека по товарам не распределена, средняя в сводке невзвешенная.
- Decimal остаются строками; UI не считает деньги через JS Number. `null` означает отсутствие данных, не нулевую цену. Интерфейс русский, десятичная запятая, явный код валюты; `purchased_on` — локальная календарная дата, момент без известного timezone подписан UTC.
- Карточка отдаёт до 50 магазинов и aliases без признака усечения. Поиск `/stores/` охватывает **все** магазины выбранной страны, включая точки без покупок товара; полного списка только магазинов товара API не предоставляет. Варианты выбора не выводятся из текущей страницы истории. Адрес/timezone обогащаются по ID из карточки, просмотренных страниц справочника и успешной сводки `group_by=store`, которая уже содержит полные объекты магазинов за выбранный период. Обогащение из сводки не добавляет запросов и не блокирует историю при её отказе.
- История, сводка и фильтр используют одну подпись: `ID 51 · Same Chain · адрес · Berlin · DE`. ID стоит первым, чтобы оставаться различимым и при длинном тексте в native select. Если адрес отсутствует, пуст или ещё не загружен: `ID 51 · Same Chain · Berlin · DE · адрес неизвестен`. При прямом выборе ID из URL краткие сведения выбранной точки берутся из загруженной истории только для подписи; без них остаётся `ID 51 · Не указано · адрес неизвестен`. Отказ справочника сохраняет карточку, строки истории, независимую сводку и известные адреса; неизвестные точки остаются различимыми по ID. Фильтр явно подписан как недоступный, локальный повтор и удаление выбранного магазина доступны.
- В контракте нет `/api/stores/{id}/` и фильтра списка магазинов по ID: доступны только `country`, `q`, `page`, `page_size`. Автоматической адресной дозагрузки неизвестных ID и полного обхода справочника нет. Пока адрес не появился в карточке, успешной сводке или просмотренной странице поиска, UI сохраняет корректный fallback с ID. Поиск по названию/городу и переходы страниц позволяют получить адрес вручную; ID и адрес не являются серверными параметрами поиска.
- ID в JSON — JS-числа. Адаптер и навигация требуют положительный `Number.isSafeInteger`; ID выше `Number.MAX_SAFE_INTEGER` отвергаются, округлённые ссылки не создаются. Полный диапазон BigAutoField пока не поддержан.

Регрессионные проверки подписей и сценарий ручной приёмки — [R1: различимые точки в истории цен](../frontend/R1_ACCEPTANCE.md).

### Фокус при локальных обновлениях (R2)

Каждый независимый запрос имеет устойчивый заголовок с `tabIndex=-1` и `data-request-focus-target`: дерево категорий, сведения категории, товары, карточка, история, сводка; справочник магазинов использует устойчивый `legend` «Магазин». `useLocalRequestFocus` и тестируемый контроллер `local-request-focus.ts` из `src/components/` следят за фокусом только внутри своего блока. `RequestState` помечает кнопку повтора `data-request-retry`; собственная кнопка справочника использует ту же метку. Эти метки не добавляют ARIA-роли или live-регионы.

Если сфокусированная кнопка/ссылка удаляется или становится недоступной при обновлении, фокус получает заголовок этого же блока во время loading. После успеха он остаётся на заголовке результата; после повторной ошибки запроса возвращается на доступную кнопку «Повторить» своего блока. Если ответ требует исправления параметров или сообщает об отсутствующем объекте, заголовок сохраняется. Устойчивая цель карточки существует и после `not_found`. Сохранившиеся доступные контролы пагинации, поиска и фильтров сохраняют фокус. Сейчас кнопки страниц магазинов исчезают на время loading, поэтому их локальная цель — `legend` «Магазин»; ссылки страниц истории и товаров используют собственный h2.

Тот же механизм охватывает локальные «Сбросить фильтры», первую страницу при `page_out_of_range`, сброс поиска магазинов и исчезающую кнопку «Убрать магазин». Сброс формы каталога по-прежнему возвращает фокус в поле поиска; применение фильтров/поиска из устойчивого поля или кнопки оставляет его в форме. Переход pathname принадлежит App/F2 и переносит фокус на h1; локальный хук не меняет навигацию и возврат к выбранному товару.

При уходе фокуса в другой блок ожидание восстановления отменяется, в том числе если позже фокус оказался на body. Потеря фокуса на body компенсируется только при подтверждённой принадлежности удалённого/недоступного элемента этому блоку. На первый ответ без локального действия переноса нет. Хук обрабатывает только принятые снимки состояния после React commit; существующие AbortController/generation guards владельцев запросов не допускают устаревшие или отменённые результаты. На unmount локальное ожидание и focusin-listener удаляются. Существующий `[tabindex]:focus-visible` показывает рамку фокуса (`--ck-focus`: золотая в тёмной теме, синяя в светлой); повторное focus на уже активном заголовке не выполняется. Существующие `aria-live="polite"`, `role="status"` и `aria-busy` сохранены, дополнительные объявления не добавлены.

Поддерево с атрибутом `data-request-focus-own` (`focusOwnerAttribute`) само возвращает фокус после своего действия; для блока оно — «другое место» (`insideLocalBlock`): блок не запоминает его элементы и не переносит их фокус на свой заголовок. Сейчас так помечена каждая карточка вырезки на экране задания: её действие — подтверждение, цель после исчезновения формы — сообщение карточки. Действия самого блока вне карточек («Повторить обновление») обрабатываются по-прежнему.

Правила выбора цели, последовательности loading/error/ok, поколения запросов и разметка проверяются Vitest в Node и SSR без новых зависимостей. Реальный DOM-фокус, прокрутку, screen reader и визуальное поведение принимает человек по сценарию ниже; результаты и ограничения R2 — [отчёт](../frontend/R2_ACCEPTANCE.md).

```powershell
# Если выбран другой свободный Vite-порт:
node frontend/scripts/check_catalog_proxy.mjs healthy http://127.0.0.1:15174
```

Скрипт без новых зависимостей использует настоящий fetch и исходные адаптеры с **явным baseUrl** напрямую и через Vite. Сверяет HTTP, Content-Type, Allow, полный JSON и результат адаптера; не переносит health-требование Cache-Control на каталог. Проверяет категории/detail, generic, товары/detail, history/summary, магазины, поиск и фильтры, минимум две страницы `page_size=1` у товаров, наблюдений и магазинов, 400 (page_size/q/date_from) и 404 `page_out_of_range`/`not_found`. Все существующие ID получает из ответов; отсутствующий ID категории вычисляет из полного дерева. QA-набор должен содержать хотя бы два товара, две точки и один Product с двумя покупками; при нехватке данных скрипт завершается с объяснением. Во время сверки QA-данные не менять: общего снимка между HTTP-запросами нет.

Ошибки конфигурации, недоступный API/proxy, неожиданный статус/JSON или результат адаптера дают `Catalog check FAILED: …` и exit 1. Единственный режим — `healthy`; остановки Postgres/API проверяются отдельно человеком, успешный negative-test не равен успешному HTTP-прогону. Скрипт требует `POSTGRES_DB=checkist_qa`, `VITE_API_BASE_URL=/api` и разные HTTP loopback origins; `DEV_API_PROXY_TARGET` задаёт прямой адрес API.

## Распознавание и чеки (И1–И5)

Экраны подключены в App к настоящему локальному API, без вымышленных данных. Загрузка принимает один JPEG/PNG/WebP: локально проверяет тип и размер по полученным лимитам, показывает предпросмотр через object URL и освобождает его при замене/уходе. Сервер проверяет фактические байты, одиночный кадр, размер и пиксели. Неизвестный браузеру MIME не заменяет серверную проверку. Указано, что установленный Codex передаёт фото облачной модели. Загрузка и retry разрешены при любом состоянии воркера, включая `absent`.

Состояние воркера клиент берёт только из текущего ответа сервера — `executor.state` (`idle`/`busy`/`absent`, [контракт](api-contract.md)). Поле необязательно на проводе: его отсутствие (старый сервер) и незнакомая строка нормализуются guard'ом в `unknown`, нестроковое значение отклоняет ответ как `invalid_response`. Тексты — `uploadExecutorNote`/`jobExecutorNote` в `features/recognition/labels.ts`:

| Где | `idle` | `busy` | `absent` | `unknown` |
| --- | --- | --- | --- | --- |
| Страница загрузки | «Воркер распознавания запущен и ждёт заданий.» | «Воркер распознавания сейчас обрабатывает задание. Новое фото встанет в очередь.» | «Воркер распознавания не запущен. Задание будет ждать в очереди, пока воркер не запустят.» (`ck-rec-warning`) | ничего |
| Задание, `queued` | ничего | «Воркер занят другим заданием. Это задание начнётся после него.» | то же предупреждение | ничего |
| Задание, не `queued` | ничего | ничего | ничего (у зависшего — прежний текст `stalled`) | ничего |

Уведомление после загрузки («Фото загружено. Задание принято.» / «Это фото уже было загружено…») и повтора («Создано новое задание обработки.») текста о воркере не содержит: строка о воркере строится по свежему снимку, а не по ответу POST. Пока последнее обновление не удалось (`refreshError`) или данные ещё не получены, о воркере ничего не утверждается — виден только блок ошибки с повтором.

`src/api/recognition.ts` и `receipts.ts` используют `http.ts` и runtime-схемы для Photo, Job, ReceiptImage, Receipt, строк, скидок и налогов, включая nullable поля и Decimal strings. Эталоны тестов читаются прямо из `backend/recognition/tests/fixtures/public/`. Успешный HTTP без подходящего JSON становится `invalid_response`; provider payload/message не показываются. Деньги форматирует `lib/format.ts` строками/BigInt, с запятой и валютой. Дата покупки отображается в timezone магазина, технические моменты задания — явно UTC. Неизвестные поля чека подписаны «Не распознано»; nullable данные needs_review — «Не прочитано».

CSRF transport: `GET /api/recognition/csrf/` устанавливает cookie и возвращает token/limits/executor. Token хранится только в памяти, параллельные читатели разделяют запрос и могут отменяться независимо. Все новые запросы используют `credentials: same-origin`; POST отправляет `X-CSRFToken`. Upload — FormData, Content-Type с boundary устанавливает fetch; cancel/retry — JSON `{}`. Таймаут чтения/действий 15 с, upload 60 с; AbortSignal прекращает ожидание клиента. После `csrf_failed` token сбрасывается; новое явное действие получает новый token. POST никогда не повторяется автоматически. При сетевой ошибке действие могло сохраниться: UI предлагает проверить обработку до повтора. Уход со страницы/отмена fetch не отменяют серверный job.

Vite dev **и preview** передают `/api` и `/media` на один `DEV_API_PROXY_TARGET`, без rewrite, с changeOrigin. `DJANGO_CSRF_TRUSTED_ORIGINS` должен содержать точный origin клиента (порт включён). Поддержан один browser origin, внешний CORS не настроен. `safeMediaUrl` разрешает только относительные пути `/media/`, без внешнего host, traversal, query/hash и encoded separators. В v1 backend принимает только `MEDIA_URL=/media/` (default при отсутствии переменной); любое другое значение, включая пустое, даёт ранний `ImproperlyConfigured`. Клиентские проверки URL и Vite proxy рассчитаны только на `/media/`; изменение префикса требует согласованной правки клиента и proxy. Исходник, preview и вырезки имеют alt и отдельный fallback/повтор при ошибке изображения. MEDIA отдаётся Django только при DEBUG, независимо от флага локального API. Описания «Vite только /api» в исторических backend-документах относятся к состоянию до И1.

Job detail опрашивается после ответа раз в 2 с, без перекрытия запросов. После сетевых отказов интервалы 2/4/8/15 с, в скрытой вкладке не менее 10 с; возвращение во вкладку обновляет данные. Последний корректный снимок сохраняется с локальной ошибкой/повтором. Старое поколение запроса и меньшая version не принимаются; heartbeat той же version допустим. Terminal status прекращает опрос. Список заданий обновляется, пока видимые задания active. Смена route/query и unmount отменяют запросы и таймеры. Cancel/retry приостанавливают чтение на время POST. `actions.can_cancel/can_retry` управляют доступностью; сервер повторно проверяет состояние, 409 приводит к обновлению снимка. Cancel running показывает «Отмена запрошена» до подтверждения воркера. Страница загрузки тем же контроллером опрашивает `GET /api/recognition/csrf/`, только пока `executor.state=absent`: предупреждение исчезает после запуска воркера без перезагрузки; любое другое состояние и unmount останавливают опрос, ручное «Обновить условия загрузки» возобновляет его при `absent`. На время отправки фото фоновое чтение приостановлено; фоновый опрос не отключает кнопки — их отключает только ручное обновление.

Шапка задания, исходник и вырезки независимы; вырезки обновляются при изменении items/version, preview — этапа. `needs_review` показывает вырезку, фиксированные причины и безопасный нормализованный результат в details. Успешные imported/reused/updated с issues показывают «Замечания распознавания»: наличие issues само по себе не делает их needs_review. Единую подпись статуса и один компонент замечаний используют задание и чек — см. [сгруппированные замечания](#сгруппированные-замечания-распознавания). Вырезку `needs_review` человек исправляет и подтверждает в её карточке — см. [исправление и подтверждение](#исправление-и-подтверждение-вырезки-needs_review). Серверного черновика нет.

Список чеков имеет поиск по данным контракта, период, продажу/возврат, сортировку и пагинацию в URL. Пустой список предлагает загрузку; пустой результат фильтров — сброс. Детальный чек независимо загружает шапку, все изображения, строки, скидки и налоги с локальными loading/empty/error/retry и отдельными страницами. Отказ шапки сохраняет строки с предупреждением об неизвестной валюте. Несопоставленный товар явно подписан; залог и скидки ссылаются на строку или её ID на другой странице. Таблица строк имеет собственную фокусируемую область горизонтальной прокрутки; мобильная страница сохраняет действия. Локальный фокус принадлежит `useLocalRequestFocus`; pathname/h1 — App. Визуальное соответствие и фактический DOM-фокус принимает человек.

Переходы job → receipt → catalog product и receipt → job сохраняют корректный внутренний источник в History state. Видны «К заданию»/«К чеку»; query товара и reload сохраняют возврат. Back/Forward восстанавливают прежние записи истории. При прямом входе контекста нет, доступны списки/каталог. Контекст списка чеков/заданий сохраняет фильтры; App восстанавливает фокус ссылки списка после локального возврата. Контекст не передаётся новой вкладке; её поведение — прямой вход.

Новый CLI [check_recognition_proxy.mjs](../frontend/scripts/check_recognition_proxy.mjs) запускает настоящий Vite dev/preview и свои `recognition_worker --once` с fake, загружает demo через proxy, использует те же исходные адаптеры/runtime guards через Vite SSR loader. Node явно переносит QA CSRF cookie и Origin: это проверяет HTTP transport, но не browser cookie policy/React. Нужен отдельный пустой QA DB/project и Django с тем же env/MEDIA, без внешнего OCR-worker; preview требует build. Скрипт отказывается от dev ports/DB, внешних origins и Codex provider. Проверяет состояние воркера на настоящем сервере теми же функциями клиента: опрос условий при `absent`, переход в `idle` после запуска простаивающего воркера и остановку опроса, возврат в `absent` после его завершения, `queued`+`absent` — предупреждение, `queued`+`busy` — строка о занятом воркере, `running`/terminal — без строки, уведомления загрузки/повтора без текста о воркере. Проверяет 202, client polling/его остановку, PNG MEDIA и исходные байты, 2 чека/6 строк/5 товаров, replay, queued/running cancel, retry/409, новое фото того же Receipt без новых строк/товаров, needs_review и 403/400. После прогона закрывает свои Vite/таймеры/воркеры, оператор останавливает Django/Compose. [Команды, результаты и ручная приёмка](verification.md#распознавание-сквозная-проверка-клиента-и5), [краткий показ](../frontend/I5_ACCEPTANCE.md).

Это единое локальное пространство DEBUG + ALLOW_LOCAL_RECOGNITION_API + loopback, без пользовательского доступа. Fake распознаёт фиксированные DTO, качество OCR произвольных фото не подтверждено. Автоматической очистки MEDIA/заданий нет; успешный job не retryable, точный повтор возвращает последний job. Уже сохранённые части cancel не удаляет. Возможное ложное объединение по точному store/time/total и stale admin POST при параллельном OCR остаются ограничениями v1.

### Сгруппированные замечания распознавания

Карточка вырезки в задании (`features/recognition/ReceiptImages.tsx`) и блок фото в чеке (`features/receipts/ReceiptContent.tsx`) выводят issues одним компонентом `components/RecognitionIssues.tsx` (props `issues`, `status`). Вся логика — чистые функции `lib/recognition-issues.ts`, стили — `.rec-issues*` в `App.css`. Компонент не делает запросов, не хранит состояние и не имеет live-областей. Серверный `message`, имена и значения закрытых реквизитов не выводятся: текст собирается только из словарей клиента и целых чисел контекста.

**Контракт и guard.** Сервер отдаёт у каждого issue `reason`, `severity`, `context {entity, index, position, attribute}` ([api-contract.md](api-contract.md#issues-вырезки-reason-severity-context)). `isRecognitionIssue` в `api/recognition-schema.ts`:

| Ответ | Поведение |
| --- | --- |
| нет ни одного из трёх ключей | принят как ответ старого сервера |
| есть часть ключей, неверный тип, `severity` вне `info`/`warning`/`error`, `index` вне 0..9999, `position` вне 1..32767 | весь ответ отклонён, `invalid_response` |
| `reason` вида `^[a-z_]{1,64}$` не из словаря; `entity`/`attribute` вида `^[a-z_]{1,32}$` вне перечня | принят, показывается как `unknown`, само имя не выводится |

Правила `code`/`field`/`message` прежние. `attribute` и `index`/`position` могут быть `null`.

**Fallback для старого ответа** (`issueView`): `reason = code`; `severity = error` при статусе вырезки `needs_review`/`failed`, иначе `warning`; `entity`/`index`/`attribute` — `fieldContext(field)`, тот же разбор, что `issue_context` на сервере (включая закрытые подпути: `/lines/N/product_hint…` → строка/товар, прочее `/lines/N/…` → строка/unknown, закрытые `/discounts/N/…`, `/taxes/N/…` и шапка → `receipt_metadata`); `position = null`. Для `code=invalid_value` подпись — «Замечание распознавания»: старый сервер прячет под этим кодом любые причины. Особые заголовки НДС/итогов/реквизитов старому ответу недоступны — причины в нём нет.

**Группировка** (`groupIssues`): ключ `(severity, reason, entity, attribute)`; порядок блоков error → warning → info. Внутри блока порядок не зависит от порядка issues в ответе сервера (контракт его не задаёт): сначала три группы `optional_omitted` в фиксированном порядке — ставки строк (строка + `tax_rate`), налоговые итоги (налог), реквизиты (`receipt_metadata`), — затем остальные группы по первому вхождению.

| Группа | Заголовок (формы 1 / 2–4 / 5+, 11–14 — третья) | Пояснение |
| --- | --- | --- |
| `optional_omitted` + строка + `tax_rate`, у всех есть index | «НДС не использован в {n} строке / строках» | «Распознавание не подтвердило чтение ставки, поэтому ставка не сохранена. Остальные данные строк сохранены.» |
| `optional_omitted` + налог, у всех есть index | «Пропущен 1 налоговый итог» / «Пропущены 2 налоговых итога» / «Пропущено 5 налоговых итогов» | «Налоговый итог не сохранён: ставка не подтверждена или суммы не сходятся.» |
| `optional_omitted` + `receipt_metadata` | «Не прочитан 1 реквизит» / «Не прочитаны 2 реквизита» / «Не прочитано 5 реквизитов» | «Необязательные реквизиты чека не прочитаны уверенно и не сохранены. Значения не показываются.» |
| остальное | «{подпись причины}», затем « · {подпись области}», если она есть, и « ({n})» при n > 1 | нет |

Подпись области — `areaLabels[attribute]`, иначе по сущности: «Строки», «Налоги», «Скидки», «Границы чека»; `receipt_metadata` → «Реквизиты чека». Перечень под пояснением: «Строки: 1, 2, 3» по `position`; без `position` — «Строки распознавания №: 4, 7» (index + 1); «Налоговые итоги №: 1, 2»; для скидок — «Скидки: …» / «Скидки распознавания №: …». Номера без повторов, по возрастанию.

**Разметка.** Блок error — всегда видимый список под `h4` «Причины проверки» (для `failed` — «Причины ошибки»), с перечнем строк под причиной. Warning и info — под `h4` «Замечания распознавания»: каждая группа — нативный `<details><summary>`, свёрнутый по умолчанию; клавиатура штатная (Tab до summary, Enter/Space). Группа без пояснения и перечня (например, «Тип операции определён автоматически · Операция») выводится обычной строкой: раскрывать в ней нечего. Под причинами у `needs_review` стоит [форма исправления и подтверждения](#исправление-и-подтверждение-вырезки-needs_review); причины над ней после отказа сервера заменяются причинами отказа. Summary не ниже 44 px, с видимым focus-visible; длинные тексты переносятся.

**Автопроверки** (Vitest, Node/SSR, без браузера): guard — `api/recognition-schema.test.ts`; разбор `field`, плюралы 1/2/5/11/21/25, группы 25 + 2 + 2 из ответа в порядке настоящего сервера (2 реквизита, 25 ставок, 2 итога), порядок групп при перемешанном ответе и с посторонней группой между известными, fallback, `position` вместо index + 1 — `lib/recognition-issues.test.ts`; разметка обоих экранов, отделение error, отсутствие `message` — `recognition-markup.test.tsx`, `receipts-markup.test.tsx`. Они не подтверждают вид, фокус и поведение `<details>` в браузере.

#### Ручная приёмка замечаний человеком

Запуск QA API, Vite и fake-worker — по разделу [«Запуск изолированной QA»](#запуск-изолированной-qa-для-ручной-приёмки) и [development.md](development.md#распознавание-запуск-для-клиента); свой worker перезапускать с нужным `--fake-scenario`, для нового сценария брать ещё не загруженный файл.

1. Worker `recognition_worker --fake-scenario tax_evidence_missing`, загрузить `single.png`. В задании: вырезка «Чек сохранён», задание «Завершено», заголовок «Замечания распознавания» и три свёрнутые группы в этом порядке: «НДС не использован в 25 строках», «Пропущены 2 налоговых итога», «Не прочитаны 2 реквизита». Строк «Некорректное значение» и заголовка «Причины проверки» нет.
2. Раскрыть группы. В первой — пояснение о ставке и «Строки: 1, 2, …, 25»; во второй — пояснение и «Налоговые итоги №: 1, 2»; в третьей — только пояснение «…Значения не показываются.», без номера чека, подписи и других значений.
3. Клавиатура: Tab доходит до каждого summary по порядку, фокус виден (рамка фокуса: золотая в тёмной теме, синяя в светлой); Enter и Space раскрывают и сворачивают группу; фокус остаётся на summary; страница не прыгает и ничего не перезагружается. Раскрытие одной группы не меняет остальные.
4. Открыть чек по ссылке «Открыть чек №…»: в блоке фото те же три группы с теми же текстами и тем же поведением.
5. Остановить свой worker, запустить `--fake-scenario tax_evidence_present`, загрузить `double.png`: одна группа «Не прочитаны 2 реквизита» в задании и в чеке.

### Форма и тело запроса

Форма создаётся один раз из `normalized_result` и дальше принадлежит человеку: повторные чтения той же вырезки введённое не перезаписывают. Правки живут только в памяти открытой страницы — об этом сказано рядом с формой; перезагрузка возвращает распознанные данные. При `normalized_result: null` форма пустая, с одной строкой.

- **Числа.** Деньги, количества и ставки редактируются текстом и никогда не становятся JS-числом. В полях — серверная строка с запятой (`1,2900`); `decimalText` принимает запятую или точку и пробелы между цифрами, дополняет нулями до 2 / 3 / 4 знаков и отбрасывает лишние нули. Нетронутое значение уходит символ в символ таким, каким пришло. То, что к формату не приводится (`шесть`, `1,2345` для суммы), уходит как введено — сервер называет поле в `fields`.
- **Пустые поля.** Пустое поле — `null` («на чеке отсутствует»); непрочитанные распознаванием поля пусты и помечены «Не прочитано», пока не заполнены. Необязательный `utc_offset` при пустом поле в тело не входит. Напечатанная дата, не являющаяся календарной, в поле даты не подставляется.
- **Строки и ссылки.** Строки, скидки и налоговые итоги добавляются и удаляются. Внутри формы строки ссылаются друг на друга по устойчивым ключам; `position` тела — порядковый номер на момент отправки, `parent_position` и `line_position` вычисляются из него. Удаление строки снимает связь залога и делает скидку строки скидкой на весь чек, о чём сообщает строка состояния формы; залог может ссылаться только на товарную строку. `source_position` — позиция распознанной строки (только если она напечатана ровно у одной строки), у добавленной вручную — `null`.
- **Магазин.** Либо вывеска, адрес и страна, либо существующий магазин: поиск `GET /api/stores/?q=` (от двух символов, первая страница — до 50 магазинов) и выбор → `store_id`. Страна — выбор из `GET /api/countries/?all=1`; пока справочник не прочитан или при его отказе — поле кода и кнопка повторной загрузки. Валюта — текстовый код с подсказками: API отдаёт только валюты уже сохранённых чеков, а не весь справочник валют.
- **Перед отправкой** клиент проверяет только пустые обязательные поля (дата, время, итог, тип и название строки, название и сумма скидки, вид налога итога, хотя бы одна строка): запрос не отправляется, поля отмечены. Все остальные правила — серверные.

### Привязка причин к полям

Идентификатор поля повторяет путь контракта с ключом строки вместо индекса: `receipt.total`, `lines.7.unit_price`, `taxes.9.tax_rate.rate`. Индексы ответа сервера переводятся в ключи по снимку отправленных массивов, поэтому отметки остаются на своих строках и после добавления или удаления других; для причин самого распознавания тот же перевод идёт по массивам `normalized_result`.

- **Причины** (`issues` вырезки, после `review_invalid` — причины отказа): отмечаются только `severity: error`; текст — подпись причины из словаря клиента. `context.entity/index/attribute` → поле строки, вся строка или весь список; у шапки — поле по `attribute`, а для причин, которые лечатся в другом месте, — по причине: `store_ambiguous` / `store_conflict` / `merchant_conflict` → поиск магазина, `country_unknown` → страна, `currency_unknown` → валюта, `timestamp_ambiguous` / `timestamp_conflict` / `time_ambiguous` → смещение от UTC. Причина без поля (`identity_conflict`, закрытые реквизиты) остаётся только в списке над формой.
- **Пути** `fields` ответа `400 invalid_parameter`: `receipt.store_id` → поиск магазина; путь без своего поля (`lines.1.source_position`) → строка целиком. Текст — фиксированный клиентский; фразы сервера не выводятся.
- Отметка поля снимается, когда человек меняет это поле. Поле связано с текстом ошибки, пометкой «Не прочитано» и подсказкой через `aria-describedby`, отмечено `aria-invalid`.

### Действие и состояния

Одно действие на весь экран задания: пока идёт подтверждение, недоступны остальные кнопки подтверждения, «Отменить» и «Повторить обработку», и наоборот. Чтение задания и вырезок приостановлено на время POST; POST никогда не повторяется автоматически. Пауза может отменить чтение, которое уже шло, — список вырезок после предыдущего успеха. Такое чтение считается долгом: возобновление выполняет его и после отказа, который сам перечитывания не требует (`review_invalid`, `invalid_parameter`, `invalid_request`, `csrf_failed`, `permission_denied`); данные задания из ответа подтверждения долг снимают. Сохранённая вырезка показывается по ответу своего подтверждения, пока её не принесёт чтение списка, — в том числе пока подтверждается следующая вырезка; поэтому она не возвращается к виду «Требует проверки» с новой формой. Форма другой вырезки при перечитывании списка не пересоздаётся, введённое в ней сохраняется.

| Состояние | Что видит человек |
| --- | --- |
| Задание не завершено | поля редактируются, кнопка недоступна, под ней причина |
| Ожидание POST | поля и кнопки строк отключены; нажатая кнопка — «Сохраняем чек…», выглядит недоступной и помечена `aria-disabled` (не `disabled`, чтобы не потерять фокус), повторное нажатие ничего не делает |
| `200`: `imported` | карточка сразу показана по ответу: статус, «Открыть чек №N», «Подтверждено вручную: дата UTC», замечания подтверждения; задание заменено заданием из ответа (счётчики, статус, действия), вырезки перечитаны один раз |
| `200`: `reused` / `updated` | то же и явный текст: чек уже был сохранён, его заполненные значения не изменены, исправления к ним не применены; расхождения (`receipt_conflict`, `receipt_line_conflict`, `receipt_structure_conflict`) — в замечаниях. Текст виден и после перезагрузки (по `confirmed_at` и статусу) |
| `409 review_invalid` | человек остаётся в форме с введённым; сообщение у кнопки, причины над формой заменены причинами отказа, поля отмечены |
| `400 invalid_parameter` | то же, отмечены поля из `fields`; причины прежние |
| `400 invalid_request` | сообщение у кнопки; форма сохранена |
| `409 review_resolved`, `review_unavailable`, `404 not_found` | сообщение у кнопки, задание и вырезки перечитаны; если вырезка больше не требует проверки, вместо формы — её сохранённое состояние, а сообщение и фокус переходят в начало карточки |
| `409 review_busy`, `job_active` | сообщение у кнопки, состояние перечитано; повтор — только новым нажатием |
| `403 csrf_failed` | у кнопки: токен обновлён, действие не повторялось — подтвердить снова; `permission_denied` — сообщение о выключенном локальном API |
| сеть, таймаут, 5xx, неожиданный ответ | у кнопки: «Действие могло выполниться: проверьте задание перед повтором»; задание и вырезки перечитаны |

**Где виден результат.** Правило одно для всех отказов: пока форма показана, текст отказа выводится плашкой ошибки `role="status"` (`.ck-review-refusal`: текст, подложка и рамка из тройки `--ck-error-*`) прямо над кнопкой «Подтвердить и сохранить чек», а фокус остаётся на этой кнопке — результат виден без прокрутки, даже когда форма длиннее экрана. Сообщение карточки над формой (`.ck-rec-result`) при этом пусто, чтобы отказ объявлялся один раз. Если формы больше нет — успех либо перечитанная после отказа вырезка уже не требует проверки, — тот же текст показывает сообщение в начале карточки, и фокус переходит на него. Серверный `message` не выводится. Локальные действия со строками объявляет строка состояния формы (`role="status"`, `.ck-review-notice`, над кнопкой подтверждения); она живая область и фокус для объявления не получает. После добавления записи фокус в её первом поле; при пустых обязательных полях — в первом из них, а если пуст сам список строк при заполненной шапке — на кнопке «Добавить строку». Текст «Запрос не отправлен: заполните обязательные поля (N).» стоит, только пока он верен: он стирается при первой правке любого поля и в момент настоящей отправки (до «Сохраняем чек…»), поэтому его нет ни во время запроса, ни рядом с текстом отказа; идентификатор объявления при стирании не меняется, и фокус остаётся в редактируемом поле либо на кнопке. Нажатие, остановленное локальной проверкой, заменяет и текст отказа предыдущего запроса: над кнопкой остаётся одно сообщение. Объявления добавления и удаления записей правка и отправка не стирают. После удаления строки, скидки или налогового итога фокус остаётся в месте правки: в первом поле записи, занявшей место удалённой; если удалена последняя — в первом поле предыдущей; если список опустел — на кнопке «Добавить …» этого списка. Первое поле — «Название» у строки и скидки, «Вид налога» у налогового итога. Кнопка удаления следующей записи целью не выбрана намеренно: удержанный Enter удалял бы записи одну за другой, а отмены удаления нет. Текст об удалении (перенумерация, снятая связь залога, скидки на весь чек) по-прежнему объявляет строка состояния.

**Кнопки, которые исчезают от своего нажатия.** Такая кнопка называет устойчивое поле атрибутом `data-review-focus`, и форма переводит на него фокус сразу при нажатии: «Повторить поиск» (ошибка поиска магазина) — поле «Найти существующий магазин», «Загрузить справочник» — поле «Страна». Когда справочник прочитан, поле «Страна» из текстового становится выбором — это другой элемент с тем же идентификатором; фокус возвращается на него, если поле «Страна» было последним в фокусе и человек не перевёл фокус сам. «Выбрать: …» и «Не использовать выбранный магазин» по-прежнему передают фокус строке о выбранном магазине.

**Фокус подтверждения.** Нажатая кнопка на время запроса не получает `disabled` и остаётся в фокусе; карточка вырезки помечена `data-request-focus-own`, поэтому блок «Вырезки чеков» не переносит фокус на свой заголовок ни во время запроса, ни когда форма исчезает ([механизм](#фокус-при-локальных-обновлениях-r2)). После ответа `reviewFocusTarget` выбирает нажатую кнопку, а если её нет — сообщение карточки. Фокус, который человек успел перевести сам, не перехватывается. Кнопки, поля и выборы не ниже 44 px. Формы `<form>` нет намеренно: Enter в поле не должен сохранить чек.

**Подписи.** Внутри одной записи подписи полей не повторяются: у строки и налогового итога — «Вид налога», «Ставка НДС, %», «Код налога»; суммы налогового итога — «Сумма без налога», «Сумма налога», «Сумма с налогом». «Местное время» открывает текстовую клавиатуру (на цифровой может не быть двоеточия).

На экране чека у вырезки с `confirmed_at` выводится «Подтверждено вручную: дата UTC».

## Слияние дублей товаров (Ф1–Ф2)

Экраны работают на настоящем локальном API `/api/product-merges/` ([контракт](api-contract.md#реализовано-локальный-api-слияния-дублей-товаров-с2)), без вымышленных данных. Слой запросов — `src/api/product-merges*.ts` ([описание Ф1](../frontend/src/api/PRODUCT_MERGES.md)); экраны, состояние и пометки — `src/features/merges/`. Сценарий ручной приёмки, запуск QA и ограничения — [ACCEPTANCE.md](../frontend/src/features/merges/ACCEPTANCE.md).

### Маршруты и оболочка

`/catalog/merges?status=&page=` и `/catalog/merges/{id}` разбирает и собирает `navigation/routes.ts`: `MergesQuery = { status?: 'confirmed' | 'cancelled' | 'all'; page }`, `parseMergesQuery`, `buildMergesQuery`, маршруты `{ kind: 'merges'; query }` и `{ kind: 'merge'; groupId }`. Отсутствие `status` — список по умолчанию (ожидающие); `status=pending` приводится к тому же адресу без параметра. Неверные `status` / `page` дают общий экран «Некорректная ссылка» без запроса. Заголовки — «Дубли товаров» и «Группа дублей». На всех экранах раздела каталога (каталог, категория, товар, дубли) App показывает дополнительную навигацию «Раздел каталога»: «Товары» / «Дубли» / «Категории» (третья вкладка — [категории товаров](#категории-товаров-предположение-с-подтверждением-ф1ф2)). Переход из списка в группу хранит адрес списка с фильтром в History state: «К списку групп» и Back возвращают тот же фильтр и страницу; при прямом входе ссылка ведёт на список по умолчанию. Props — `MergesPageProps`, `MergePageProps` в `pages/types.ts`.

### Экраны

| Экран / блок | Данные и поведение |
| --- | --- |
| `MergesPage` | `GET product-merges/?status=&page=`: карточки групп (оставляемая запись, состояние, число записей и покупок, названия, признак «Есть конфликт данных»), фильтр состояния в URL, страницы. «Найти дубли» — `POST detect/`, результат («Создано групп: N, дополнено групп: M» либо «Новых дублей не найдено») и ссылки на найденные группы; после ответа список перечитывается |
| `MergePage`: «Группа №N» | `GET product-merges/{id}/`: состояние словами, счётчики, даты (UTC), итог после действия |
| `MergeGroupView`: «Записи группы» | Таблица записей: название, написания в чеках, число покупок, даты, факты. Радио «Оставить» (по умолчанию `target_product_id` группы); select «Название оставляемого товара» (по умолчанию «Не менять»); по каждому полю из `conflicts` — обязательная группа радио со значениями записей из `product_ids`; «Подтвердить слияние», «Отменить слияние», «Исключить из группы» у каждой активной записи |
| `MergeLines`: «Покупки группы» | `GET product-merges/{id}/lines/`, локальные страницы: напечатанное название, исходная запись (`origin_product_id`; `null` — «Добавлена после слияния»), дата, магазин, количество, цена, сумма, ссылка на чек либо «Чужая покупка» у строки с `receipt_id: null` ([моя / чужая покупка](#моя--чужая-покупка)) |

Тело `confirm` собирает `confirmInput` (`state.ts`): `version` последней прочитанной группы, `target_product_id`, `name_product_id` только при явном выборе названия, `resolutions` только по спорным полям этой группы. `exclude` также передаёт `version`. Пока хотя бы одно спорное поле без значения, «Подтвердить слияние» недоступна, а подпись под кнопкой называет недостающие поля. Выбор человека относится к одной прочитанной версии группы: новая `version`, смена состояния или `merge_changed` возвращают выбор к значениям по умолчанию.

Ссылка на карточку есть только у записи, которая сейчас является товаром каталога: у оставляемой записи ожидающей группы, у исключённой записи, у всех записей отменённой группы и у существующей записи подтверждённой.

### Состояния

| Состояние | Что видит человек |
| --- | --- |
| Загрузка | Локальный loading и `aria-busy` в своём блоке; группа и покупки грузятся независимо |
| Пусто | «Групп, требующих подтверждения, нет.» и «Найти дубли»; для других фильтров — «Групп с таким состоянием нет.» и ссылка на ожидающие; у отменённой группы покупок нет — объяснение вместо таблицы |
| Ошибка чтения | Локальный текст по причине и «Повторить»; отсутствующая группа или страница — выход в список / на первую страницу. Неудачное обновление сохраняет последние данные с предупреждением |
| `permission_denied` | «Локальный API выключен…» и «Повторить»; «Найти дубли» недоступна |
| `merge_conflict` | Сообщение, спорные поля из `fields` подсвечены (`aria-invalid`, текст ошибки связан через `aria-describedby`); `name` подсвечивает выбор названия; группа перечитана |
| `merge_changed` | «Состав группы изменился…», группа и покупки перечитаны, выбор сброшен |
| `merge_resolved` | Группа перечитана, показано итоговое состояние, выбор и кнопки скрыты |
| `merge_busy` | «Каталог сейчас изменяется…» и кнопка «Повторить», которая заново выполняет то же действие только по нажатию |
| Сеть / таймаут / 5xx при действии | «Действие могло выполниться: проверьте состояние группы перед повтором»; группа перечитана |
| Выполняется действие | Все кнопки, радио и select экрана отключены, нажатая кнопка подписана («Подтверждаем…», «Отменяем…», «Исключаем…», «Ищем дубли…») |

Изменяющий запрос никогда не повторяется автоматически; `csrf_failed` обновляет токен и просит выполнить действие снова. Одновременно выполняется одно действие. Чтение группы и списка приостанавливается на время POST, поздний ответ более раннего чтения не заменяет ответ действия; смена маршрута и unmount отменяют чтения и ожидание действия (серверное действие при этом могло выполниться). Серверные сообщения на экран не выводятся: тексты — локальные переводы кодов.

### Пометки в каталоге и карточке

- Список товаров (`ProductsSection` → `ProductList`, проп `merges`): отдельный запрос `GET product-merges/?status=pending&page_size=200`; у оставляемого товара ожидающей группы — значок-ссылка «Дубли: требует подтверждения» на группу. Больше 200 ожидающих групп одной страницей не охватываются.
- Карточка (`ProductPage`): отдельный запрос `GET product-merges/?product={id}`. Оставляемый товар ожидающей группы получает блок «Предварительно объединено N написаний — требует подтверждения» (N — активные записи группы) со ссылкой на группу.
- Карточка при `not_found`: если id — поглощённая запись, вместо «Товар не найден» показано «Товар объединён с „…“» и ссылка на группу (пока она ожидает) либо на оставляемый товар (после подтверждения). Пока ответ не получен, и при любом отказе — прежнее «Товар не найден».
- Запросы пометок независимы от каталога и карточки: загрузка, `permission_denied`, сеть и любая другая ошибка означают «без пометок», без сообщений и повторов.

### Доступность и фокус

Таблицы имеют `caption`, `th scope`, собственную фокусируемую область горизонтальной прокрутки (`role="region"` с подписью); страница по горизонтали не прокручивается. Радио и select — нативные, с подписями; у радио «Оставить» и кнопок «Исключить из группы» в доступном имени есть номер и название записи. Результат действия объявляет `role="status"`. После действия фокус возвращается на нажатую кнопку, а если она исчезла или недоступна — на сообщение о результате; фокус, который человек успел перевести сам, не перехватывается. Блоки чтения используют общий `useLocalRequestFocus`. Фактический фокус, клавиатуру, screen reader и узкий экран принимает человек.

## Категории товаров: предположение с подтверждением (Ф1–Ф2)

Экран и пометки работают на настоящем локальном API `/api/product-classifications/` ([контракт](api-contract.md#реализовано-локальный-api-предположений-категорий-товаров)), без вымышленных данных. Товар, созданный при распознавании чека, сервер сразу приписывает к предложенному обобщённому продукту; человек подтверждает предложение, выбирает другой обобщённый продукт либо отклоняет. Слой запросов — `src/api/product-classifications*.ts`; экран, состояние, действия и пометки — `src/features/classification/`. Сценарий ручной приёмки, запуск QA, превью и ограничения — [ACCEPTANCE.md](../frontend/src/features/classification/ACCEPTANCE.md).

### Маршрут и оболочка

`/catalog/classification?status=&product=&page=` разбирает и собирает `navigation/routes.ts`: `ClassificationQuery = { status?: 'confirmed' | 'rejected' | 'superseded' | 'all'; product?: number; page }`, `parseClassificationQuery`, `buildClassificationQuery`, маршрут `{ kind: 'classification'; query }`. Отсутствие `status` — ожидающие записи; `status=pending` приводится к тому же адресу без параметра. `product` — id товара: экран показывает записи одного товара; отдельной страницы записи нет. Неверные `status` / `product` / `page` дают общий экран «Некорректная ссылка» без запроса. Заголовок и `document.title` — «Категории товаров». Навигация «Раздел каталога» на всех экранах каталога — «Товары» / «Дубли» / «Категории». Переход с записи на карточку товара хранит адрес экрана в History state: «Назад к списку» и Back возвращают тот же фильтр, товар и страницу. Props — `ClassificationPageProps` в `pages/types.ts`.

### Экран

Блок состояния и список читаются отдельными запросами, каждый со своим состоянием загрузки; область выбора другого продукта — третьим.

| Блок | Данные и поведение |
| --- | --- |
| `StatePanel`: «Предположение категорий» | `GET product-classifications/status/`: «Ожидают подтверждения: N. Без категории: M.», строка запуска и воркера, при `auto_suggest` — «Автозапуск после импорта чека включён.». Кнопка «Предложить категории» — `POST runs/` с `{}`; недоступна без товаров без категории («Товаров без категории нет.»), при активном запуске, во время другого действия и при выключенном локальном API. Пока запуск `queued` или `running`, состояние опрашивается раз в 2 секунды при видимой странице. Список за состоянием следит сам (см. «Состояние и список» ниже): записи очередного пакета появляются, пока запуск ещё активен |
| Фильтр «Состояние записей» | Ссылки «Ожидают» / «Подтверждённые» / «Отклонённые» / «Заменённые» / «Все», значение в URL; `product` сохраняется |
| `GroupList`: ожидающие | `GET product-classifications/?status=pending&product=&page=&page_size=200&ordering=generic`. Записи страницы группируются по `suggested.generic.id` **в порядке сервера** (он сортирует по кодовым точкам, не по алфавиту; клиент группы не пересортировывает). Группа: название обобщённого продукта с пометкой «новый» при `is_new`, путь категории через « → » с пометкой «новая» у созданных элементов, «Базовая единица: кг / л / шт», число товаров; «Показано N из M…», если на странице меньше записей, чем `pending_count`; «Подтвердить все (N)» по записям с `can_confirm`. Запись: название (ссылка на карточку, если товар существует и не поглощён ожидающей группой дублей), написания в чеках, бренд и фасовка, «Входит в группу дублей №N»; кнопки «Подтвердить», «Выбрать другой», «Отклонить» |
| `FlatList`: остальные фильтры | Тот же запрос с `ordering=-id`, для «Все» — без `status`: состояние словами (по `status` и `resolution`), предложенное, итог, время решения; действий нет, у ещё ожидающей записи — ссылка «Открыть среди ожидающих» |
| `GenericChooser`: «Выбрать другой» | Область под записью с собственным запросом `GET generic-products/?q=&page_size=50`: поиск от 2 символов, радио с названием, путём категории и единицей; без «Не разобрано» и без уже предложенного |

Действия: «Подтвердить» — `POST {id}/confirm/` с `version` записи и `generic_id = suggested.generic.id`; «Применить выбор» — тот же запрос с выбранным `generic_id`; «Отклонить» → строка «Отклонить предложение? Товар вернётся в „Не разобрано“.» → `POST {id}/reject/` с `version`; «Подтвердить все (N)» → строка «Подтвердить N товаров как „…“?» → `POST confirm/` с парами `{id, version}`, больше 100 записей — последовательными запросами по 100 с остановкой на первом отказе и итогом «Подтверждено X из N». `window.confirm` и модальные окна не используются; на экране открыта не больше одной области. Тела собирают `actions.ts` и `state.ts` только из документированных ключей.

Времена в ответах принимаются с долями секунды и без них; `suggested.category`, `source.run_id` и `source.trigger` могут быть `null` (категория — «Категория не указана»).

| Состояние | Что видит человек |
| --- | --- |
| Загрузка | Локальный loading и `aria-busy` в своём блоке; состояние и список грузятся независимо |

| Сеть / таймаут / 5xx при действии | «Ответ сервера не получен. Действие могло выполниться: проверьте состояние записи перед повтором.»; запись перечитана |
| Запись ожидает, но действий нет | Вместо кнопок — «Обобщённый продукт товара изменён вне этого экрана. Запись закроется как „заменено“ при следующем действии или запуске.» либо «Товар удалён.» |
| Запуск в очереди | По `executor.state`: `absent` — предупреждение «…Воркер распознавания не запущен: запуск начнётся, когда воркер запустят.»; `busy` — «…Воркер занят другим заданием.»; `idle` — «…начнётся в ближайшие секунды.»; неизвестное значение — только «Запуск в очереди.» |

Текст о прогрессе, а не «начнётся»: `idle` и неизвестное значение — «Модель предлагает категории: обработано X из Y.»; `busy` — то же и «Воркер занят другим заданием.»; `absent` — предупреждение «Запуск приостановлен: обработано X из Y. Воркер распознавания не запущен: запуск продолжится, когда воркер запустят.» |
| Пакет применён, запуск ещё активен (между пакетами, «Запуск приостановлен», следующий пакет выполняется) | Сервер применяет предложения после каждого пакета, и список перечитывается сразу, как только очередное чтение состояния показало новый результат: записи пакета появляются без перезагрузки, их можно подтвердить, не дожидаясь конца запуска; «Ожидают подтверждения: N» и «Всего: N записей» совпадают. Если опрос не идёт (воркер остановлен до открытия страницы — опрос идёт; вкладка открыта до запуска и запуск начат не в ней — не идёт), список обновится при следующем чтении состояния |
| Список перечитан, пока открыта область | Область «Выбрать другой», «Отклонить предложение?» или «Подтвердить N товаров…» остаётся открытой, введённый поиск, выбранный вариант и фокус сохраняются, если запись (для группы — набор подтверждаемых записей) та же, что при открытии. Если запись исчезла из списка или по ней больше нельзя действовать, область закрывается с текстом «Предложение уже решено либо записи больше нет в этом списке. Показано актуальное состояние.»; если у записи изменилась `version` — «Предложение изменилось. Данные обновлены: проверьте запись и повторите действие.»; для группы — «Состав группы изменился. Данные обновлены: проверьте группу и повторите действие.» либо «В группе больше нет записей для подтверждения. #### Запуск и воркер: все сочетания

Строку запуска строит `runText` (`labels.ts`): для каждого статуса запуска решено каждое состояние воркера. Тест `features/classification/run-worker-table.test.tsx` проверяет таблицу целиком (28 сочетаний) — текст, тон, разметку, кнопку и опрос — на телах, прошедших настоящий адаптер; статус запуска или состояние воркера, добавленные в типы без строки в таблице теста, не компилируются.

| `cancelled` | «Запуск отменён.» | то же | то же | то же | доступна | нет |

«Доступна» — при `unclassified_count > 0`, без другого действия и при включённом локальном API; иначе кнопка недоступна при любом сочетании, а при `unclassified_count = 0` рядом написано «Товаров без категории нет.». Чего тексты не обещают: `running` + `busy` — это и работающий пакет, и воркер, убитый посреди пакета, пока жива lease (срок запроса + 60 с): сервер их не различает, клиент пишет только «Модель предлагает…», а после истечения lease строка сама сменяется предупреждением. `running` + `idle` — короткий промежуток между истечением lease и следующим проходом живого воркера, который сам вернёт запуск в очередь. «Продолжится, когда воркер запустят» верно для первых двух восстановлений; на третьей потерянной lease сервер закрывает запуск как `failed` / `worker_lost` — тогда строка сменится на «Запуск завершился ошибкой: обработчик перестал отвечать…», и кнопка снова доступна. `queued` + `busy` — обычно воркер занят распознаванием фото, но на один опрос (до 2 с) так выглядит и собственный запуск между пакетами: сервер читает запуск и воркер двумя запросами, и воркер успевает взять следующий пакет между ними (наблюдалось в QA с постоянным воркером без заданий распознавания: «…обработано 2 из 3. Воркер занят другим заданием.», следующий опрос — `running` / `busy`); текст задан контрактом К1 и не менялся. Завершённый запуск о воркере не говорит: если воркера нет, об этом скажет предупреждение очереди сразу после нажатия кнопки.

**Состояние и список.** Это два независимых чтения, и они не должны противоречить друг другу. Решение «нужно перечитать» — чистая функция `syncReads` (`features/classification/list-sync.ts`), её вызывает `createReadSync` при каждом опубликованном состоянии любого из двух запросов (не при отрисовке). Правила: (1) два подряд прочитанных состояния различаются в том, что показывают списки, — `listOutdated`: изменился `pending_count`, у того же запуска изменился `progress.processed` или `progress.applied`, появился другой запуск с `processed > 0`, активный запуск перестал быть активным — список перечитывается один раз, при любом фильтре и при фильтре по товару (пакет создаёт ожидающие и закрывает устаревшие записи, решение в другой вкладке меняет подтверждённые и отклонённые); переход `queued → running` без изменения прогресса и повтор того же состояния ничего не читают; (2) числа двух чтений не могут быть верны одновременно — `countsAgree`: у «Ожидают» без товара `count` списка равен `pending_count`, у «Ожидают» одного товара — не больше, у «Все» без товара — не меньше, остальные фильтры числом не связаны — перечитывается сторона, прочитанная раньше, затем один раз другая; больше по тому же расхождению запросов нет (не более одного дополнительного чтения каждой стороны, без цикла). Сравнение чисел ждёт окончания идущего чтения; первое открытие страницы — начало отсчёта, а не изменение. Во время POST чтения стоят на паузе и просьба перечитать ничего не делает; после действия оба запроса и так перечитываются, и их ответы считаются новым началом — собственное решение человека не вызывает второго чтения списка. Если список не прочитан (ошибка первого чтения), автоматически он не перечитывается: у блока своя кнопка «Повторить».

Изменяющий запрос никогда не повторяется автоматически. Одновременно выполняется одно действие; чтения приостанавливаются на время POST, поздний ответ более раннего чтения не заменяет ответ действия; после успеха записи заменяются ответом сервера, затем состояние и список перечитываются. **Чтения на паузе и уход посреди действия.** Паузу ставит только действие (`ActionLifecycle.pause` в `actions.ts`), и за каждой паузой следует ровно одно из трёх: `success`, `failure` либо `release`. Запрос состояния живёт всю страницу, а запрос списка, связь двух чтений и действия создаются заново при смене фильтра, товара и страницы (в том числе по Back / Forward в пределах экрана), поэтому действие может закончиться, когда его списка уже нет (`page-lifecycle.ts`). Уничтожение действий с незавершённым запросом (`dispose`) сразу снимает паузу (`release`): состояние перечитывается, опрос активного запуска и «Повторить» блока работают. Сам POST при этом не обрывается — обрыв не отменил бы его на сервере, только скрыл бы момент сохранения: когда он ответил (успехом, отказом или без ответа), `settled` ещё раз перечитывает состояние и тот список, который показан сейчас; ответ на экран не выводится и в новый список не подставляется. «Подтвердить все» из нескольких запросов дожидается текущего и следующие не отправляет. Если уход пришёлся на проверку записи после потерянного ответа либо на обновление токена, это чтение отменяется, пауза снимается, второго перечитывания нет. Новое действие в новом списке ставит собственную паузу: ответ прежнего POST под ней ничего не читает. Уход с экрана уничтожает оба запроса: ответ оставленного POST ничего не читает, а возврат на экран начинается с собственных чтений. Чтение прежнего списка, не успевшее ответить до смены фильтра, отбрасывается и новый список не заменяет; опрос состояния сменой списка не прерывается. Область «Выбрать другой» приостанавливает собственный запрос вариантов на время действия парой «эффект — очистка эффекта» и возобновляет его при любом исходе, включая закрытие области. Серверные сообщения, включая `run.error.message`, на экран не выводятся: тексты — локальные переводы кодов (`labels.ts`).

### Схема ответов предположений

`api/product-classifications-schema.ts` проверяет типы и только те связи полей, которые сервер гарантирует ([таблица сочетаний полей Запуска](api-contract.md#допустимые-сочетания-полей-запуска)); ответ вне их — `invalid_response`.

- **Запуск** (`GET status/` → `run`, `GET runs/`, `GET runs/{id}/`, `POST runs/` → `run`): `error` — объект тогда и только тогда, когда `status: "failed"`; `finished_at` заполнен тогда и только тогда, когда статус `succeeded` / `failed` / `cancelled`; `started_at: null` допустим только у `queued` и `cancelled` и только при `progress.processed = 0`. Заполненный `started_at` у `queued` и `cancelled` — норма: запуск возвращается в очередь после каждого пакета, после `Ctrl+C` воркера и после восстановления lease. Не проверяются: сумма `applied + unknown + skipped` против `processed`, `processed ≤ requested`, порядок `created_at` и `started_at`, зависимость `remaining` от статуса.
- **Состояние** и ответ `POST runs/`: типы, `run` — Запуск либо `null`; у `POST runs/` при `created: true` запуск обязателен.
- **Запись**: ожидающая — без `resolution`, `resolved_at` и `final_generic`; решённая — с `resolved_at`, с `resolution` из набора своего статуса и без доступных действий; у существующего товара есть `generic`, у удалённого — `generic: null`, пустые `aliases` и `merge_group_id: null`; категория — последний элемент своего пути.
- **Массовое подтверждение**: `confirmed` равно числу записей, все `confirmed`, по возрастанию `id`.

Тест `api/product-classifications-schema.test.ts` читает каталог эталонов сервера с диска (сейчас 40 файлов) и падает, если файл появился без проверки.

### Пометки категорий в каталоге и карточке

Источник — `features/classification/marks.ts` (`pendingMarks`, `markFor`, `marksOf` и два хука) и `ClassificationMarks.tsx` (`ClassificationBadge`, `ProductClassificationNotice`).

- Список товаров (`ProductsSection` → `ProductList`, проп `classifications`): отдельный запрос `GET product-classifications/?status=pending&page_size=200`. У товара с ожидающей записью — значок-ссылка «Категория: требует подтверждения» на `/catalog/classification?product={id}`. Значок стоит после значка дублей, если у товара есть оба.
- Карточка (`ProductPage`): отдельный запрос `GET product-classifications/?product={id}&status=pending`. Под фактами товара — блок «Категория предложена автоматически: „Колбаса“ (Продукты питания → Мясные продукты) — требует подтверждения. Товар уже участвует в сравнении цен по этому обобщённому продукту.» и ссылка «Открыть в списке категорий» на тот же адрес. Пустое название — «Не указано», отсутствующая категория — «Категория не указана».
- Правило совпадения: пометка показывается, только если `generic.id` товара из ответа каталога (или карточки) равен `suggested.generic.id` записи. Запись, которую сервер ещё не закрыл сверкой после ручной смены обобщённого продукта, пометки не даёт.
- **Ограничение 200 записей.** Пометки списка читают одну страницу: больше 200 ожидающих записей ею не охватываются, и у части товаров значка не будет, пока записи не разобраны, — то же ограничение, что у пометок дублей. Блок карточки читает записи своего товара и этим не ограничен.
- Запросы пометок независимы от каталога и карточки: загрузка, `permission_denied` (выключенный локальный API), сеть, таймаут, 5xx, неверный формат и любая другая ошибка означают «без пометок» — без сообщений, без «Повторить» и без повторов. Опроса и кеша нет: запрос выполняется один раз при открытии списка или карточки, поэтому после решения на экране категорий пометка исчезает при следующем открытии. Каталог, категория, поиск и карточка при этом работают как раньше; пометки дублей и пометки категорий друг от друга не зависят.
- Поглощённый ожидающей группой дублей товар в каталоге не виден и карточки не имеет (`404`), поэтому пометки категории у него нет; его запись видна на экране категорий со ссылкой на группу. Экран сравнения альтернатив в SPA не подключён, пометок там нет.

### Доступность и фокус экрана категорий

Блоки чтения используют общий `useLocalRequestFocus`. Результат действия и строка запуска объявляются через `role="status"`; пустые live-области остаются в дереве доступности и не занимают места. После действия фокус возвращается на нажатую кнопку, а если она исчезла или недоступна — на сообщение о результате; фокус, который человек успел перевести сам, не перехватывается. Открытие области переводит фокус в неё (поле поиска либо группа подтверждения), «Отмена» возвращает его на открывшую кнопку. Перечитывание списка фокус не трогает и ничего не объявляет: блок списка не переходит в загрузку, строки результата остаются пустыми; если перечитывание закрыло область, в которой был фокус, он переходит на сообщение о причине, а фокус, стоящий в другом месте, не перехватывается. У кнопок записей и групп в доступном имени есть название товара или обобщённого продукта (скрытый текст). Варианты «Выбрать другой» — нативные радио в `fieldset` с `legend`. Значок каталога и ссылка блока карточки — обычные ссылки с областью нажатия от 44 px; блок карточки — текст и ссылка, без live-области: он не сообщает об ошибке и не перехватывает фокус. Фактический фокус, клавиатуру, screen reader, узкий экран и zoom 200% принимает человек.

## Статистика: траты, средний чек и график цен (Ф1–Ф7)

Три экрана работают на настоящем API статистики ([контракт](api-contract.md#реализовано-статистика-трат-походы-и-ряды-цен-серверная-часть)), без вымышленных данных и без новых зависимостей: диаграммы — собственный SVG. Сценарий ручной приёмки, демо-числа и ограничения — [frontend/src/features/stats/ACCEPTANCE.md](../frontend/src/features/stats/ACCEPTANCE.md); команды и фактические результаты — [verification.md](verification.md#статистика-клиент-ф7).

### Маршруты и оболочка

| URL | Экран | Параметры адреса |
| --- | --- | --- |
| `/stats` | «Траты за период» | `date_from`, `date_to`, `country`, `currency`, `store` (id через запятую, до 20), `group_by` (`generic`, `product`, `store`; без него — категории), `category`, `generic` |
| `/stats/receipts` | «Почему изменился средний чек» | `base_from`, `base_to`, `current_from`, `current_to`, `country`, `currency`, `store`, `interval` (`week`, `quarter`, `year`; без него — месяц) |
| `/catalog/products/:id` | блок «График цен» в карточке товара | к прежним добавлены `price` (`normalized`) и `interval` (`week`, `day`) |

Значения по умолчанию в адрес не пишутся; непонятное значение параметра статистики отбрасывается при разборе, а не даёт экран «Некорректная ссылка». Всё состояние экранов — период, фильтры, разбивка, место в drill-down, интервал — живёт в адресе: Back/Forward, перезагрузка и копирование ссылки восстанавливают экран. В шапке — «Статистика», под ней навигация раздела «Траты» / «Средний чек»; заголовки страниц — «Траты за период» и «Средний чек».

### Слой запросов

- `src/api/stats.ts` — `getSpending(params, options)`, `getReceiptSeries(params, options)`, `getReceiptCompare(params, options)` через `getLocalJson` (локальный API, `credentials: 'same-origin'`), `statsFailureKind(failure)` → `invalid_parameter | range_too_large | permission_denied | not_found | unavailable | invalid_response`; помощники `listParam`, `omitEmpty`. Типы — `stats-types.ts`, runtime-схемы — `stats-schema.ts` (`isSpending`, `isReceiptSeries`, `isReceiptCompare`).
- `src/api/price-series.ts` — `getProductPriceSeries(productId, params, options)`: открытый эндпоинт, как каталог, без cookie; типы и схема — `price-series-types.ts`, `price-series-schema.ts` (`isPriceSeries`).
- Деньги, количества, цены и проценты остаются строками; для осей — `decimalNumber`, `dateMs`. Небезопасные id и `limit` отклоняются локально до запроса. Серверные тексты ошибок на экран не попадают — только имена полей.
- Схемы проверяются на эталонах сервера `backend/api/tests/fixtures/stats/*.json` (`stats-test-support.ts` читает их напрямую, второй копии нет). `parent` в ответе трат принимается при любом `group_by` (Ф6а): сервер называет категорию фильтра и при группировке по обобщённым продуктам, товарам и магазинам — эталон `spending-category-generic.json`.

### Диаграммы

`src/lib/charts/` — `PieChart` и `LineChart` на чистой геометрии (`pie.ts`, `line.ts`, `scale.ts`, `selection.ts`), стили `Charts.css` на CSS-переменных `App.css`. Рисунок помечен `aria-hidden`; доступная форма — таблица под диаграммой (`caption`, заголовки столбцов), у линейного графика — раскрываемая «Таблица значений». Секторы круговой диаграммы — ссылки вне порядка Tab, те же ссылки стоят в таблице. Линейный график — одна остановка Tab: ← и → — соседний интервал, Home и End — первый и последний, Esc — снять выделение; флажки «Серии на графике» прячут и возвращают линии. Подсказка выделенного интервала стоит со стороны, где больше места, и привязана к краю графика с этой стороны (`left` в левой половине, `right` в правой — `lineTooltipAnchor`), отступ от линии — `margin`, а не `transform`: ширина по содержимому ограничена свободной частью графика, и подсказка не выходит за него. Выделение мышью снимается, когда указатель уходит с графика; после касания пальцем оно остаётся до касания в другом месте, Esc или потери фокуса. Серии различаются цветом, штрихом и формой маркера; «прочее» и неположительные суммы — отдельными тонами. При `prefers-reduced-motion` переходы отключены.

### Экран «Траты за период»

`features/stats/SpendingPage.tsx` (запрос и справочники), `spending-filters.tsx`, `spending-results.tsx`, чистые `spending-state.ts` и `spending-view.ts`, стили `Spending.css`.

- Быстрый выбор периода («Этот месяц», «Прошлый месяц», «Этот год», «Прошлый год», «Всё время») считается от даты браузера; форма — две даты, страна, валюта, магазины. «Применить фильтры» меняет адрес, «Сбросить фильтры» убирает фильтры и сохраняет место в drill-down.
- Разбивка «Категории / Обобщённые продукты / Товары / Магазины». Drill-down: категория → подкатегории и её собственные товары → обобщённый продукт → товары → карточка товара; путь («хлебные крошки») и «На уровень выше» строятся из `parent.path` ответа.
- **Одна валюта — один блок** со своим итогом, диаграммой и таблицей; суммы разных валют не складываются и не пересчитываются. Под блоком объяснена разница суммы чеков и суммы строк, а под фильтром категории или обобщённого продукта — почему сумма чеков не показывается.
- «Не разобрано», строки без товара, услуги и залог показываются как есть с подсказкой про админку; «прочее» — одной строкой после обычных элементов; сумма ≤ 0 в диаграмму не входит, доля не считается.
- Состояния: загрузка; прежний ответ остаётся приглушённым, пока грузится новый; пусто без фильтров — «Чеков пока нет» со ссылкой на загрузку фото; пусто с фильтрами — ссылка сброса; `403` — «Локальный режим выключен…» без повтора; `400` — пометка полей; `range_too_large`; сеть, таймаут 15 с, `5xx` — «Повторить». Справочники стран и магазинов грузятся независимо: их отказ оставляет фильтры рабочими.

### Экран «Почему изменился средний чек»

`ReceiptsStatsPage.tsx`, `receipts-filters.tsx`, `receipts-compare.tsx`, `receipts-trend.tsx`, чистые `receipts-state.ts`, `receipts-wording.ts`, `receipts-series.ts`, запрос `receipts-request.ts` (`useStatsRequest`), стили `ReceiptsStats.css`.

- Два периода — базовый («было») и текущий («стало»), готовые пары периодов, общие фильтры страны, валюты и магазинов. Пересечение периодов и перевёрнутые даты отклоняются до запроса с фокусом на первом ошибочном поле.
- Блок сравнения по каждой валюте: вывод словами, обе стороны (походы, средний и медианный чек, позиций на чек), слагаемые изменения — **количество, цены, состав** — таблицей и полосой, индекс Фишера с покрытием и допущением, таблица товаров, купленных в обоих периодах. Без совпавших товаров цены и состав не разделяются; при походах только в одном периоде разложения нет — оба случая объяснены текстом.
- Блок «Средний чек по времени» — независимый запрос: средний и медианный чек и «позиций на чек» по интервалам, охват — от начала базового до конца текущего периода. Интервал «Месяц / Квартал / Год» меняет только график: сравнение не перезагружается. Интервал без походов — разрыв линии, не ноль; возвраты исключены и названы.
- Отказ одного блока не убирает другой; `403`, `400`, `range_too_large` (с предложением интервала крупнее) и «Повторить» — как на экране трат.

### График цен в карточке товара

`features/product/PriceChart.tsx` и `price-chart-state.ts`; блок подключён в `ProductPage.tsx` рядом с прежними таблицей истории и сводкой, которые не менялись.

- Ряды этого товара — по магазинам, ряды похожих товаров (тот же обобщённый продукт) — по странам. Каждая пара «валюта, единица» — отдельная панель: цены разных валют на одной оси не стоят.
- Переключатели «Цена» (за единицу в чеке / за кг, л, шт) и «Интервал» (месяц / неделя / день) пишутся в адрес; «Показывать похожие товары» и выключенные в легенде серии живут на странице и сохраняются при перезагрузке ряда.
- Пояснения: `generic_unassigned` — товар в «Не разобрано», сравнивать не с чем; несравнимые фасовки при цене за единицу; пропущенные наблюдения без нормализованной цены; усечение числа рядов.
- **Из фильтров карточки график берёт только период.** Магазин, страна и валюта карточки на него не влияют.
- Блок независим: его отказ не трогает историю и сводку; эндпоинт открыт и работает при выключенном локальном режиме.

## Вход, сессия и разделение пользователей (К1)

Чеки, фото и статистика принадлежат пользователю, каталог и цены общие ([проект](multi-user.md)). Клиент работает в двух режимах сервера и узнаёт режим из ответа `GET /api/me/`: `accounts` — вход по имени и паролю, сессия Django общая с `/admin/`; `local_single` — входа нет, все запросы идут от служебного пользователя `local`, интерфейс прежний. Слой запросов и хранилище сессии описаны в [src/api/README.md](../frontend/src/api/README.md), экраны — `src/features/auth/`, ручная приёмка и запуск QA с двумя пользователями — [ACCEPTANCE.md](../frontend/src/features/auth/ACCEPTANCE.md). Регистрации, восстановления пароля и управления пользователями в клиенте нет.

### Сессия и «Я»

`src/session/store.ts` (без React; хук `useSession` — `src/session/index.ts`) хранит одно из состояний: `loading` — «Я» ещё не прочитано; `error` — прочитать не удалось, о сессии ничего не известно; `guest` (`expired: true`, если сеанс закончился посреди работы); `user` с `mode`, `user { id, username, is_staff }` и `permissions.moderate_catalog`. Ответ «Я» — `{ mode, user, permissions, csrf_token }`; его же возвращают вход и смена пароля. Токен и пароль не выводятся и не попадают в адрес, History state и хранилища браузера.

- `App` читает «Я» при открытии и при каждом возврате во вкладку (`visibilitychange`, `watchSession`): в другой вкладке могли выйти или войти другим человеком. Известная сессия перечитывается тихо — остаётся на экране во время запроса и переживает неудачный запрос.
- `401 not_authenticated` на `/api/me/` — это гость, не ошибка и не сигнал.
- В `local_single` «Я» отвечает `200` без входа: пользователь `local`, право модератора есть всегда.
- `canModerate(session)` — есть ли право `catalog.moderate_catalog`; `permissionDeniedText(session)` — текст для `403 permission_denied`: пользователю `accounts` «Нет права модератора каталога.», иначе прежний текст про `ALLOW_LOCAL_RECOGNITION_API=1`.

### Транспорт: 401, 403 и cookie

- Все GET и POST идут с `credentials: 'same-origin'` (cookie `sessionid` и `csrftoken`); health по-прежнему `omit` и от сессии не зависит.
- `401 not_authenticated` на любом запросе, кроме вызовов входа, — не ошибка экрана: адаптер возвращает `{ kind: 'aborted' }` (экраны это состояние уже умеют) и один раз сообщает оболочке сигнал `unauthenticated` (`src/api/auth-signal.ts`). `401` с другим телом — `invalid_response`.
- `403 permission_denied` возвращает экрану прежний результат и дополнительно шлёт сигнал `forbidden`: хранилище перечитывает «Я» (одно чтение на несколько отказов), так обнаруживается отозванное право.
- Множества причин `ApiErrorReason` / `LocalApiErrorReason` не расширялись: экраны каталога, чеков, распознавания и статистики не менялись.
- Вход, выход и смена пароля — POST с `X-CSRFToken`; токен до входа берётся из анонимного `GET /api/auth/csrf/`, после входа — из ответа «Я». Django меняет токен при входе, поэтому после входа, выхода, смены пароля и смены пользователя на той же cookie клиент забывает и токен локального API (`clearRecognitionCsrf`); следующий POST читает `recognition/csrf/` заново. Ни один POST, включая вход, автоматически не повторяется.
- Серверные `message` не выводятся: тексты отказов — локальные, по коду.

### Оболочка: что показано вместо страницы

Вход — состояние оболочки **на том же адресе**: гость видит его на любом адресе, кроме `/health`, после входа открывается страница этого адреса с тем же query, параметра `next` нет. Есть и собственный адрес `/login` — тот же экран; только с него после входа клиент переходит в каталог (`navigate('/catalog', { replace: true })`, записи в истории не остаётся). Экран входа рисуется без оболочки — без шапки, меню и подвала ([экран входа `/login`](#экран-входа-login)). Решение принимает `shellView(session, route)` (`features/auth/auth-state.ts`); во всех состояниях, кроме «страница», запросов данных нет.

| Сессия | Маршрут | Показано | `h1` |
| --- | --- | --- | --- |
| любая | `/health` | health-экран; не ждёт «Я» | «Состояние сервисов» |
| `loading` | остальные | «Проверяем вход…» | «Проверяем вход» |
| `error` | остальные | «Не удалось проверить вход…» и «Повторить» | «Вход не проверен» |
| `guest` | остальные, включая `/login` | экран входа без оболочки; при `expired` — «Сеанс завершён. Войдите снова.» | «Вход» |
| `user`, `accounts` | `/login` | страницы нет: переход в каталог с заменой записи истории | — |
| `user`, `local_single` | `/account`, `/login` | «Такой страницы нет…» | «Страница не найдена» |
| `user` без права модератора | `/catalog/merges`, `/catalog/merges/{id}`, `/catalog/classification` | «Раздел доступен модератору каталога.» и «В каталог» | «Раздел модератора каталога» |
| `user` | остальные | страница маршрута | заголовок страницы |

Шапка: гость видит её только на health-экране — «Состояние сервисов» и «Войти» (ведёт на `/login`); пользователь — прежние разделы и, в режиме `accounts`, своё имя ссылкой на `/account` (`aria-label="Аккаунт: имя"`). В `local_single` имени, «Аккаунт» и «Выйти» нет. Подразделы «Товары / Дубли / Категории» показаны только модератору.

Страница создаётся заново (`key = режим:user.id`), когда на той же cookie оказывается другой человек: данные двух людей на одном экране не смешиваются. Health-экран при смене сессии не пересоздаётся. Фокус переходит на `h1` при каждой смене того, что показывает оболочка: вход, результат входа, конец сеанса, пересозданная страница.

401 посреди сеанса снимает страницу целиком и открывает вход с текстом о завершённом сеансе. Несохранённые правки формы `needs_review` при этом теряются, как при перезагрузке: серверного черновика нет.

### Экран входа и «Аккаунт»

`LoginPage` — настоящая `<form method="post">` с полями «Имя пользователя» (`autocomplete="username"`, до 150 символов, без автозамены) и «Пароль» (`current-password`): менеджер паролей предлагает сохранить и подставляет. Имя отправляется как введено; пустые поля отклоняются без запроса. Раскладка экрана (логотип, подписи, переключатель темы) — [экран входа `/login`](#экран-входа-login).

`AccountPage` (`/account`): имя пользователя, кнопка «Выйти» и форма «Смена пароля» — текущий пароль, новый пароль (`new-password`) со списком четырёх правил сервера, повтор. Скрытое поле `username` помогает менеджеру паролей привязать новый пароль к учётной записи. После смены эта сессия остаётся, остальные сессии пользователя сервер завершает; поля очищаются. После выхода оболочка показывает вход без текста о завершённом сеансе.

Состояние каждой формы ведёт `createAuthForm`: один POST одновременно, второе нажатие во время запроса ничего не делает; кнопка не получает `disabled` (остаётся в фокусе, `aria-disabled`), подпись на время запроса — «Входим…» / «Сохраняем…» / «Выходим…». Результат выводится один раз рядом с кнопкой в области `aria-live="polite"`, неверные поля помечаются `aria-invalid`.

| Ответ | Вход | Смена пароля | Выход |
| --- | --- | --- | --- |
| `401 invalid_credentials` | «Неверное имя пользователя или пароль.» — одно на неизвестное имя, неверный пароль и выключенную запись | — | — |
| `429 login_throttled` + `retry_after` | «Слишком много попыток входа. Повторите через N минут.» (секунды округлены вверх до минут; без срока — «Повторите позже.») | «Слишком много попыток с неверным паролем. …» | — |
| `400 invalid_parameter`, `fields.current_password` | — | «Текущий пароль неверный.» | — |
| `400 invalid_parameter`, `fields.new_password` + `password_issues` | — | «Новый пароль не подходит. Пароль:» и нарушенные правила (`too_similar`, `too_short`, `too_common`, `entirely_numeric`); без кодов — все четыре | — |
| `403 csrf_failed` | «Токен безопасности устарел. Вход не выполнен: нажмите «Войти» ещё раз.» | то же про пароль | то же про выход |
| сеть, таймаут | «Нет ответа сервера. Проверьте соединение и повторите вход.» | «Ответ сервера не получен. Пароль мог измениться…» | «Ответ сервера не получен. Выход мог выполниться…» |
| `404` (сервер в `local_single`) | «Вход по паролю на этом сервере не используется. Обновите страницу.» | то же | то же |
| `401 not_authenticated` при смене пароля | — | сигнал `unauthenticated`, открывается вход | — |

Проверка «новый пароль и повтор совпадают» и «все поля заполнены» выполняется до запроса.

### Модератор каталога

Решения об общем каталоге — слияние дублей и категории — принимает пользователь с правом `catalog.moderate_catalog`; в `local_single` оно есть всегда. Без права:

- подразделов «Дубли» и «Категории» нет, прямые адреса дают экран «Раздел доступен модератору каталога.» без запросов;
- пометки «Дубли: требует подтверждения» и «Категория: требует подтверждения» в каталоге и блоки-пометки в карточке товара остаются текстом, без ссылок на группу и на список категорий (`MergeMarks.tsx`, `ClassificationMarks.tsx`); чтение списков для пометок открыто любому вошедшему;
- подсказка для поглощённого товара, пока слияние ждёт, ведёт на оставляемый товар, а не на группу;
- POST слияний и предположений сервер отклоняет `403 permission_denied`; если право отозвали посреди сеанса, первое же действие приводит к перечитыванию «Я» и экрану «Раздел доступен модератору каталога.».

### Моя / чужая покупка

История цен общая, чек за ценой — личный. Слово `own` здесь — «моя покупка»; с `role: 'own'` ряда цен («ряд этого товара») оно не связано.

- **История цен** (`GET products/{id}/prices/`, `PriceHistory.tsx`): у каждой точки обязательное `own`. У чужой точки (`own: false`) пять полей — `observed_at`, `quantity`, `discount_amount`, `receipt_id`, `position` — равны `null`; guard отвергает точку, у которой `own` расходится с этими полями, и ответ без `own`. В таблице появился столбец «Покупка»: «Моя · Чек №N» (ссылка на чек) либо «Чужая»; момент покупки под датой показан только у своих. Цены, магазин и дата видны у всех. Ключ строки — её место на странице: у чужих нет ни чека, ни позиции. Порядок строк считает сервер по настоящему моменту покупки. Ссылка на чек открывает его без контекста возврата: на чеке будет «К чекам».
- **Покупки группы дублей** (`GET product-merges/{id}/lines/`, `MergeLines.tsx`): не модератор получает только свои строки; модератор — все, у чужих `receipt_id: null`, остальные поля как есть, поля `own` нет. В столбце «Чек» у такой строки — «Чужая покупка» без ссылки и позиции.
- `products.last_observed_at` равно `null`, если последнее наблюдение чужое; экраны это поле не выводят.
- Сводка, ряды цен, альтернативы и сравнение не менялись.
- Чеки, фото, задания, вырезки и статистика — только свои; чужой id отвечает `404`, как несуществующий, и экраны показывают прежнее «не найдено». Файл чужого фото по прямой ссылке `/media/…` — пустой `404`; у `<img>` срабатывает прежняя замена картинки.
- В `local_single` все данные принадлежат пользователю `local`: на базе, созданной в этом режиме, все строки истории — «Моя».

### Проверки входа и разделения

Юнит-тесты (Vitest в Node, серверная разметка): `api/http.test.ts`, `api/session.test.ts`, `session/store.test.ts`, `features/auth/auth-state.test.ts`, `auth-markup.test.tsx`, `pages/session-shell.test.tsx`, дополнения в тестах маршрутов, пометок, истории цен и покупок группы; эталоны входа и «Я» — `backend/api/tests/fixtures/auth/`.

Настоящий HTTP двух пользователей без браузера — `frontend/scripts/check_accounts_proxy.mjs`:

```powershell
node frontend/scripts/check_accounts_proxy.mjs dev|preview <origin Vite> <файл с JSON от seed_accounts_demo>
```

Нужны сервер с `CHECKIST_AUTH_MODE=accounts`, свежая база после `migrate` и `seed_accounts_demo` (команда печатает JSON с идентификаторами; пароли в него не входят), те же пароли в `ACCOUNTS_DEMO_MODERATOR_PASSWORD` и `ACCOUNTS_DEMO_USER_PASSWORD`, точный origin Vite в `DJANGO_CSRF_TRUSTED_ORIGINS`; полный блок окружения и команды — в [ACCEPTANCE.md](../frontend/src/features/auth/ACCEPTANCE.md#запуск-qa-сервера-и-клиента). Скрипт вызывает настоящие адаптеры клиента через Vite proxy и ведёт отдельную «банку» cookie (`csrftoken`, `sessionid`) на каждого участника, сбрасывая токены CSRF при переключении. Проверяет: гость; неверный пароль (один раз, чтобы не включить задержку); вход двоих; чеки, фото, задания и вырезки не пересекаются, чужой id — `404`; история цен зеркально; покупки группы; `403` не-модератору; статистика; MEDIA своего и чужого; смена пароля гасит вторую сессию (пароль затем возвращается); выход и повтор старой cookie — `401`; ни в одном JSON-ответе нет `receipt_id`, ссылки или пути файла чужого чека. Каталог не меняется, прогон можно повторять на одной базе (dev, затем preview).

Шесть прежних proxy-скриптов (`check_catalog_proxy.mjs`, `check_recognition_proxy.mjs`, `check_review_proxy.mjs`, `check_product_merges_proxy.mjs`, `check_product_classifications_proxy.mjs`, `check_stats_proxy.mjs`) переносят только cookie `csrftoken` и рассчитаны на сервер без входа. Каждый проверяет окружение: без `CHECKIST_AUTH_MODE=local_single` в терминале скрипта (и сервера) он отказывает до первого запроса с объяснением. Переменную нужно задавать явно в блоке QA-окружения: умолчание сервера — `accounts`.

Не покрыто без браузера: cookie и SameSite в настоящем браузере, менеджер паролей, фокус в DOM, вторая вкладка, вид экранов, `429` на настоящем сервере, отзыв права посреди сеанса, вход через `/admin/`, работа за HTTPS-прокси. Фактические результаты прогонов QA записывает в [verification.md](verification.md).

## Health-экран

Health-страница React 19, TypeScript и Vite на русском языке показывает состояние настоящего анонимного `GET /api/health/`: API, базы данных, Redis и Celery. На этой технической странице бизнес-данные не выводятся; каталог и история доступны на отдельных маршрутах выше. Заглушек в SPA нет; `/login` — настоящий вход ([вход и сессия](#вход-сессия-и-разделение-пользователей-к1)). Контракт принадлежит backend: [api-contract.md](api-contract.md).

Компонент `src/pages/HealthPage.tsx` владеет состоянием технической страницы и кнопкой повтора, `src/api/health.ts` — запросом и runtime-проверкой JSON. Перенос из App сохраняет state/effect, AbortController, generation guard, словари статусов и повтор. Навигация реализована локально, глобальное состояние, UI-библиотеки, внешние шрифты и изображения не используются.

| Состояние | Поведение страницы |
| --- | --- |
| Открытие / повтор | «Проверяем соединение…», четыре строки проверки, «Повторить» disabled |
| Валидный 200 | «Соединение установлено», API отвечает, три сервиса доступны |
| Валидный 503 | «Некоторые сервисы недоступны», API отвечает, все checks сохранены |
| Ошибка сети | Понятное сообщение о соединении, состояния зависимостей неизвестны, повтор доступен |
| Таймаут 15 секунд | Сообщение об истёкшем ожидании, повтор доступен |
| 500 / протокольная ошибка | Безопасное сообщение, повтор доступен |
| Невалидный JSON / схема / пара HTTP–тело | Сообщение о некорректном ответе, повтор доступен |

Коды отказов переводятся в тексты: `database_unavailable` — «База данных недоступна», `redis_unavailable` — «Кеш недоступен», `broker_unavailable` — «Очередь задач недоступна», `worker_unavailable` — «Обработчик задач не отвечает». Серверные сообщения и исключения напрямую в UI не выводятся.

Повтор сбрасывает предыдущий результат и делает новый реальный запрос. Во время запроса кнопка недоступна. Замена запроса и unmount отменяют предыдущий AbortController; проверка поколения запроса и сигнала предотвращает запись устаревшего результата, включая повторный запуск эффекта в StrictMode. Таймаут охватывает fetch и чтение тела, timer и внешний abort-listener удаляются при завершении. Отмена отличается от ошибки сети и таймаута.

Статусы выражены текстом, сводка использует `aria-live="polite"`. Кнопка имеет видимый клавиатурный фокус. CSS резервирует высоту сводки и строк при загрузке, предусматривает узкий экран и перенос длинных сообщений. Анимаций нет. Фактическая визуальная, клавиатурная и интерактивная приёмка остаётся за человеком.

## Планируется

- Правка уже сохранённого чека и ручной выбор товара каталога для строки. Исправление и подтверждение неполного распознавания реализовано.
- Общий дашборд, курсы валют и пересчёт сумм между валютами. Тёмная и светлая темы [реализованы](#тема-бренд-и-экран-входа). Экраны статистики (траты, средний чек, график цен) [реализованы](#статистика-траты-средний-чек-и-график-цен-ф1ф7).

Health-экран перечисляет только будущие ручные правки, пользовательский вход и дашборд (его текст не менялся). Каталог, загрузка фото/OCR и просмотр чеков реализованы на отдельных маршрутах. Провайдер Codex CLI выбран оператором, fake служит проверкам. Пользовательский вход и доступ к своим чекам [реализованы](#вход-сессия-и-разделение-пользователей-к1); регистрации, восстановления пароля и управления пользователями в клиенте нет — учётные записи заводит оператор в `/admin/`. Предметная модель описана в [data-model.md](data-model.md); её API каталога/цен только на чтение, локальный API также принимает фото и cancel/retry ([контракт](api-contract.md)).

| `test` | `vitest run` — адаптер, Node environment, mocked fetch |
| `preview` | `vite preview` — локальный просмотр собранного приложения |

Vite читает единый корневой `.env` (`envDir` — корень репозитория), process environment имеет приоритет. Создать файл из `.env.example`, если его ещё нет; существующий не перезаписывать. Дополнительный `.env` внутри `frontend/` не требуется.

Адаптер берёт `import.meta.env.VITE_API_BASE_URL || "/api"`, убирает лишние завершающие и повторяющиеся слэши пути, добавляет `/health/`. Запрос передаёт `Accept: application/json`, `credentials: "omit"`, `cache: "no-store"`. По умолчанию браузер запрашивает `/api/health/` на своём origin.

Dev и preview слушают **127.0.0.1:5173**, `strictPort: true`: занятый порт приводит к ошибке, а не тихому выбору другого. В QA порт задаётся аргументом `--port 15173`. Proxy `/api` направляет запрос на `DEV_API_PROXY_TARGET` (default `http://127.0.0.1:8000`) **без переписывания пути**. Например, `http://127.0.0.1:15173/api/health/` → `http://127.0.0.1:18000/api/health/`.

`DEV_API_PROXY_TARGET` используется только Node-конфигурацией Vite. `envPrefix: []` выключает автоматическую передачу пользовательских env-переменных; через `define` передаётся только `VITE_API_BASE_URL`. Общий env-объект, DB-реквизиты и секреты не прокидываются в браузер. `VITE_API_BASE_URL` публичен и не должен содержать секреты. После изменения env перезапустить Vite; публичный адрес фиксируется при build, для preview после его изменения нужна новая сборка. Произвольный внешний origin/CORS не проверен; результаты и ограничения проверки — в [verification.md](verification.md).

При остановленном API Vite 8.3.2 возвращает пустой HTTP **502**, хотя браузер по-прежнему достигает самого Vite. Адаптер трактует не-JSON 502/504 как ошибку соединения. Валидный health 503 обрабатывается отдельно с сохранением checks.

Для просмотра сборки при работающем QA API и применённых QA overrides:

```powershell
Set-Location frontend
npm.cmd run build
npm.cmd run preview -- --port 15173
```

Предварительно остановить dev-сервер на этом порту. Preview — локальный инструмент приёмки; production reverse proxy, hosting и deployment не настроены.

В F6 базовые образцы и дополнения загружены в `checkist_qa` и сохранены после `down`; повторная загрузка для ручной приёмки не нужна. ## Ручная приёмка каталога человеком

Автоматический обход browser UI запрещён. Ниже сценарий §6 ответа `task_mutu93ml5l`, для доступного QA API и расширенных синтетических данных. Скриншоты и визуальные результаты в F5 не создавались. Настоящий интерфейс доступен человеку локально через команды выше; автономного макета с подставными данными нет.

1. На `http://127.0.0.1:15173/catalog` пройти дерево → категорию (включая родителя с товарами потомков) → список → Product → историю и сводку. Сверить значения с QA API, включая RU `130.5882 RUB/л` и DE `normalized=null`. Проверить поиск по имени/бренду/модели/GTIN, generic, страницы и сброс. В истории применить точку/страну/валюту/локальный период; сводка охватывает всё окно, а не страницу.
2. Скопировать URL категории и товара с query, открыть напрямую и reload. Back/Forward и «Назад к списку» восстанавливают `q`, `generic`, page; direct-entry товара имеет выход в категорию. Проверить неверный ID пути/неизвестный ID/неверный диапазон/page вне набора — безопасные разные сообщения и сброс/первая страница. При возврате проверить фокус выбранного товара после загрузки; с Slow network перевести фокус в форму до ответа и убедиться, что App его не перехватывает. Если товара больше нет, заголовок остаётся доступен.
3. Пустая категория, поиск без совпадений, Product без покупок, пустые фильтры истории/сводки/магазинов; отсутствующие бренд/фасовка/нормализация. Один Product в двух точках и валютах: точки не склеиваются, валюты/единицы/неизвестные налоги не становятся одной сравнимой ценой. Поиск магазинов не ограничен 50 точками карточки; точка без покупок даёт пустую историю.
4. DevTools Slow network: быстро менять query/фильтры и уходить со страницы; поздний ответ не подменяет новый. Отдельно заблокировать `prices/`, затем `prices/summary/`, затем `stores/`: карточка и другие доступные секции сохраняются, локальный повтор восстанавливает свою секцию. Offline → ошибка → Online → повтор. Задержка fetch или тела >15 секунд → timeout → снять задержку → повтор. Проверить доступность форм и недоступные действия.
5. Только клавиатурой: ссылка «К содержимому», Tab/Shift+Tab, Enter у ссылок/поиска, Enter/Space у кнопок, native selects, сброс/повтор, страницы, фокус при переходах и возврате. Screen reader читает единственный h1, крошки/labels/ошибки/таблицу/caption/th и локальные статусы без избыточных объявлений. Обновление query не забирает фокус из формы. Повторы и локальные страницы проверить отдельно по сценарию R2 ниже.
6. Ширины **320/375/768/1280 px**, **zoom 200%**, длинные названия/адреса/GTIN: действия видны, тексты переносятся, фокус различим, вертикальный scroll принадлежит странице, горизонтальный — подписанному контейнеру таблицы. Проверить геометрию loading и reduced motion. По завершении повторить health-сценарий ниже и из verification.md: успех, частичный отказ, сеть/timeout, повтор, клавиатура и узкий экран.

### Клавиатурная приёмка локального фокуса R2

Нужны работающие QA API/Vite по командам выше и вымышленные QA-данные. Для кнопок страниц справочника нужны **более 50 подходящих магазинов**, для списка/истории — более 50 товаров/наблюдений; базовые образцы F6 этого не дают. Такие данные готовит человек только в изолированной QA, без очистки существующих томов. Автоматического browser runner и подтверждения этого сценария агентом нет.

1. В DevTools вручную заблокировать только запрос проверяемого блока и перезагрузить страницу. В карточке/категории остальные запросы не блокировать. Повторить весь цикл для каждой строки таблицы:

   | Страница и блок | Запрос для блокировки | Устойчивая цель фокуса |
   | --- | --- | --- |
   | `/catalog`: дерево категорий | `/api/categories/` без ID | h2 «Категории» |
   | `/catalog/categories/<id>`: сведения категории | `/api/categories/<id>/` | h2 «Категория», после успеха — имя категории |
   | `/catalog`: товары | `/api/products/` без ID | h2 «Все товары» / «Результаты поиска» |
   | `/catalog/categories/<id>`: товары категории | `/api/products/` без ID, с фильтром категории | h2 «Товары всей ветви» |
   | `/catalog/products/<id>`: карточка | `/api/products/<id>/`, без `prices/` | h2 «Карточка товара», после успеха — имя товара |
   | Там же: история | `/api/products/<id>/prices/`, без `summary/` | h2 «История цен» |
   | Там же: сводка | `/api/products/<id>/prices/summary/` | h2 «Сводка по магазинам» |
   | Там же: справочник магазинов | `/api/stores/` | legend «Магазин» |

2. Только Tab/Shift+Tab дойти до **локальной** «Повторить», нажать Enter или Space. На loading фокус и его рамка переходят к цели из таблицы. Оставить блокировку: после новой ошибки фокус на «Повторить» **этого же блока**. Затем снять блокировку, вернуть клавиатурный фокус на эту кнопку и повторить с сетевой задержкой меньше 15 секунд: на loading и после успеха фокус на той же локальной цели. Следующий Tab продолжает работу из блока; фокус не на body, h1 или соседней секции.
3. В справочнике с >50 результатов сфокусировать «Следующие магазины», нажать Enter. На loading кнопки исчезают: фокус на legend «Магазин»; после ответа там же. Через Shift+Tab выбрать магазин или Tab продолжить по действиям блока. Перейти назад кнопкой «Предыдущие магазины», повторить на последней странице и при новой ошибке. Если контрол сохраняется доступным, допустимо оставить фокус на нём; недоступный/удалённый контрол передаёт его локальной цели. Поле поиска и выбор магазина остаются доступны в обычной клавиатурной последовательности.
4. На нескольких страницах товаров/истории нажать Enter у следующей/предыдущей/номерной ссылки: loading и ответ сохраняют фокус у h2 **своих** результатов. Открыть корректный `?page=999999`, получить `page_out_of_range`, клавиатурой нажать «На первую страницу»: фокус у того же h2. Для справочника воспроизвести устаревшую страницу на отдельном QA-наборе, уменьшив число подходящих магазинов между запросами вручную: «Первая страница магазинов» передаёт фокус legend. При отсутствии такого набора этот вариант записать как непроверенный.
5. Поиск без совпадений в каталоге/категории или пустая фильтрованная история: Enter/Space на «Сбросить фильтры» **в результате** сохраняет фокус у h2 результата. Сброс **в форме каталога** возвращает его в поле поиска; сброс/«Применить фильтры» в форме товара оставляет на устойчивой кнопке. Поиск Enter из полей каталога и магазина сохраняет фокус в поле до/после ответа; поиск кнопкой оставляет на устойчивой кнопке. Проверить исправление/сброс поиска магазинов при 400 и «Убрать магазин»: если нажатая кнопка исчезла, цель — legend «Магазин».
6. С Slow network нажать повтор/пагинацию и **до ответа** перевести Tab/Shift+Tab фокус в другой блок: успех и повторная ошибка его не забирают. Повторить с переводом в поле поиска того же блока: ввод не прерывается. Быстро менять поиск/фильтры, использовать Back/Forward и уходить на другой pathname: устаревший/отменённый ответ не меняет фокус; переход маршрута оставляет F2-фокус на h1, возврат в список — на выбранном товаре после загрузки, если пользователь не ушёл с заголовка.
7. Screen reader: загрузка/результат объявляются локально и спокойно, без добавленных двойных live-объявлений; после повторной ошибки доступна кнопка повтора. На 320/375/768/1280 px, zoom 200% и с длинными текстами проверить видимый фокус и действия, отсутствие перекрытий/горизонтального scroll страницы. Вертикальная прокрутка — страницы, горизонтальная — только таблицы. После проверки снять блокировки и остановить свои процессы/QA по правилам выше.

## Исторический ручной сценарий F2: каркас и переходы

В своём QA-терминале применить полный environment выше, выполнить в `frontend/` `npm.cmd ci`, затем `npm.cmd run dev -- --port 15173`. Для проверки preview сначала `npm.cmd run build`, остановить dev, затем `npm.cmd run preview -- --port 15173`. Ниже проверяется настоящий интерфейс; отдельного статического макета нет. У заглушек не требуется catalog API. Для успешных health-состояний нужен свой подготовленный QA backend/worker по инструкциям выше.

1. Открыть `/`, затем `/catalog?q=молоко&generic=2&page=3`: видны «Каталог продуктов» и явная заглушка следующего этапа. В Network не должно быть health-запроса. На F2 это заглушки с ID, параметры остаются в адресе; карточка и запросы каталога появятся после F5. Повторить на preview. `/missing` и `/catalog/products/0` показывают «Страница не найдена», «В каталог» возвращает в каталог.
3. `/catalog/categories/42?page=0` и `/catalog/products/42?date_from=2026-02-29` показывают «Некорректная ссылка». «Сбросить параметры» сохраняет нужный маршрут, удаляет query и заменяет ошибочную запись History; Back не возвращает тот же ошибочный URL. Лишний `unknown=1` не ломает маршрут, `page=2&page=3` использует 3.
4. Проверить Tab/Shift+Tab, Enter на ссылках, видимый фокус и «К содержимому». Ctrl/Cmd-клик, Shift-клик и средняя кнопка оставляют нативные новые вкладки/окна. До F5 эти формы и пагинация не выведены в заглушки; Node-проверки разметки не заменяют эту приёмку.

Вернуться в health, повторить сценарий ниже (загрузка, частичный отказ, безопасная ошибка/повтор); без работающего API ожидается безопасная ошибка. Успех/отказы настоящих зависимостей принимаются только со своим QA backend.

После приёмки остановить созданный Vite/preview через Ctrl+C; если запускался свой QA backend/Compose, выполнить уборку по разделу health ниже. Не останавливать чужую QA.

## Ручной сценарий health-приёмки человеком

Открыть `http://127.0.0.1:15173/health`. Автоматический обход browser UI запрещён правилами проекта; результаты и ограничения ручной приёмки — в [verification.md](verification.md).

1. При первом открытии увидеть «Проверяем соединение…», недоступную кнопку повтора, затем «Соединение установлено» и все три успешных статуса. Чтобы рассмотреть загрузку, временно замедлить сеть в DevTools. Проверить, что блок не меняет высоту при смене состояния.
2. В третьем QA-терминале выполнить `docker compose -p checkist_qa stop worker`. Нажать «Повторить»: во время запроса кнопка disabled, затем «Некоторые сервисы недоступны», API отвечает, БД/Redis доступны, Celery — «Обработчик задач не отвечает». Выполнить `docker compose -p checkist_qa up -d --wait --wait-timeout 90 worker`, дождаться healthy, повторить — успех.
3. Остановить QA runserver через Ctrl+C, оставить Vite работающим. «Повторить» должно показать «Не удалось проверить соединение» и «Не удалось связаться с сервером…». Прежний успех и успешные статусы не должны остаться текущими. Вернуть API той же командой, нажать «Повторить» без reload — успех.
4. В DevTools включить Offline, повторить: безопасная ошибка и доступная кнопка. Вернуть Online, повторить — успех. Для таймаута задержать health-запрос дольше 15 секунд при доступном Vite: показать сообщение «Сервер не ответил за 15 секунд…», без вечной загрузки. Затем снять задержку и повторить.
5. Tab до «Повторить», проверить видимый фокус, Enter/Space запускают запрос. Убедиться, что при завершении можно продолжить клавиатурную работу. Со screen reader проверить объявление сводки при успехе/отказе.
6. На ширине около 375 px повторить успех, частичный отказ и ошибку сети: нет горизонтальной прокрутки, обрезанных сообщений или скрытой кнопки. Проверить масштаб 200%, длинные тексты и читаемость статусов без опоры только на цвет. При reduced motion интерфейс остаётся статичным.
7. Убедиться, что health-страница техническая, будущие ручные правки/пользовательский вход/дашборд показаны только списком; загрузка чеков доступна отдельно из меню «Чеки».

После приёмки Ctrl+C остановить Vite/preview и runserver, выполнить `docker compose -p checkist_qa down` без `-v`, проверить отсутствие созданных процессов и QA-слушателей. Тома сохраняются; закрыть QA-терминалы, чтобы overrides не попали в dev.

## Границы автоматических проверок

Vitest проверяет API-адаптер с mocked fetch в Node, без jsdom/Playwright: 200, каждый документированный код отказа и их комбинации, сохранение checks при 503, 405/406/500, сеть/502/504, таймаут fetch и чтения тела, внешний abort, отмену до запроса и поздний ответ, cleanup, неправильный JSON, схему и несогласованную пару HTTP–тело. Это не тесты React-поведения или настоящих сервисов.

Реальная интеграция проверяется отдельно через HTTP/CLI; сборка подтверждает только типизацию и создание bundle. Результаты сквозной проверки через Vite proxy и ограничения — в [verification.md](verification.md). Ручную UI-приёмку, скриншоты, browser runtime и производственный запуск автоматические проверки не подтверждают.

Общие документы описывают реализованные frontend и backend. Frontend владеет `frontend/` и `docs/frontend.md`; backend — контрактом API, серверной инфраструктурой и общими документами. Сценарии и результаты сквозной проверки — в [verification.md](verification.md).
