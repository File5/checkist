# Frontend Checkist

## Каркас и навигация

`App.tsx` владеет оболочкой: шапкой «Каталог / Чеки / Обработка / Состояние сервисов», единственным `h1`, document title и содержимым текущего маршрута. При первом открытии и смене pathname фокус переходит на `h1#page-heading` (`tabIndex=-1`); изменение только query не забирает фокус из формы. Есть ссылка «К содержимому». Каталог не запрашивает health и не зависит от его результата. F5 подключает настоящие `CatalogPage`, `CategoryPage` (F3) и `ProductPage` (F4) вместо точек подключения F2; данные загружаются адаптерами F1, runtime-mocks и вымышленных цен в UI нет.

| URL | Экран и query |
| --- | --- |
| `/`, `/catalog` | Каталог; `q`, `generic`, `page` |
| `/catalog/categories/:id` | Категория; `q`, `generic`, `page` |
| `/catalog/products/:id` | Товар и история; `store`, `country`, `currency`, `date_from`, `date_to`, `page` |
| `/health` | Прежний технический health-экран |
| `/receipts` | Чеки; `q`, `date_from`, `date_to`, `operation`, `ordering`, `page`; также поддержаны ссылки с `store`, `product`, `country`, `currency` |
| `/receipts/upload` | Загрузка одного фото с одним или несколькими чеками |
| `/receipts/:id` | Чек: шапка, изображения всех фото, строки, скидки, налоги |
| `/recognition/jobs` | Обработка; `photo`, `status`, `ordering`, `page` |
| `/recognition/jobs/:id` | Задание: статус, этап, исходник, вырезки, cancel/retry |
| Неизвестный путь или неверный ID | «Страница не найдена», ссылка «В каталог» |

`/` — алиас каталога без принудительного redirect; build создаёт `/catalog`. Один завершающий слэш допустим. ID и page — положительные safe integers, небезопасные значения не округляются. Первая страница подразумевается и при build не записывается. Поиск trim, 2–100 Unicode code points; пустое значение означает отсутствие фильтра. Коды стран/валют приводятся к верхнему регистру, проверяется их синтаксис; существование в справочнике проверяет API. Даты — настоящие календарные `YYYY-MM-DD`, нижняя граница не позже верхней. Управляющие символы в известных параметрах запрещены. Неизвестные и чужие этому маршруту параметры игнорируются, повторённый параметр берётся по последнему значению. Кодирование выполняет `URLSearchParams`; строки не склеиваются в query вручную.

Некорректный известный query даёт экран «Некорректная ссылка» со сбросом параметров через replaceState; запрос данных в этом состоянии не запускается. Положительный page сохраняется даже без знания pages: `page_out_of_range` обрабатывает экран, получивший API-ответ, со ссылкой на первую страницу. Смена фильтров в F3/F4 должна явно устанавливать `page: 1`.

Используются History API и popstate без библиотек. `Link` рендерит обычный `<a href>` и перехватывает только основной клик без модификаторов: Enter поддерживается браузером, Ctrl/Cmd/Shift/Alt, другие кнопки мыши, target, download, фрагменты и внешние ссылки сохраняют нативное поведение. Back/Forward читают маршрут и фильтры из адреса. При переходе из каталога/категории в товар исходный URL хранится в history state; история фильтров товара сохраняет этот контекст, reload читает его заново. Контекст принимается только для корректного внутреннего URL совместимого списка или связанной detail-страницы (job/receipt/product, см. раздел распознавания). При прямом входе `returnTo` отсутствует: после загрузки F4 предлагает категорию товара. При возврате в исходный список App ждёт загрузки ссылки выбранного товара и возвращает ей фокус. Если пользователь уже перевёл фокус, ожидание отменяется; если товар исчез или список не загрузился, остаётся заголовок. Уход и изменение query отключают observer. Фактический фокус и прокрутку принимает человек.

Прямые URL и reload поддерживаются SPA fallback Vite dev/preview: сервер отдаёт `index.html` для этих путей. Это проверяется HTTP, отдельно от работы React в браузере. Production hosting, reverse proxy и их fallback не настроены и не подтверждаются.

### Интерфейсы для F3/F4/F5

Все публичные функции и типы навигации экспортируются из `src/navigation/index.ts`:

```ts
type CatalogQuery = { q?: string; generic?: number; page: number }
type HistoryQuery = {
  store?: number; country?: string; currency?: string
  date_from?: string; date_to?: string; page: number
}
type NavigableRoute =
  | { kind: 'catalog'; query: CatalogQuery }
  | { kind: 'category'; categoryId: number; query: CatalogQuery }
  | { kind: 'product'; productId: number; query: HistoryQuery }
  | { kind: 'health' }
type Route = NavigableRoute
  | { kind: 'not-found'; path: string }
  | { kind: 'invalid-query'; path: string; fields: string[]; resetTo: string }
type NavigationTarget = string | NavigableRoute
type NavigateOptions = { replace?: boolean }
type NavigationSnapshot = { href: string; route: Route; returnTo?: string }

parseRoute(input: string | URL): Route
buildRoute(route: NavigableRoute): string
parseCatalogQuery(search: string | URLSearchParams): ParsedQuery<CatalogQuery>
parseHistoryQuery(search: string | URLSearchParams): ParsedQuery<HistoryQuery>
// ParsedQuery<T> = { query: T; invalidFields: string[] }
buildCatalogQuery(query: CatalogQuery): string
buildHistoryQuery(query: HistoryQuery): string
// buildQuery возвращает ведущий '?' или ''. Невалидный build бросает RangeError.
navigate(target: NavigationTarget, options?: NavigateOptions): void
useNavigation(): NavigationSnapshot
useRoute(): Route
```

`navigate` допускает только HTTP(S) этого origin, публикует snapshot сразу после push/replace (браузер сам не вызывает popstate), не добавляет дубликат текущего URL. `Link` — именованный export из navigation, default export из `navigation/Link.tsx`; props: `to: NavigationTarget`, `replace?: boolean`, остальные нативные props ссылки кроме href (включая onClick). `createNavigation(environment)` из `navigation/controller.ts` — тестируемый store с `navigate/getSnapshot/subscribe`; `NavigationEnvironment` предоставляет `getHref/getState/pushState/replaceState/listenPopState`. Импорт helpers в Node не требует window; browser hooks используются только в SPA.

`RequestState` — default export из `components/RequestState.tsx`; props — объединение:

```ts
{ kind: 'loading'; message?: string }
| { kind: 'error'; message?: string; onRetry: () => void; retryDisabled?: boolean }
| { kind: 'empty'; message: string; action?: ReactNode }
```

Loading резервирует min-height без фиксированной высоты. Все варианты используют `aria-live="polite"`, `aria-busy` true только при loading. Error по умолчанию показывает локальный безопасный текст и «Повторить»; message должен быть собственным переводом UI, серверные message/fields/исключения передавать запрещено. Пустое состояние допускает действие (обычно Link). Успешное содержимое рендерит владелец запроса; запросы, отмена, гонки и соответствующие блоки aria-busy остаются у feature-экрана.

`Pagination` — default export из `components/Pagination.tsx`; props:

```ts
{ page: number; pages: number; buildPageHref: (page: number) => NavigationTarget; label?: string }
```

`buildPageHref` меняет только page и сохраняет текущие фильтры. Default label — «Страницы результатов». Навигация — нативные ссылки, ровно одна имеет `aria-current="page"`; предыдущая/следующая скрываются на границах. При pages 0/1 либо некорректных счётчиках компонент не рендерит навигацию; выход за диапазон обрабатывает экран. На больших наборах остаются первая/последняя и окно около текущей страницы (до семи ссылок страниц), без создания тысяч элементов.

Ожидаемые props экранов экспортированы из `src/pages/types.ts`:

```ts
CatalogPageProps = { query: CatalogQuery }
CategoryPageProps = { categoryId: number; query: CatalogQuery }
ProductPageProps = { productId: number; query: HistoryQuery; returnTo?: string }
```

Feature-экраны рендерятся под общим h1, собственный h1/main/shell не создают; имена категории/товара используют h2. Они владеют формами и запросами, используют native label/input/select, самостоятельные inline-сообщения. Новых систем состояния, оверлеев, уведомлений или локализации не добавлено; UI русский, форматирование принадлежит F1. F3/F4 могут импортировать общие компоненты, навигацию и props без правок файлов F2.

### Границы данных

- Runtime-схемы сохраняют `position=0`: позиция строки — неотрицательное безопасное целое, ID — положительное. История использует ключ `receipt_id:position`, без проверки позиции на truthiness. Невалидная обязательная запись даёт ошибку всего блока, строки молча не отбрасываются.
- Нулевые счётчики каталога, магазинов и пустых страниц допустимы (`page=1`, `count=pages=0`). `observations` внутри существующей группы/магазина товара, `total.count` и `buckets[].count` положительны: backend строит эти группы только из наблюдений. `skipped_without_normalized` может быть нулём. Размер массива страницы ограничен `page_size`, но не счётчиком `count`: COUNT и выборка могут видеть разные SQL-снимки при конкурентном вводе.
- В ответах коды стран/валют принимаются как непустые строки длиной до 2/3 Unicode-символов: модели справочников не проверяют ISO-синтаксис и сериализация их не меняет. Значения сохраняются без изменения регистра. Фильтры query по-прежнему требуют ISO-синтаксис; введённый через админку нестандартный код может отображаться, но backend не принимает его как фильтр. `model`, `gtin`, город, адрес и названия-сопоставления могут быть пустыми; `attributes` остаётся произвольным JSON. Decimal принимаются строками с фиксированной точностью, со знаком и нулём; календарные даты и UTC-моменты с `Z` проверяются отдельно.
- Аудит R3 со ссылками на фактические ограничения backend, регрессиями и сценарием ручной приёмки — [frontend/R3_ACCEPTANCE.md](../frontend/R3_ACCEPTANCE.md).

- Это **наблюдения покупок из чеков**, не текущие предложения магазина. Отображаются только сопоставленные товарные позиции продаж; возвраты, залог и услуги в историю не входят.
- Валюты и фактические единицы не смешиваются. Нормализованная цена подписана своей единицей; `comparable` означает совместимость единиц, не налоговой базы. Налоги неизвестны, скидка всего чека по товарам не распределена, средняя в сводке невзвешенная.
- Decimal остаются строками; UI не считает деньги через JS Number. `null` означает отсутствие данных, не нулевую цену. Интерфейс русский, десятичная запятая, явный код валюты; `purchased_on` — локальная календарная дата, момент без известного timezone подписан UTC.
- Карточка отдаёт до 50 магазинов и aliases без признака усечения. Поиск `/stores/` охватывает **все** магазины выбранной страны, включая точки без покупок товара; полного списка только магазинов товара API не предоставляет. Варианты выбора не выводятся из текущей страницы истории. Адрес/timezone обогащаются по ID из карточки, просмотренных страниц справочника и успешной сводки `group_by=store`, которая уже содержит полные объекты магазинов за выбранный период. Обогащение из сводки не добавляет запросов и не блокирует историю при её отказе.
- История, сводка и фильтр используют одну подпись: `ID 51 · Same Chain · адрес · Berlin · DE`. ID стоит первым, чтобы оставаться различимым и при длинном тексте в native select. Если адрес отсутствует, пуст или ещё не загружен: `ID 51 · Same Chain · Berlin · DE · адрес неизвестен`. При прямом выборе ID из URL краткие сведения выбранной точки берутся из загруженной истории только для подписи; без них остаётся `ID 51 · Не указано · адрес неизвестен`. Отказ справочника сохраняет карточку, строки истории, независимую сводку и известные адреса; неизвестные точки остаются различимыми по ID. Фильтр явно подписан как недоступный, локальный повтор и удаление выбранного магазина доступны.
- В контракте нет `/api/stores/{id}/` и фильтра списка магазинов по ID: доступны только `country`, `q`, `page`, `page_size`. Автоматической адресной дозагрузки неизвестных ID и полного обхода справочника нет. Пока адрес не появился в карточке, успешной сводке или просмотренной странице поиска, UI сохраняет корректный fallback с ID. Поиск по названию/городу и переходы страниц позволяют получить адрес вручную; ID и адрес не являются серверными параметрами поиска.
- ID в JSON — JS-числа. Адаптер и навигация требуют положительный `Number.isSafeInteger`; ID выше `Number.MAX_SAFE_INTEGER` отвергаются, округлённые ссылки не создаются. Полный диапазон BigAutoField пока не поддержан.

Регрессионные проверки подписей и сценарий ручной приёмки — [R1: различимые точки в истории цен](../frontend/R1_ACCEPTANCE.md).

### Фокус при локальных обновлениях (R2)

Каждый независимый запрос имеет устойчивый заголовок с `tabIndex=-1` и `data-request-focus-target`: дерево категорий, сведения категории, товары, карточка, история, сводка; справочник магазинов использует устойчивый `legend` «Магазин». `useLocalRequestFocus` и тестируемый контроллер `local-request-focus.ts` из `src/components/` следят за фокусом только внутри своего блока. `RequestState` помечает кнопку повтора `data-request-retry`; собственная кнопка справочника использует ту же метку. Эти метки не добавляют ARIA-роли или live-регионы.

Если сфокусированная кнопка/ссылка удаляется или становится недоступной при обновлении, фокус получает заголовок этого же блока во время loading. После успеха он остаётся на заголовке результата; после повторной ошибки запроса возвращается на доступную кнопку «Повторить» своего блока. Если ответ требует исправления параметров или сообщает об отсутствующем объекте, заголовок сохраняется. Устойчивая цель карточки существует и после `not_found`. Сохранившиеся доступные контролы пагинации, поиска и фильтров сохраняют фокус. Сейчас кнопки страниц магазинов исчезают на время loading, поэтому их локальная цель — `legend` «Магазин»; ссылки страниц истории и товаров используют собственный h2.

Тот же механизм охватывает локальные «Сбросить фильтры», первую страницу при `page_out_of_range`, сброс поиска магазинов и исчезающую кнопку «Убрать магазин». Сброс формы каталога по-прежнему возвращает фокус в поле поиска; применение фильтров/поиска из устойчивого поля или кнопки оставляет его в форме. Переход pathname принадлежит App/F2 и переносит фокус на h1; локальный хук не меняет навигацию и возврат к выбранному товару.

При уходе фокуса в другой блок ожидание восстановления отменяется, в том числе если позже фокус оказался на body. Потеря фокуса на body компенсируется только при подтверждённой принадлежности удалённого/недоступного элемента этому блоку. На первый ответ без локального действия переноса нет. Хук обрабатывает только принятые снимки состояния после React commit; существующие AbortController/generation guards владельцев запросов не допускают устаревшие или отменённые результаты. На unmount локальное ожидание и focusin-listener удаляются. Существующий `[tabindex]:focus-visible` показывает синюю рамку; повторное focus на уже активном заголовке не выполняется. Существующие `aria-live="polite"`, `role="status"` и `aria-busy` сохранены, дополнительные объявления не добавлены.

Правила выбора цели, последовательности loading/error/ok, поколения запросов и разметка проверяются Vitest в Node и SSR без новых зависимостей. Реальный DOM-фокус, прокрутку, screen reader и визуальное поведение принимает человек по сценарию ниже; результаты и ограничения R2 — [отчёт](../frontend/R2_ACCEPTANCE.md).

### CLI настоящего HTTP без браузера

Из корня, Node 24, после полного QA environment, запуска API и Vite:

```powershell
node --check frontend/scripts/check_catalog_proxy.mjs
node frontend/scripts/check_catalog_proxy.mjs healthy
# Если выбран другой свободный Vite-порт:
node frontend/scripts/check_catalog_proxy.mjs healthy http://127.0.0.1:15174
```

Скрипт без новых зависимостей использует настоящий fetch и исходные адаптеры с **явным baseUrl** напрямую и через Vite. Сверяет HTTP, Content-Type, Allow, полный JSON и результат адаптера; не переносит health-требование Cache-Control на каталог. Проверяет категории/detail, generic, товары/detail, history/summary, магазины, поиск и фильтры, минимум две страницы `page_size=1` у товаров, наблюдений и магазинов, 400 (page_size/q/date_from) и 404 `page_out_of_range`/`not_found`. Все существующие ID получает из ответов; отсутствующий ID категории вычисляет из полного дерева. QA-набор должен содержать хотя бы два товара, две точки и один Product с двумя покупками; при нехватке данных скрипт завершается с объяснением. Во время сверки QA-данные не менять: общего снимка между HTTP-запросами нет.

Ошибки конфигурации, недоступный API/proxy, неожиданный статус/JSON или результат адаптера дают `Catalog check FAILED: …` и exit 1. Единственный режим — `healthy`; остановки Postgres/API проверяются отдельно человеком, успешный negative-test не равен успешному HTTP-прогону. Скрипт требует `POSTGRES_DB=checkist_qa`, `VITE_API_BASE_URL=/api` и разные HTTP loopback origins; `DEV_API_PROXY_TARGET` задаёт прямой адрес API.

## Распознавание и чеки (И1–И5)

Экраны подключены в App к настоящему локальному API, без вымышленных данных. Загрузка принимает один JPEG/PNG/WebP: локально проверяет тип и размер по полученным лимитам, показывает предпросмотр через object URL и освобождает его при замене/уходе. Сервер проверяет фактические байты, одиночный кадр, размер и пиксели. Неизвестный браузеру MIME не заменяет серверную проверку. Указано, что установленный Codex передаёт фото облачной модели. Загрузка и retry разрешены и при executor=false: доступность idle-воркера неизвестна.

`src/api/recognition.ts` и `receipts.ts` используют `http.ts` и runtime-схемы для Photo, Job, ReceiptImage, Receipt, строк, скидок и налогов, включая nullable поля и Decimal strings. Эталоны тестов читаются прямо из `backend/recognition/tests/fixtures/public/`. Успешный HTTP без подходящего JSON становится `invalid_response`; provider payload/message не показываются. Деньги форматирует `lib/format.ts` строками/BigInt, с запятой и валютой. Дата покупки отображается в timezone магазина, технические моменты задания — явно UTC. Неизвестные поля чека подписаны «Не распознано»; nullable данные needs_review — «Не прочитано».

CSRF transport: `GET /api/recognition/csrf/` устанавливает cookie и возвращает token/limits/executor. Token хранится только в памяти, параллельные читатели разделяют запрос и могут отменяться независимо. Все новые запросы используют `credentials: same-origin`; POST отправляет `X-CSRFToken`. Upload — FormData, Content-Type с boundary устанавливает fetch; cancel/retry — JSON `{}`. Таймаут чтения/действий 15 с, upload 60 с; AbortSignal прекращает ожидание клиента. После `csrf_failed` token сбрасывается; новое явное действие получает новый token. POST никогда не повторяется автоматически. При сетевой ошибке действие могло сохраниться: UI предлагает проверить обработку до повтора. Уход со страницы/отмена fetch не отменяют серверный job.

Vite dev **и preview** передают `/api` и `/media` на один `DEV_API_PROXY_TARGET`, без rewrite, с changeOrigin. `DJANGO_CSRF_TRUSTED_ORIGINS` должен содержать точный origin клиента (порт включён). Поддержан один browser origin, внешний CORS не настроен. `safeMediaUrl` разрешает только относительные пути `/media/`, без внешнего host, traversal, query/hash и encoded separators. В v1 backend принимает только `MEDIA_URL=/media/` (default при отсутствии переменной); любое другое значение, включая пустое, даёт ранний `ImproperlyConfigured`. Клиентские проверки URL и Vite proxy рассчитаны только на `/media/`; изменение префикса требует согласованной правки клиента и proxy. Исходник, preview и вырезки имеют alt и отдельный fallback/повтор при ошибке изображения. MEDIA отдаётся Django только при DEBUG, независимо от флага локального API. Описания «Vite только /api» в исторических backend-документах относятся к состоянию до И1.

Job detail опрашивается после ответа раз в 2 с, без перекрытия запросов. После сетевых отказов интервалы 2/4/8/15 с, в скрытой вкладке не менее 10 с; возвращение во вкладку обновляет данные. Последний корректный снимок сохраняется с локальной ошибкой/повтором. Старое поколение запроса и меньшая version не принимаются; heartbeat той же version допустим. Terminal status прекращает опрос. Список заданий обновляется, пока видимые задания active. Смена route/query и unmount отменяют запросы и таймеры. Cancel/retry приостанавливают чтение на время POST. `actions.can_cancel/can_retry` управляют доступностью; сервер повторно проверяет состояние, 409 приводит к обновлению снимка. Cancel running показывает «Отмена запрошена» до подтверждения воркера.

Шапка задания, исходник и вырезки независимы; вырезки обновляются при изменении items/version, preview — этапа. `needs_review` показывает вырезку, фиксированные причины и безопасный нормализованный результат в details. Успешные imported/reused/updated с issues показывают «Замечания распознавания»: наличие issues само по себе не делает их needs_review. Единую подпись статуса и один компонент замечаний используют задание и чек — см. [сгруппированные замечания](#сгруппированные-замечания-распознавания). Черновиков, ручной формы исправления и подтверждения в v1 нет.

Список чеков имеет поиск по данным контракта, период, продажу/возврат, сортировку и пагинацию в URL. Пустой список предлагает загрузку; пустой результат фильтров — сброс. Детальный чек независимо загружает шапку, все изображения, строки, скидки и налоги с локальными loading/empty/error/retry и отдельными страницами. Отказ шапки сохраняет строки с предупреждением об неизвестной валюте. Несопоставленный товар явно подписан; залог и скидки ссылаются на строку или её ID на другой странице. Таблица строк имеет собственную фокусируемую область горизонтальной прокрутки; мобильная страница сохраняет действия. Локальный фокус принадлежит `useLocalRequestFocus`; pathname/h1 — App. Визуальное соответствие и фактический DOM-фокус принимает человек.

Переходы job → receipt → catalog product и receipt → job сохраняют корректный внутренний источник в History state. Видны «К заданию»/«К чеку»; query товара и reload сохраняют возврат. Back/Forward восстанавливают прежние записи истории. При прямом входе контекста нет, доступны списки/каталог. Контекст списка чеков/заданий сохраняет фильтры; App восстанавливает фокус ссылки списка после локального возврата. Контекст не передаётся новой вкладке; её поведение — прямой вход.

Новый CLI [check_recognition_proxy.mjs](../frontend/scripts/check_recognition_proxy.mjs) запускает настоящий Vite dev/preview и свои `recognition_worker --once` с fake, загружает demo через proxy, использует те же исходные адаптеры/runtime guards через Vite SSR loader. Node явно переносит QA CSRF cookie и Origin: это проверяет HTTP transport, но не browser cookie policy/React. Нужен отдельный пустой QA DB/project и Django с тем же env/MEDIA, без внешнего OCR-worker; preview требует build. Скрипт отказывается от dev ports/DB, внешних origins и Codex provider. Проверяет 202, client polling/его остановку, PNG MEDIA и исходные байты, 2 чека/6 строк/5 товаров, replay, queued/running cancel, retry/409, новое фото того же Receipt без новых строк/товаров, needs_review и 403/400. После прогона закрывает свои Vite/таймеры/воркеры, оператор останавливает Django/Compose. [Команды, результаты и ручная приёмка](verification.md#распознавание-сквозная-проверка-клиента-и5), [краткий показ](../frontend/I5_ACCEPTANCE.md).

Это единое локальное пространство DEBUG + ALLOW_LOCAL_RECOGNITION_API + loopback, без пользовательского доступа. Fake распознаёт фиксированные DTO, качество OCR произвольных фото не подтверждено. Автоматической очистки MEDIA/заданий нет; успешный job не retryable, точный повтор возвращает последний job. Уже сохранённые части cancel не удаляет. Возможное ложное объединение по точному store/time/total и stale admin POST при параллельном OCR остаются ограничениями v1.

### Сгруппированные замечания распознавания

Карточка вырезки в задании (`features/recognition/ReceiptImages.tsx`) и блок фото в чеке (`features/receipts/ReceiptContent.tsx`) выводят issues одним компонентом `components/RecognitionIssues.tsx` (props `issues`, `status`). Вся логика — чистые функции `lib/recognition-issues.ts`, стили — `.rec-issues*` в `App.css`. Компонент не делает запросов, не хранит состояние и не имеет live-областей. Серверный `message`, имена и значения закрытых реквизитов не выводятся: текст собирается только из словарей клиента и целых чисел контекста.

**Контракт и guard.** Сервер отдаёт у каждого issue `reason`, `severity`, `context {entity, index, position, attribute}` ([api-contract.md](api-contract.md#issues-вырезки-reason-severity-context)). `isRecognitionIssue` в `api/recognition-schema.ts`:

| Ответ | Поведение |
| --- | --- |
| нет ни одного из трёх ключей | принят как ответ старого сервера |
| есть часть ключей, неверный тип, `severity` вне `info`/`warning`/`error`, `index` вне 0..9999, `position` вне 1..32767 | весь ответ отклонён, `invalid_response` |
| `reason` вида `^[a-z_]{1,64}$` не из словаря; `entity`/`attribute` вида `^[a-z_]{1,32}$` вне перечня | принят, показывается как `unknown`, само имя не выводится |

Правила `code`/`field`/`message` прежние. `attribute` и `index`/`position` могут быть `null`.

**Fallback для старого ответа** (`issueView`): `reason = code`; `severity = error` при статусе вырезки `needs_review`/`failed`, иначе `warning`; `entity`/`index`/`attribute` — `fieldContext(field)`, тот же разбор, что `issue_context` на сервере (включая закрытые подпути: `/lines/N/product_hint…` → строка/товар, прочее `/lines/N/…` → строка/unknown, закрытые `/discounts/N/…`, `/taxes/N/…` и шапка → `receipt_metadata`); `position = null`. Для `code=invalid_value` подпись — «Замечание распознавания»: старый сервер прячет под этим кодом любые причины. Особые заголовки НДС/итогов/реквизитов старому ответу недоступны — причины в нём нет.

**Группировка** (`groupIssues`): ключ `(severity, reason, entity, attribute)`; порядок блоков error → warning → info. Внутри блока порядок не зависит от порядка issues в ответе сервера (контракт его не задаёт): сначала три группы `optional_omitted` в фиксированном порядке — ставки строк (строка + `tax_rate`), налоговые итоги (налог), реквизиты (`receipt_metadata`), — затем остальные группы по первому вхождению.

| Группа | Заголовок (формы 1 / 2–4 / 5+, 11–14 — третья) | Пояснение |
| --- | --- | --- |
| `optional_omitted` + строка + `tax_rate`, у всех есть index | «НДС не использован в {n} строке / строках» | «Распознавание не подтвердило чтение ставки, поэтому ставка не сохранена. Остальные данные строк сохранены.» |
| `optional_omitted` + налог, у всех есть index | «Пропущен 1 налоговый итог» / «Пропущены 2 налоговых итога» / «Пропущено 5 налоговых итогов» | «Налоговый итог не сохранён: ставка не подтверждена или суммы не сходятся.» |
| `optional_omitted` + `receipt_metadata` | «Не прочитан 1 реквизит» / «Не прочитаны 2 реквизита» / «Не прочитано 5 реквизитов» | «Необязательные реквизиты чека не прочитаны уверенно и не сохранены. Значения не показываются.» |
| остальное | «{подпись причины}», затем « · {подпись области}», если она есть, и « ({n})» при n > 1 | нет |

Подпись области — `areaLabels[attribute]`, иначе по сущности: «Строки», «Налоги», «Скидки», «Границы чека»; `receipt_metadata` → «Реквизиты чека». Перечень под пояснением: «Строки: 1, 2, 3» по `position`; без `position` — «Строки распознавания №: 4, 7» (index + 1); «Налоговые итоги №: 1, 2»; для скидок — «Скидки: …» / «Скидки распознавания №: …». Номера без повторов, по возрастанию.

**Разметка.** Блок error — всегда видимый список под `h4` «Причины проверки» (для `failed` — «Причины ошибки»), с перечнем строк под причиной. Warning и info — под `h4` «Замечания распознавания»: каждая группа — нативный `<details><summary>`, свёрнутый по умолчанию; клавиатура штатная (Tab до summary, Enter/Space). Группа без пояснения и перечня (например, «Тип операции определён автоматически · Операция») выводится обычной строкой: раскрывать в ней нечего. Блок «Распознанные данные для проверки» у `needs_review` не изменён; формы подтверждения нет. Summary не ниже 44 px, с видимым focus-visible; длинные тексты переносятся.

**Автопроверки** (Vitest, Node/SSR, без браузера): guard — `api/recognition-schema.test.ts`; разбор `field`, плюралы 1/2/5/11/21/25, группы 25 + 2 + 2 из ответа в порядке настоящего сервера (2 реквизита, 25 ставок, 2 итога), порядок групп при перемешанном ответе и с посторонней группой между известными, fallback, `position` вместо index + 1 — `lib/recognition-issues.test.ts`; разметка обоих экранов, отделение error, отсутствие `message` — `recognition-markup.test.tsx`, `receipts-markup.test.tsx`. Они не подтверждают вид, фокус и поведение `<details>` в браузере.

## Health-экран

Health-страница React 19, TypeScript и Vite на русском языке показывает состояние настоящего анонимного `GET /api/health/`: API, базы данных, Redis и Celery. На этой технической странице бизнес-данные не выводятся; каталог и история доступны на отдельных маршрутах выше. Заглушек и пользовательского входа в SPA нет. Контракт принадлежит backend: [api-contract.md](api-contract.md).

Компонент `src/pages/HealthPage.tsx` владеет состоянием технической страницы и кнопкой повтора, `src/api/health.ts` — запросом и runtime-проверкой JSON. Перенос из App сохраняет state/effect, AbortController, generation guard, словари статусов и повтор. Навигация реализована локально, глобальное состояние, UI-библиотеки, внешние шрифты и изображения не используются.

| Состояние | Поведение страницы |
| --- | --- |
| Открытие / повтор | «Проверяем соединение…», четыре строки проверки, «Повторить» disabled |
| Валидный 200 | «Соединение установлено», API отвечает, три сервиса доступны |
| Валидный 503 | «Некоторые сервисы недоступны», API отвечает, все checks сохранены |
| Ошибка сети | Понятное сообщение о соединении, состояния зависимостей неизвестны, повтор доступен |
| Таймаут 15 секунд | Сообщение об истёкшем ожидании, повтор доступен |
| 500 / протокольная ошибка | Безопасное сообщение, повтор доступен |
| Невалидный JSON / схема / пара HTTP–тело | Сообщение о некорректном ответе, повтор доступен |

Коды отказов переводятся в тексты: `database_unavailable` — «База данных недоступна», `redis_unavailable` — «Кеш недоступен», `broker_unavailable` — «Очередь задач недоступна», `worker_unavailable` — «Обработчик задач не отвечает». Серверные сообщения и исключения напрямую в UI не выводятся.

Повтор сбрасывает предыдущий результат и делает новый реальный запрос. Во время запроса кнопка недоступна. Замена запроса и unmount отменяют предыдущий AbortController; проверка поколения запроса и сигнала предотвращает запись устаревшего результата, включая повторный запуск эффекта в StrictMode. Таймаут охватывает fetch и чтение тела, timer и внешний abort-listener удаляются при завершении. Отмена отличается от ошибки сети и таймаута.

Статусы выражены текстом, сводка использует `aria-live="polite"`. Кнопка имеет видимый клавиатурный фокус. CSS резервирует высоту сводки и строк при загрузке, предусматривает узкий экран и перенос длинных сообщений. Анимаций нет. Фактическая визуальная, клавиатурная и интерактивная приёмка остаётся за человеком.

## Scripts, адрес API и proxy

| Script | Команда / назначение |
| --- | --- |
| `dev` | `vite` — локальная разработка |
| `build` | `tsc -b && vite build` — проверка типов и сборка в `dist/` |
| `lint` | `eslint . --max-warnings=0` |
| `test` | `vitest run` — адаптер, Node environment, mocked fetch |
| `preview` | `vite preview` — локальный просмотр собранного приложения |

Vite читает единый корневой `.env` (`envDir` — корень репозитория), process environment имеет приоритет. Создать файл из `.env.example`, если его ещё нет; существующий не перезаписывать. Дополнительный `.env` внутри `frontend/` не требуется.

Адаптер берёт `import.meta.env.VITE_API_BASE_URL || "/api"`, убирает лишние завершающие и повторяющиеся слэши пути, добавляет `/health/`. Запрос передаёт `Accept: application/json`, `credentials: "omit"`, `cache: "no-store"`. По умолчанию браузер запрашивает `/api/health/` на своём origin.

Dev и preview слушают **127.0.0.1:5173**, `strictPort: true`: занятый порт приводит к ошибке, а не тихому выбору другого. В QA порт задаётся аргументом `--port 15173`. Proxy `/api` направляет запрос на `DEV_API_PROXY_TARGET` (default `http://127.0.0.1:8000`) **без переписывания пути**. Например, `http://127.0.0.1:15173/api/health/` → `http://127.0.0.1:18000/api/health/`.

`DEV_API_PROXY_TARGET` используется только Node-конфигурацией Vite. `envPrefix: []` выключает автоматическую передачу пользовательских env-переменных; через `define` передаётся только `VITE_API_BASE_URL`. Общий env-объект, DB-реквизиты и секреты не прокидываются в браузер. `VITE_API_BASE_URL` публичен и не должен содержать секреты. После изменения env перезапустить Vite; публичный адрес фиксируется при build, для preview после его изменения нужна новая сборка. Произвольный внешний origin/CORS не проверен; результаты и ограничения проверки — в [verification.md](verification.md).

При остановленном API Vite 8.3.2 возвращает пустой HTTP **502**, хотя браузер по-прежнему достигает самого Vite. Адаптер трактует не-JSON 502/504 как ошибку соединения. Валидный health 503 обрабатывается отдельно с сохранением checks.

Для просмотра сборки при работающем QA API и применённых QA overrides:

```powershell
Set-Location frontend
npm.cmd run build
npm.cmd run preview -- --port 15173
```

Предварительно остановить dev-сервер на этом порту. Preview — локальный инструмент приёмки; production reverse proxy, hosting и deployment не настроены.

## Ручная приёмка каталога человеком

Автоматический обход browser UI запрещён. Ниже сценарий §6 ответа `task_mutu93ml5l`, для доступного QA API и расширенных синтетических данных. Скриншоты и визуальные результаты в F5 не создавались. Настоящий интерфейс доступен человеку локально через команды выше; автономного макета с подставными данными нет.

1. На `http://127.0.0.1:15173/catalog` пройти дерево → категорию (включая родителя с товарами потомков) → список → Product → историю и сводку. Сверить значения с QA API, включая RU `130.5882 RUB/л` и DE `normalized=null`. Проверить поиск по имени/бренду/модели/GTIN, generic, страницы и сброс. В истории применить точку/страну/валюту/локальный период; сводка охватывает всё окно, а не страницу.
2. Скопировать URL категории и товара с query, открыть напрямую и reload. Back/Forward и «Назад к списку» восстанавливают `q`, `generic`, page; direct-entry товара имеет выход в категорию. Проверить неверный ID пути/неизвестный ID/неверный диапазон/page вне набора — безопасные разные сообщения и сброс/первая страница. При возврате проверить фокус выбранного товара после загрузки; с Slow network перевести фокус в форму до ответа и убедиться, что App его не перехватывает. Если товара больше нет, заголовок остаётся доступен.
