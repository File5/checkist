# Редизайн клиента — ручная приёмка

Клиент переведён с зелёной схемы на красную с золотом: тёмная тема по умолчанию, светлая по переключателю, логотип «ЧЕКИСТ — продуктовая разведка», экран входа в том же оформлении. После слияния с разделением пользователей (2026-10-08) вход настоящий: сессия Django, имя пользователя в шапке, страница `/account`; адрес `/login` рисует тот же экран входа без оболочки. Описание — [docs/frontend.md](../docs/frontend.md#тема-бренд-и-экран-входа), токены — `frontend/src/theme/tokens.css`.

**Интерфейс в браузере агент не открывал**: автоматический обход UI в проекте запрещён, скриншотов нет. Всё, что ниже, проверяет человек глазами, клавиатурой и экранным диктором. Автоматически проверены только lint, тесты в Node, сборка и текстовый поиск по исходникам ([результаты слитой ветки](../docs/verification.md#фактические-результаты-редизайн-клиента-слияние-с-разделением-пользователей-м4-2026-10-08)); серверы при этом не запускались.

## Запуск

Запуск — по [docs/development.md](../docs/development.md), только в QA, не на dev-базе. Режимов сервера два, и сценарии делятся между ними:

| Режим | Сценарии | База |
| --- | --- | --- |
| `local_single` — без входа, как раньше | 1–5, 7–11 | `checkist_qa` с демо из раздела «Данные» |
| `accounts` — вход по имени и паролю | 6 и повтор шагов шапки из 7, 8 и 11 | отдельная **пустая** `checkist_qa_accounts`, см. [запуск со входом](#запуск-со-входом-accounts) |

### Запуск без входа (`local_single`)

В **каждом** терминале PowerShell из корня репозитория сначала весь блок окружения из [verification.md](../docs/verification.md#изолированная-qa-среда) (база `checkist_qa`, Postgres 25432, Redis 16379, API 18000, Vite 15173, `CHECKIST_AUTH_MODE=local_single` — без этой строки сервер работает в `accounts` и клиент покажет вход), затем:

```powershell
$env:CHECKIST_AUTH_MODE='local_single'
$env:DJANGO_DEBUG='1'
$env:ALLOW_LOCAL_RECOGNITION_API='1'
$env:RECEIPT_OCR_PROVIDER='fake'            # с codex_cli воркер делает настоящие модельные запросы
$env:PRODUCT_MERGE_AUTO_DETECT='0'
$env:PRODUCT_CLASSIFICATION_AUTO_SUGGEST='0'
$env:DJANGO_CSRF_TRUSTED_ORIGINS='http://127.0.0.1:15173,http://localhost:15173'
$env:MEDIA_ROOT=Join-Path $env:TEMP 'checkist-qa-recognition-media'
$env:RECEIPT_OCR_TEMP_ROOT=Join-Path $env:TEMP 'checkist-qa-recognition-scratch'
```

Терминал 1 — сервер с данными (см. «Данные» ниже), затем `./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py runserver 127.0.0.1:18000 --noreload`.

Терминал 2 — клиент, **в PowerShell** (Git Bash переписывает `VITE_API_BASE_URL=/api` в путь Windows):

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd run dev -- --port 15173
# собранное приложение: npm.cmd run build; npm.cmd run preview -- --port 15173
```

Открыть `http://127.0.0.1:15173/`. Без сервера клиент не знает режима и вместо экранов показывает «Вход не проверен» с кнопкой «Повторить» (кроме `/health`): сценарии смотреть только с запущенным Django. Сценарий 2 (вспышка) и 10 (значок) повторить на собранном приложении (`preview`). После приёмки остановить Vite и Django, `docker compose -p checkist_qa down` без `-v`.

### Запуск со входом (`accounts`)

Нужна **пустая** база: `seed_accounts_demo` отказывает, если в ней уже есть товары, чеки, фото или группы слияния. Отдельный Compose-проект со своими портами, чтобы не трогать `checkist_qa`. PowerShell из корня репозитория; `.env` и `backend/.venv` подготовлены по [docs/development.md](../docs/development.md). В **каждом** терминале — весь блок:

```powershell
$env:COMPOSE_PROJECT_NAME = "checkist_qa_accounts"
$env:POSTGRES_DB = "checkist_qa_accounts"
$env:POSTGRES_HOST = "127.0.0.1"
$env:POSTGRES_PORT = "25433"
$env:REDIS_PORT = "16380"
$env:CELERY_BROKER_URL = "redis://127.0.0.1:16380/0"
$env:CELERY_RESULT_BACKEND = "redis://127.0.0.1:16380/1"
$env:DJANGO_CACHE_URL = "redis://127.0.0.1:16380/2"
$env:VITE_API_BASE_URL = "/api"
$env:DEV_API_PROXY_TARGET = "http://127.0.0.1:18001"
$env:DJANGO_DEBUG = "1"
$env:CHECKIST_AUTH_MODE = "accounts"
$env:RECEIPT_OCR_PROVIDER = "fake"            # с codex_cli воркер делает настоящие модельные запросы
$env:PRODUCT_MERGE_AUTO_DETECT = "0"
$env:PRODUCT_CLASSIFICATION_AUTO_SUGGEST = "0"
$env:DJANGO_CSRF_TRUSTED_ORIGINS = "http://127.0.0.1:15174,http://localhost:15174"
$env:MEDIA_ROOT = Join-Path $env:TEMP "checkist-qa-accounts-media"
$env:RECEIPT_OCR_TEMP_ROOT = Join-Path $env:TEMP "checkist-qa-accounts-scratch"
# Пароли придумывает проверяющий: разные, не короче 8 символов, не из одних цифр, не распространённые.
# В репозиторий, отчёт и журнал их не записывать.
$env:ACCOUNTS_DEMO_MODERATOR_PASSWORD = "<пароль demo_moderator>"
$env:ACCOUNTS_DEMO_USER_PASSWORD = "<пароль demo_user>"
```

`CHECKIST_AUTH_MODE` задаётся явно: в `.env` из образца стоит `local_single`, а переменная процесса выше файла. Origin Vite обязан быть в `DJANGO_CSRF_TRUSTED_ORIGINS`, иначе вход ответит «Токен безопасности устарел…» (`403 csrf_failed`).

Терминал 1 — сервер и **учётные записи для проверки**:

```powershell
docker compose -p checkist_qa_accounts up -d --wait --wait-timeout 90 postgres redis
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py migrate --noinput
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py seed_accounts_demo --moderator-password $env:ACCOUNTS_DEMO_MODERATOR_PASSWORD --user-password $env:ACCOUNTS_DEMO_USER_PASSWORD | Out-File -Encoding utf8 (Join-Path $env:TEMP "checkist-accounts-demo.json")
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py runserver 127.0.0.1:18001 --noreload
```

`seed_accounts_demo` заводит двух пользователей — `demo_moderator` (право модератора каталога) и `demo_user` (без него) — с паролями из переменных выше и по одному чеку у каждого; данные описаны в `src/features/auth/ACCEPTANCE.md`. Другие способы завести пользователя, если демо не нужно (обе команды интерактивные, пароль проверяют четыре правила Django):

- `./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py createsuperuser` — оператор со всеми правами и входом в `/admin/`; остальных пользователей он заводит в `http://127.0.0.1:18001/admin/` → Users, право модератора — `catalog | product | Can moderate the shared catalog`;
- `./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py changepassword local` — пароль служебному пользователю `local`, которому миграции отдали прежние чеки (на базе с данными вместо пустой).

Терминал 2 — клиент, в PowerShell с тем же блоком:

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd run dev -- --port 15174
# собранное приложение: npm.cmd run build; npm.cmd run preview -- --port 15174
```

Открыть `http://127.0.0.1:15174/`. Срок блокировки входа после пяти неверных паролей — 900 секунд; для проверки его сокращают `$env:AUTH_LOGIN_LOCK_SECONDS = "60"` в терминале сервера до запуска. После приёмки остановить свои `runserver` и Vite, затем `docker compose -p checkist_qa_accounts down` без `-v`.

| Экраны | Данные | Где описано |

| Загрузка, обработка, задание с вырезкой «Требует проверки» | `seed_recognition_demo`, загрузить `MEDIA\demo\double.png` на `/receipts/upload`, затем `recognition_worker --once --fake-scenario partial_success` | `src/features/recognition/ACCEPTANCE.md` |

Демо статистики ставится первым. Совмещение всех четырёх демо в одной базе агентом не проверялось (сервер в этой задаче не запускался): если команда демо отказывает из-за совпадения названий, взять для этой функции отдельный проект Compose с новым томом, как в её приёмке.

## Что считать дефектом

- Текст, который трудно прочитать; красный текст в тёмной теме; золотой текст на светлой «бумаге».
- Остаток прежнего оформления: зелёная кнопка, ссылка или рамка (зелёным остаётся только «успех»), белая панель или белое поле в тёмной теме.
- Поле, список, календарь или полоса прокрутки системного светлого цвета в тёмной теме (и наоборот).
- Ошибка, которую от красной кнопки отличает только цвет.
- Сдвиг раскладки, обрезанный текст или горизонтальная прокрутка страницы, которых до редизайна не было: геометрия экранов не менялась.

## Сценарии

### 1. Первый заход

1. Очистить данные сайта (DevTools → Application → Storage → Clear site data) либо открыть окно инкогнито. Открыть `/`.
2. Тема тёмная: почти чёрный фон, тёплый светлый текст. Каталог работает: поиск, категории, список товаров, пагинация.
3. Шапка — тёмная полоса во всю ширину окна с золотой и красной линией снизу. В ней слева эмблема (меч с чеком на красном щите) и «ЧЕКИСТ» прописными, справа кнопка «Тема: тёмная», ниже пять разделов: «Каталог», «Чеки», «Статистика», «Обработка», «Состояние сервисов». Текущий раздел золотой, со звёздочкой перед названием. Ссылки «Войти», имени пользователя и «Аккаунт» в режиме без входа нет (со входом — сценарий 6).
4. Эмблема в шапке — без фона и без надписи: красная звезда, лучи, меч, красный щит с белым чеком и штрихкодом, золотые колосья, красная лента. Вокруг неё нет ни тёмного квадрата, ни рамки, ни скруглённой подложки — сквозь поля картинки виден цвет полосы шапки; слов «ЧЕКИСТ» и «продуктовая разведка» на самой картинке нет (надпись «ЧЕКИСТ» рядом — текст ссылки). Переключить тему на светлую: шапка остаётся тёмной, эмблема выглядит так же. Края рисунка ровные, без светлой или цветной каймы; пропорции не искажены (эмблема чуть выше, чем шире). При масштабе 200 % и на плотном экране картинка резкая. Тёмные просветы между колосьями и щитом — часть рисунка (в исходнике они чёрные), это не дефект.
5. Над заголовком экрана строка «Доверяй, но проверяй чек», в подвале — «Чекист · Продуктовая разведка · Совершенно несекретно».

### 2. Светлая тема

1. Нажать «Тема: тёмная». Страница сразу становится светлой («бумажный» фон, тёмный текст), без перезагрузки и без мигания; подпись кнопки — «Тема: светлая», фокус остаётся на кнопке. Шапка осталась тёмной.
2. Перезагрузить страницу (F5 и Ctrl+F5): светлая тема на месте, тёмной вспышки перед отрисовкой нет.
3. То же на медленной сети: DevTools → Network → Slow 3G (либо Slow 4G), отключить кэш, перезагрузить. Пока грузятся скрипты, фон уже светлый; заголовки могут сначала показаться системным шрифтом и смениться на узкий Oswald — это допустимо.
4. Открыть приложение во второй вкладке, переключить тему в первой — вторая меняется без перезагрузки.
5. Application → Local Storage: ключ `checkist.theme` со значением `light` либо `dark`; других ключей приложение не пишет.
6. Вернуть тёмную тему, перезагрузить — тёмная.

### 3. Обход экранов в обеих темах

Каждый экран открыть в тёмной и в светлой теме. Смотреть: текст читается, нет зелёных остатков и белых панелей в тёмной теме, поля ввода, выпадающие списки, календарь выбора даты и полосы прокрутки — в цвете темы.

| № | Экран | Адрес | Обратить внимание |
| --- | --- | --- | --- |

| 2 | Категория | `/catalog/categories/1` | то же, ссылка возврата |
| 3 | Товар с графиком цен | `/catalog/products/1` | фильтры (списки, календарь), таблица истории, сводка, блок «График цен» |

### 4. Состояния

В обеих темах:

1. **Ошибка.** Остановить Django и открыть `/catalog`, `/receipts`, `/stats`: панели ошибки с текстом и кнопкой «Повторить». Отказ подтверждения вырезки (шаг 3 приёмки `src/features/recognition/ACCEPTANCE.md`, сценарий воркера `inconsistent_total`) — плашка отказа над кнопкой, у поля «Итого» рамка и текст ошибки. Текст ошибки — коралловый в тёмной теме и малиновый в светлой; он отличим от красных кнопок **не только цветом**: у ошибки есть текст сообщения, рамка или полоса слева, у кнопки — белая подпись на сплошной красной заливке.
2. **Предупреждение** — оранжевое, не золотое: «Есть данные, требующие проверки…» в задании, сообщение о воркере на странице задания и на `/catalog/classification` при остановленном воркере, `/health` при остановленном Redis или Celery («Некоторые сервисы недоступны»).
3. **Успех** — зелёный и только он: «Подтверждено. Чек №… сохранён.» после подтверждения вырезки, статусы «Завершено» и «Подтверждено», `/health` при работающих сервисах.
4. **«Требует подтверждения»** — пометки в каталоге, карточке товара и на `/catalog/classification`; «в процессе» и нейтральные статусы — серо-бежевые, сведения — синие.
5. **Недоступная кнопка** (например, «Повторить» во время запроса) читается и не выглядит как активная.
6. **Контурные кнопки** («Отклонить» и «Выбрать другой» на `/catalog/classification`, «Отменить слияние» в группе дублей, «Удалить строку …» в форме вырезки, «Сбросить фильтры» и «Повторить» на экранах статистики, «Сбросить фильтры» в поиске каталога): фон панели, текст цвета ссылки, рамка видна в обеих темах. Навести мышь и нажать (мышью и клавишей Space): кнопка остаётся контурной, фон чуть светлее либо темнее панели, красной заливки под текстом не появляется ни на миг. Главные кнопки при наведении и нажатии темнеют. Отдельного вида опасного действия нет: «Отклонить» и «Удалить …» выглядят как остальные контурные кнопки.
7. **Залитая кнопка-ссылка** «Загрузить фото» на `/receipts` (красная заливка, белая подпись; рядом контурная «Обработка»). В тёмной и в светлой теме навести мышь, нажать и удерживать, дойти клавишей Tab: подпись остаётся белой и читается, заливка при наведении темнеет, при нажатии темнеет ещё, рамка того же цвета, что заливка; при фокусе — кольцо фокуса вокруг, подпись прежняя. Золотой либо тёмно-красной подписи на красном быть не должно. Соседняя «Обработка» и остальные контурные кнопки-ссылки («К чекам», «В каталог», «Сбросить фильтры») при наведении меняют только цвет текста и рамки (в тёмной теме — светлее, в светлой — темнее), заливки не получают.

### 5. Графики

В обеих темах, на демо статистики:

1. `/stats` с разбивкой, где долей не меньше восьми (на демо — по товарам либо по обобщённым продуктам): восемь серий различимы между собой и с «Прочее»; несопоставленное показано штриховкой. Если на данных серий меньше восьми — записать, сколько было.
2. Навести на долю и на строку легенды: подсветка видна, подсказка читается (текст на подложке, рамка, тень), не уходит за край.
3. `/stats/receipts`: линии графика и сетка видны, подсказка у правого края не обрезана, метки слагаемых в таблице различимы.
4. `/catalog/products/1`, «График цен»: серии магазинов и похожих товаров различимы, легенда и «Таблица значений» читаются.
5. Светлая тема: бирюзовая, жёлтая и розовая серии бледнее остальных (контраст с панелью ниже 3:1 — это известно и записано в `tokens.css`); проверить, что по подписям, легенде и таблице их всё равно можно различить.
6. Клавиатура: Tab доходит до ссылок легенды круговой диаграммы, до поля линейного графика (стрелки двигают выделение), до «Таблицы значений»; кольцо фокуса видно в обеих темах.

### 6. Вход, сессия и «Аккаунт»

Сервер и клиент — по разделу [«Запуск со входом»](#запуск-со-входом-accounts) (`CHECKIST_AUTH_MODE=accounts`, адрес `http://127.0.0.1:15174/`, пользователи `demo_moderator` и `demo_user`). **Каждый шаг пройти дважды — в тёмной и в светлой теме**; шаги 6.1, 6.2, 6.7 и 6.8 — ещё и на ширине 375 и 320 px. Здесь — оформление и состояния; разделение данных двух пользователей (чужой чек, «моя / чужая» покупка, разделы модератора) — в `src/features/auth/ACCEPTANCE.md`.

**6.1. Экран входа.** Окно инкогнито, 1280 px.

1. Открыть `/catalog/products/1?date_from=2026-09-01`: экран без шапки, меню, подвала и строки «Доверяй, но проверяй чек» — слева большой логотип на тёмной доске с золотой рамкой и лучами, справа заголовок «ВХОД», «Продуктовая разведка», линия со звездой, «Предъявите пропуск», поля «Имя пользователя» и «Пароль», красная кнопка «Войти» во всю ширину формы, «Пропуска выдаёт администратор», кнопка темы. Адрес в строке браузера не изменился, заголовок вкладки — «Чекист — Вход».
2. Открыть `/login`: тот же экран, тоже без оболочки.
3. Переключить тему кнопкой на экране входа: оформление меняется сразу, фокус остаётся на кнопке. В светлой теме доска с логотипом по-прежнему тёмная, вокруг логотипа не виден квадрат картинки, подписи и рамки полей читаются.
4. Tab с начала страницы: имя пользователя → пароль → «Войти» → тема, других остановок нет; кольцо фокуса видно на каждой.

**6.2. Кнопки входа: наведение и нажатие.**

1. «Войти»: навести — заливка темнеет, нажать и удерживать — темнеет ещё, подпись остаётся белой; золотой либо тёмно-красной подписи на красном нет.
2. DevTools → Network → Slow 3G, ввести имя и пароль, «Войти»: подпись «Входим…», кнопка серая; под указателем, при нажатии и при повторном Enter остаётся серой, второго запроса `auth/login/` в Network нет, фокус на кнопке.
3. Кнопка темы на экране входа: наведение и нажатие меняют фон, подпись читается.

**6.3. Отказы входа.**

1. Пустые поля, «Войти»: «Введите имя пользователя и пароль.» с полосой слева, у обоих полей рамка толще; запроса в Network нет.
2. `demo_moderator` и неверный пароль (**один раз**: пять подряд блокируют вход на 15 минут): «Неверное имя пользователя или пароль.» один раз у кнопки, поля не очищены, адрес прежний. Текст отказа отличим от красной кнопки не только цветом — у него полоса слева.
3. **Ошибка сети.** DevTools → Network → Offline, «Войти»: «Нет ответа сервера. Проверьте соединение и повторите вход.»; сам запрос не повторяется. Вернуть Online — вход проходит только новым нажатием.
4. **Сервер остановлен при открытии.** Остановить `runserver`, перезагрузить страницу: оболочка с шапкой и заголовком «Вход не проверен», «Не удалось проверить вход. Проверьте соединение и повторите попытку.» и кнопка «Повторить». В меню при этом только «Состояние сервисов». Запустить сервер, «Повторить» — открывается вход.
5. Сообщения «Вход пока не подключён» нет ни в одном из состояний.

**6.4. Успешный вход.**

1. На адресе `/catalog/products/1?date_from=2026-09-01` войти как `demo_moderator`: открылась карточка товара с тем же фильтром, фокус на заголовке страницы, тема та же, что была на экране входа.
2. Шапка: пять разделов и справа от них имя `demo_moderator` — ссылка цвета текста шапки, читается на тёмной полосе в обеих темах; при наведении — подложка, как у разделов. Ссылки «Войти» нет.
3. Back не возвращает на экран входа; перезагрузка оставляет пользователя вошедшим.
4. Выйти (шаг 6.7), открыть `/login`, войти: открылся каталог (`/catalog`), Back не возвращает на `/login`. Вошедшим открыть `/login` вручную — сразу каталог.

**6.5. «Аккаунт».** Нажать имя в шапке.

1. `/account`: заголовок «Аккаунт», имя в шапке отмечено как текущий раздел; две карточки на поверхности панели с рамкой — «Пользователь» (имя, контурная кнопка «Выйти») и «Смена пароля» (три поля, серый список четырёх правил, красная кнопка «Сменить пароль» с белой подписью).
2. «Выйти» — навести и нажать, не отпуская (чтобы не выйти, увести указатель с кнопки до отпускания; с клавиатуры — Tab до кнопки): фон чуть меняется, текст и рамка видны, красной заливки под текстом нет ни на миг.
3. «Сменить пароль» — наведение и нажатие: заливка темнеет, подпись белая.
4. Неверный текущий пароль: «Текущий пароль неверный.» с полосой слева, поле с толстой рамкой. Новый пароль `12345678`: «Новый пароль не подходит. Пароль:» и нарушенные правила списком. Несовпадающий повтор: «Новый пароль и его повтор не совпадают.» без запроса.
5. Перед верной сменой войти тем же пользователем во втором окне (другой профиль либо инкогнито) — оно понадобится в шаге 6.6. Сменить пароль: «Пароль изменён. Вход на других устройствах завершён.» зелёным, поля очищены, окно осталось вошедшим.
6. Slow 3G: «Сохраняем…» и «Выходим…» серые и остаются серыми под указателем и при нажатии.

**6.6. Истёкшая сессия.**

1. Во втором окне из шага 6.5.5 перейти в другой раздел либо перезагрузить страницу: вместо страницы — экран входа без оболочки с плашкой «Сеанс завершён. Войдите снова.» над формой (оранжевое предупреждение с рамкой, не ошибка); читается в обеих темах. Данных прежней страницы на экране нет.
2. Старый пароль не подходит, новый подходит; после входа открыта страница того же адреса.
3. Без второго окна то же состояние даёт удаление cookie: вошедшим открыть DevTools → Application → Cookies, удалить `sessionid`, перейти в другой раздел.

**6.7. Выход.**

1. `/account` → «Выйти»: открылся экран входа **без** плашки про завершённый сеанс, фокус на заголовке «Вход».
2. Открыть `/health`: оболочка гостя — в меню только «Состояние сервисов» и «Войти»; «Каталог», «Чеки», «Статистика», «Обработка» и имени нет. «Войти» ведёт на `/login`. Навести на «Войти» — подложка, как у разделов; кольцо фокуса золотое.
3. Вторая вкладка, открытая до выхода на `/receipts`: при возврате на неё вместо списка чеков — вход.

**6.8. Узкий экран.** Ширина 768, 375 и 320 px, масштаб 200 %, обе темы.

1. Экран входа: на 768 px две колонки; уже 720 px — логотип сверху (не выше трети окна), форма под ним, кнопка «Войти» во всю ширину, горизонтальной прокрутки нет, плашка «Сеанс завершён…» и отказ не шире экрана.
2. `/account`: карточки не шире экрана, кнопки во всю ширину, поля и кнопки не ниже 44 px.
3. Шапка вошедшего: разделы и имя идут одной строкой с прокруткой вбок; длинное имя переносится, а не раздвигает страницу; на `/account` имя видно без прокрутки меню — в том числе сразу после перезагрузки страницы и после входа гостем с этого адреса (то же для «Обработки» на `/recognition/jobs` и «Состояния сервисов» на `/health`). Шапка гостя на `/health`: «Состояние сервисов» и «Войти» помещаются.

**6.9. Режим без входа.** Сервер `local_single` (раздел [«Запуск без входа»](#запуск-без-входа-local_single)): экрана входа, «Войти», имени и «Аккаунта» нет; `/login` и `/account` — «Страница не найдена» в оболочке.

### 7. Узкий экран и масштаб

Ширина окна 320, 375 и 768 px (DevTools → режим устройства), затем обычное окно с масштабом 200 %. В обеих темах.

1. Шапка: на 320 и 375 px (высота окна не меньше 480 px) у переключателя темы видна только иконка, эмблема на месте; **разделов в шапке нет** — после мобильной адаптации они стоят нижней панелью «Каталог · Чеки · Статистика · Ещё» у низа окна, её проверка — [MOBILE_ACCEPTANCE.md](MOBILE_ACCEPTANCE.md), сценарий В (шаги 16–23) и шаг 49 на iPhone. Прежняя лента — разделы одной строкой в шапке с прокруткой вбок, текущий раздел виден без прокрутки — остаётся только в запасном режиме: окно у́же 300 px либо ниже 480 px (альбомная ориентация, масштаб 200 % на ширине телефона), там же шаг 22. На 768 px — подпись темы видна, разделы в строку в шапке, панели внизу нет. Шапка вошедшего и гостя — шаг 6.8.
2. Экраны из сценария 3 (не меньше: каталог, товар, чек, задание с формой, группа дублей, траты, средний чек): горизонтальной прокрутки страницы нет (допустима только внутри таблиц), кнопки не уезжают за край, длинные названия переносятся.
3. Экран входа и `/account` — шаг 6.8 (нужен сервер `accounts`).
4. Масштаб 200 %: всё доступно вертикальной прокруткой, текст не накладывается.

Глубокая мобильная переработка в этот редизайн не входила (см. «Мобильная переработка»): здесь проверяется только то, что узкий экран не стал хуже прежнего. Она сделана отдельной задачей 2026-10-09 — на телефоне (окно до 540 px) таблицы показаны карточками, а меню — нижней панелью; приёмка — [MOBILE_ACCEPTANCE.md](MOBILE_ACCEPTANCE.md).

### 8. Клавиатура

В обеих темах, без мыши.

1. С начала страницы Tab: «К содержимому» (появляется поверх шапки) → «Чекист» → переключатель темы → пять разделов → содержимое. Shift+Tab — обратно. В режиме `accounts` после разделов идёт имя пользователя (ссылка на `/account`), у гостя на `/health` — «Состояние сервисов» → «Войти».
2. Кольцо фокуса видно: на тёмной шапке (золотое в обеих темах), на красных кнопках (в светлой теме кольцо синее и держится с отступом от кнопки), на ссылках, полях, флажках и графиках.
3. Перейти в другой раздел клавишей Enter: фокус на заголовке экрана `h1`, кольцо вокруг заголовка видно. Смена только фильтра фокус из формы не забирает.
4. «К содержимому» переносит на заголовок экрана.
5. Переключатель темы: Enter и Space меняют тему, фокус остаётся на кнопке.
6. Локальный фокус прежних приёмок не сломан: «Повторить» в блоке (`R2_ACCEPTANCE.md`), форма вырезки (`src/features/recognition/ACCEPTANCE.md`).

### 9. «Уменьшить движение» и высокая контрастность

1. Windows → Специальные возможности → Визуальные эффекты → выключить «Эффекты анимации» (либо DevTools → Rendering → Emulate `prefers-reduced-motion: reduce`). `/stats`: подсветка долей и строк легенды меняется мгновенно. Другого движения в приложении нет ни с настройкой, ни без неё.
2. Windows → Специальные возможности → Контрастные темы → включить любую. Шапка, текущий раздел (подчёркнут, звёздочка видна), переключатель темы, экран входа (поля, кнопка, сообщение; лучи скрыты), графики — различимы, кольцо фокуса видно. Блоки `forced-colors` есть у оболочки, переключателя темы, экрана входа и графиков; остальные экраны полагаются на системные цвета, как и до редизайна — отметить, если где-то пропала граница поля или кнопки.

### 10. Значок вкладки и заголовок

1. Значок вкладки — красная звезда с золотой обводкой на тёмном скруглённом квадрате; виден в светлом и тёмном оформлении браузера.
2. Заголовок вкладки — «Чекист — Каталог продуктов» и меняется по экранам («Чекист — Чеки», «Чекист — Вход», «Чекист — Страница не найдена»).
3. Собранное приложение (`npm.cmd run build; npm.cmd run preview -- --port 15173`): значок и эмблема на месте — так проверяется, что файлы попали в сборку.
4. iPhone либо iPad, Safari → «Поделиться» → «На экран „Домой“»: значок — та же эмблема без надписи на почти чёрном квадрате, без прозрачных дыр (`apple-touch-icon.png` непрозрачный).
5. Мобильный браузер либо режим устройства: цвет панели браузера (`theme-color`) следует теме.

### 11. Экранный диктор

Экранный диктор Windows либо NVDA, одна тема (на чтение она не влияет).

1. Шапка: ссылка читается «Чекист — каталог», эмблема отдельно не читается; «Основная навигация» с пятью ссылками, текущая объявляется текущей страницей. В режиме `accounts` шестая ссылка читается «Аккаунт: <имя>», на `/account` она объявляется текущей.
2. Переключатель темы: кнопка «Тема: тёмная» / «Тема: светлая»; после нажатия новое название читается при повторном фокусе. На узком экране, где подпись скрыта, название то же.
3. Заголовок первого уровня на каждом экране один; после перехода диктор читает его.
4. Звёздочка текущего раздела, линии и декор не читаются.
5. Экран входа: логотип — «Чекист — продуктовая разведка», заголовок и область формы «Вход», поля «Имя пользователя» и «Пароль»; отказ у кнопки читается сам (`aria-live`), неверные поля объявляются как invalid. `/account`: области «Пользователь» и «Смена пароля», результат смены пароля и отказ выхода читаются сами.
6. Прежние объявления (`aria-live`, `role="status"`) работают как раньше: редизайн разметку экранов не менял.

## Известные ограничения

- Статические превью `frontend/*-preview/`, `src/features/merges/preview/` и `src/features/classification/preview/` — снимки **прежнего** зелёного оформления, не пересобирались. Превью экрана входа удалено вместе с заготовкой `features/login`.
- Системная настройка тёмной или светлой темы не учитывается: первый заход всегда тёмный.
- При строгой CSP на сервере встроенный скрипт темы в `index.html` нужно разрешить по хэшу либо вынести в файл ([docs/frontend.md](../docs/frontend.md#переключение-и-хранение)); сейчас CSP не настроена.
- Ироничных фраз на экране больше одной: строка над заголовком и подвал видны на каждом экране оболочки, на «Странице не найдена» к ним добавляется третья, на экране входа их три. Правило «не больше одной фразы на экран» выполнено не буквально — решение за человеком.
- Отдельного вида опасного действия нет: «Отклонить», «Отменить слияние», «Удалить …», а теперь и «Выйти» — обычные контурные кнопки (сценарий 4, шаг 6; шаг 6.5). **Открытый вопрос человеку:** нужен ли опасным кнопкам «Отклонить» и «Удалить …» свой вид (например, текст и рамка цвета ошибки) — токены `--ck-error-*` для этого есть, решение не принято, оформление не менялось.
- Параметра `next` у `/login` нет: вход с этого адреса всегда открывает каталог; вход на любом другом адресе оставляет на нём.
- Сервер в этой ветке не запускался: сценарий 6 на настоящей сессии агент не проходил ни в браузере, ни скриптом.

## Мобильная переработка

Глубокая мобильная переработка — карточный вид таблиц, закреплённые панели действий, загрузка с камеры, графики под палец, нижняя навигация — в редизайн не входила и сделана отдельной задачей 2026-10-09: [MOBILE_ACCEPTANCE.md](MOBILE_ACCEPTANCE.md).
