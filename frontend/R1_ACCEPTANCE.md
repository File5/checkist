# R1: различимые точки в истории цен

Исправлена потеря ID магазина в fallback. История, сводка и фильтр используют общий формат подписи:

- С адресом: `ID 51 · Same Chain · Example Street 51 · Berlin · DE`.
- Без адреса: `ID 51 · Same Chain · Berlin · DE · адрес неизвестен`.
- Пока известен только выбранный ID: `ID 51 · Не указано · адрес неизвестен`.

ID стоит первым, чтобы длинное название в native select не скрывало идентичность точки. Пустой адрес и адрес из пробелов считаются неизвестными. Известные название, город, страна и адрес сохраняются.

Сведения обогащаются по ID из карточки, просмотренных страниц справочника и успешной сводки `group_by=store`. Сводка уже содержит полные объекты магазинов, в том числе вне первых 50 карточки. Для подписи выбранного ID фильтр также использует краткие сведения текущей истории; набор вариантов выбора из истории не строится. При отказе справочника select недоступен с явным сообщением и локальным повтором; карточка, история, независимая сводка и возможность убрать выбранный магазин сохраняются.

API не даёт магазина по ID или фильтра списка по ID. Адресной дозагрузки и автоматического обхода всех страниц нет. Если имеющиеся ответы не содержат адрес, остаётся fallback с ID; поиск по названию/городу и страницы справочника позволяют получить сведения вручную. Новых запросов, зависимостей и изменений backend нет. `PriceHistory` и `PriceSummary` получили исправление через существующий общий `storeLabel`.

## Проверено и не прошло

До исправления `npm.cmd run test -- src/features/product/product-markup.test.tsx` — exit 1: три новых SSR-проверки упали, шесть прежних прошли. Воспроизведено совпадение двух `<th scope="row">`: обе подписи были `Same Chain · Berlin · DE`; также отсутствовали ID при отказе справочника и обогащение из сводки. Причина исправлена. Полный финальный прогон прошёл; тесты не отключались, ожидания не ослаблялись.

Служебные проверки: чтение `Get-Content -Encoding utf8 backend/api/views/reference.py` сообщило, что файла нет; правильный `backend/api/views/catalog.py` прочитан успешно. Первая PowerShell-проверка кодировки — exit 1 с ложным сообщением о BOM: `StartsWith([string][char]0xFEFF)` использовал культурное сравнение и игнорировал символ. Проверка первого декодированного символа по байтам исправила сам валидатор, повтор — exit 0; файлы были корректны.

## Не проверено и почему

- Визуальная и интерактивная приёмка, клавиатура, фокус, native select, screen reader, адаптив: по правилам проекта проверяет человек. Автоматического обхода UI и скриншотов нет. Передан этот Markdown с результатами и сценарием; отдельный статический макет не создавался.
- Настоящие HTTP/proxy и QA-набор из 52 точек не запускались: задача исправляет frontend-подписи; регрессия воспроизведена и проверена SSR/unit. Результаты предыдущего F6 не засчитываются как проверки R1.
- Build подтверждает типизацию и сборку, SSR — содержимое разметки с тестовыми состояниями. Они не подтверждают поведение React в браузере. Merge, publish и deployment не выполнялись.

## Ручная проверка человеком

1. Подготовить свободную изолированную QA по `docs/verification.md` и `docs/frontend.md`; применить полный QA environment в каждом терминале. API — `127.0.0.1:18000`, proxy target тот же, Vite — `15173`. При работающем QA API запустить из `frontend/` `npm.cmd run dev -- --port 15173`. Проверять только QA, без записи в dev/локальный Postgres.
2. На QA-товаре с известным адресом открыть `/catalog/products/<product-id>`. Сверить ID и адрес в истории, сводке и варианте фильтра с JSON API. Найти магазин по названию/городу, выбрать и применить: тот же ID узнаваем во всех блоках. Проверить прямую ссылку `?store=<store-id>`, reload и Back/Forward.
3. Для полного воспроизведения нужен вымышленный QA-товар с 52 наблюдениями в 52 магазинах: две точки одной сети/города/страны должны оказаться на второй странице истории и отсутствовать в `stores` карточки и первой просмотренной странице справочника. Это проверить по ответам API; фактические ID могут отличаться от 51/52 тестов. Открыть `?page=2`. В DevTools временно заблокировать только `*/prices/summary/*` и перезагрузить: две строки имеют разные видимые ID, одинаковые name/city/country и «адрес неизвестен». Карточка и история остаются. Снять блокировку, повторить сводку: реальные адреса появляются и в истории по ID, без запроса вымышленного `/stores/{id}/`.
4. Заблокировать только `*/api/stores/*` и перезагрузить. Карточка, строки истории и доступная сводка сохраняются; select отключён и подписан «Фильтр магазина недоступен», есть повтор. Известные адреса сохраняются. Дополнительно заблокировать сводку для двух неизвестных точек: история остаётся с различимыми ID и сообщением об адресе. Для прямого `?store=<id>` выбранная точка сохраняет ID и доступные краткие сведения; «Убрать магазин» позволяет снять выбор. Снять блокировки, повторить секции отдельно.
5. Через поиск/страницы справочника загрузить неизвестную точку, выбрать её и применить фильтр. Проверить одинаковый ID/адрес в select, истории и сводке. Если у QA-точки адрес пуст, все её подписи содержат «адрес неизвестен».
6. Клавиатура: Tab/Shift+Tab, выбор магазина, Enter/Space для применения, удаления и повтора; видимый фокус и подписи полей. На 320/375/768/1280 px и zoom 200% с длинными названиями проверить видимость ID в select, перенос текста истории/сводки, доступность действий и горизонтальную прокрутку только контейнера таблицы. Screen reader должен читать ID, название и сообщение об адресе. В Slow network проверить переход от fallback к адресу без потери фокуса; при быстрой смене фильтров поздний ответ не подменяет текущие данные.

После проверки остановить только свои Vite/API-процессы и выполнить `docker compose -p checkist_qa down` без `-v` (либо `down` собственного согласованного QA project). В этой задаче серверы и QA-контейнеры не создавались.
