# Категории товаров: экран и пометки — приёмка

Экран `/catalog/classification` (Ф1), пометки «требует подтверждения» в списке товаров и в карточке товара (Ф2). Описание экрана, запросов и состояний — [docs/frontend.md](../../../../docs/frontend.md#категории-товаров-предположение-с-подтверждением-ф1ф2), контракт — [docs/api-contract.md](../../../../docs/api-contract.md#реализовано-локальный-api-предположений-категорий-товаров), запуск сервера — [docs/development.md](../../../../docs/development.md#qa-предположения-категорий-для-клиента).

**Интерфейс в браузере агент не открывал**: автоматический обход UI в проекте запрещён. Визуальное и интерактивное поведение (клики, фокус, клавиатура, screen reader, узкий экран, Back/Forward) принимает человек по сценарию ниже.

## Запуск QA-сервера и клиента

Нужна **чистая** QA-база: демо-названия не должны совпадать с существующими товарами. Dev-базу не использовать. PowerShell из корня репозитория; в каждом терминале — весь блок:

```powershell
$env:POSTGRES_DB = "checkist_qa"
$env:POSTGRES_HOST = "127.0.0.1"
$env:POSTGRES_PORT = "25432"
$env:REDIS_PORT = "16379"
$env:CELERY_BROKER_URL = "redis://127.0.0.1:16379/0"
$env:CELERY_RESULT_BACKEND = "redis://127.0.0.1:16379/1"
$env:DJANGO_CACHE_URL = "redis://127.0.0.1:16379/2"
$env:VITE_API_BASE_URL = "/api"
$env:DEV_API_PROXY_TARGET = "http://127.0.0.1:18000"
$env:DJANGO_DEBUG = "1"
$env:ALLOW_LOCAL_RECOGNITION_API = "1"
$env:RECEIPT_OCR_PROVIDER = "fake"
$env:PRODUCT_MERGE_AUTO_DETECT = "0"
$env:PRODUCT_CLASSIFICATION_AUTO_SUGGEST = "0"
$env:DJANGO_CSRF_TRUSTED_ORIGINS = "http://127.0.0.1:15173,http://localhost:15173"
$env:MEDIA_ROOT = Join-Path $env:TEMP "checkist-qa-recognition-media"
$env:RECEIPT_OCR_TEMP_ROOT = Join-Path $env:TEMP "checkist-qa-recognition-scratch"
```

`RECEIPT_OCR_PROVIDER = "fake"` обязателен: с `codex_cli` воркер делает настоящие модельные запросы.

Терминал 1 — сервер (`.env` и `backend/.venv` подготовлены по [docs/development.md](../../../../docs/development.md)):

```powershell
docker compose -p checkist_qa up -d --wait --wait-timeout 90 postgres redis
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py migrate --noinput
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py seed_product_classification_demo
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py product_classifications suggest --fake-scenario mixed
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py runserver 127.0.0.1:18000 --noreload
```

Терминал 2 — клиент:

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd run dev -- --port 15173
# либо собранное приложение: npm.cmd run build; npm.cmd run preview -- --port 15173
```

Терминал 3 — воркер, **только на шаге 8** (тот же блок окружения):

```powershell
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py recognition_worker --fake-scenario success2 --classification-fake-scenario mixed
```

Открыть `http://127.0.0.1:15173/catalog/classification`. Если том `checkist_qa` уже содержит другие данные, взять отдельный Compose-проект, порты и базу с именем `checkist_qa_<суффикс>` и согласованно заменить их во всех переменных, включая `DEV_API_PROXY_TARGET` и `DJANGO_CSRF_TRUSTED_ORIGINS` (точный origin Vite с портом). После приёмки остановить свои `runserver`, воркер и Vite, затем `docker compose -p checkist_qa down` без `-v`.

Ниже фильтр «Ожидают / Подтверждённые / Отклонённые / Заменённые / Все» и блок «Ожидают · Страница 1»: 7 групп из таблицы. У созданных механизмом обобщённых продуктов — пометка «новый», у созданных категорий в пути — «новая»; у «Молоко» пометок нет. У каждой записи — название-ссылка на карточку, написание в чеке с магазином, кнопки «Подтвердить», «Выбрать другой», «Отклонить»; у групп «Кефир» и «Колбаса» — «Подтвердить все (2)».
2. **Значок в каталоге.** `/catalog`: 12 товаров, значок «Категория: требует подтверждения» у девяти (№2–№10), у №1, №11 и №12 значка нет. Значок у «Demo Mettwurst fein» ведёт на `/catalog/classification?product=6`: блок «Записи товара №6 · Ожидают · Страница 1», одна группа «Колбаса» с одной записью и строкой «Показано 1 из 2: остальные у других товаров», ссылка «Показать записи всех товаров». Back возвращает в каталог на то же место. То же в категории (`/catalog/categories/{id}`) и в поиске каталога (`/catalog?q=Demo`).
3. **Блок в карточке.** `/catalog/products/6`: под фактами товара блок «Категория предложена автоматически: „Колбаса“ (Продукты питания → Мясные продукты) — требует подтверждения. Товар уже участвует в сравнении цен по этому обобщённому продукту.» и ссылка «Открыть в списке категорий» на `/catalog/classification?product=6`. В фактах карточки «Обобщённый продукт» — «Колбаса», в пути категории — «Каталог», «Продукты питания», «Мясные продукты». У `/catalog/products/1` и `/catalog/products/11` блока нет. Остальная карточка (фильтры, история, сводка) работает как раньше.
4. **Подтвердить.** На экране у «Demo Frischmilch 1,5%» нажать «Подтвердить»: сообщение «Категория подтверждена.», запись исчезла из ожидающих, счётчик «Ожидают подтверждения: 8». В каталоге у №2 значка нет, в карточке `/catalog/products/2` блока нет, обобщённый продукт — «Молоко». Фильтр «Подтверждённые» показывает запись с состоянием «Подтверждено», что было предложено, итог и время решения.
5. **Подтвердить все.** В группе «Кефир» нажать «Подтвердить все (2)»: открывается область «Подтвердить 2 товара как „Кефир“?» с «Да, подтвердить» и «Отмена», фокус переходит в неё. «Отмена» закрывает область и возвращает фокус на «Подтвердить все (2)». Повторить и подтвердить: «Подтверждено 2 из 2», группа исчезла, значков у №3 и №4 нет.
6. **Выбрать другой.** У «Demo Butterkäse Sch.» нажать «Выбрать другой»: область с полем «Поиск обобщённого продукта» (фокус в нём) и радио-вариантами; «Не разобрано» и сам «Сыр» не предлагаются; один символ в поиске — «Для поиска нужно не меньше 2 символов.». Найти `Мол`, выбрать «Молоко», «Применить выбор»: «Выбран другой обобщённый продукт: «Молоко».». В карточке `/catalog/products/5` обобщённый продукт — «Молоко», блока нет; созданный «Сыр» из каталога исчез.
7. **Отклонить.** У «Demo Salami Sticks» нажать «Отклонить» → «Отклонить предложение? Товар вернётся в „Не разобрано“.» → «Да, отклонить»: «Предложение отклонено: товар возвращён в «Не разобрано».», счётчик «Без категории» вырос на 1; у №7 значка и блока нет, «Колбаса» с товаром №6 осталась. 8. **Кнопка запуска, воркер и опрос.** Перед шагом открыть экран во второй вкладке Б и больше её не трогать (она понадобится в пункте «повторное нажатие»). Воркер не запущен.
   - **Очередь без воркера.** Во вкладке А нажать «Предложить категории»: «Запуск поставлен в очередь.», предупреждение «Запуск в очереди. Воркер распознавания не запущен: запуск начнётся, когда воркер запустят.», кнопка недоступна.
   - **Открытая область перед пакетом.** Во вкладке А у «Demo Toast Weizen» нажать «Выбрать другой», ввести в поиск `Мол`, дождаться вариантов и выбрать «Молоко»; «Применить выбор» **не** нажимать, фокус оставить на выбранном варианте.
   - **Между пакетами, воркер остановлен.** В терминале 3 выполнить `$env:PRODUCT_CLASSIFICATION_BATCH_SIZE = "1"` и один проход `./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py recognition_worker --once --classification-fake-scenario new_category` (печатает `Classification run 2: queued` и завершается; сценарий `new_category` нужен, чтобы пакет дал предложение: отклонённую на шаге 7 «Колбасу» `mixed` только повторил бы, и запись не появилась бы). **Не перезагружая** вкладку А, в течение 2–3 секунд увидеть предупреждение «Запуск приостановлен: обработано 1 из 3. Воркер распознавания не запущен: запуск продолжится, когда воркер запустят.». Сообщений «Не удалось обновить данные…» и «Ответ сервера не соответствует ожидаемому формату…» быть не должно, кнопка недоступна, текста «начнётся» нет.
   - **Список при активном запуске.** Там же, без перезагрузки и пока показано «Запуск приостановлен…»: счётчик стал «Ожидают подтверждения: 4. Без категории: 2.», над списком «Всего: 4 записи.», в списке появилась группа «Тестовый продукт» с пометкой «новый», категорией «Тестовая категория → Тестовая подкатегория» и товаром «Demo Mettwurst fein» с кнопками «Подтвердить», «Выбрать другой», «Отклонить». Счётчик и список не расходятся. Область «Выбрать другой» у «Demo Toast Weizen» **осталась открытой**: в поиске по-прежнему `Мол`, вариант «Молоко» выбран, фокус на нём; блок списка не мигал «Загружаем данные…», screen reader ничего, кроме строки запуска, не объявил. Закрыть область кнопкой «Отмена» (фокус вернётся на «Выбрать другой»).
   - **Открытие страницы в этот момент.** Перезагрузить вкладку А (F5): блок «Предположение категорий» показывает счётчики и то же предупреждение «Запуск приостановлен: обработано 1 из 3…», а не ошибку с кнопкой «Повторить»; кнопка «Предложить категории» недоступна, потому что запуск активен; опрос продолжается (следующий пункт виден без перезагрузки).
   - **Повторное нажатие.** Во вкладке Б (открыта до запуска, опроса в ней нет, кнопка доступна) нажать «Предложить категории»: «Запуск уже в очереди или выполняется: новый не создан.», строка запуска сразу сменяется на «Запуск приостановлен: обработано 1 из 3…», кнопка становится недоступной. Сообщения «Действие могло выполниться…» быть не должно.
   - **Следующие пакеты.** Второй проход `--once --classification-fake-scenario mixed`: в обеих вкладках без перезагрузки «…обработано 2 из 3…», список прежний (4 записи: отклонённая «Колбаса» товару «Demo Salami Sticks» повторно не предлагается). Третий такой же проход (`Classification run 2: succeeded`): «Запуск завершён: предложено 1, не распознано 1, пропущено 1.», кнопка снова доступна, пока «Без категории» больше 0. Во вкладке Б список тоже показывает 4 записи.
   - **Область закрывается, если запись решена в другом месте.** Перезагрузить вкладку Б. Во вкладке А нажать «Предложить категории»: «Запуск поставлен в очередь.», «Запуск в очереди. Воркер распознавания не запущен…» — опрос во вкладке А идёт. Там же у «Demo Mettwurst fein» нажать «Отклонить» (появится «Отклонить предложение? Товар вернётся в „Не разобрано“.»), «Да, отклонить» **не** нажимать. Во вкладке Б отклонить ту же запись («Отклонить» → «Да, отклонить»). Во вкладке А без перезагрузки в течение 2–3 секунд: «Ожидают подтверждения: 3.», записи «Demo Mettwurst fein» и группы «Тестовый продукт» в списке нет, вместо области над списком — «Предложение уже решено либо записи больше нет в этом списке. Показано актуальное состояние.», фокус на этом сообщении. Закончить запуск двумя проходами `--once --classification-fake-scenario mixed` («Запуск завершён: предложено 0, не распознано 1, пропущено 1.»).
   - **Постоянный воркер.** Запустить воркер без `--once` (команда терминала 3 выше, `BATCH_SIZE` по-прежнему `1`) и нажать кнопку: «Запуск поставлен в очередь.», затем за несколько секунд строка проходит «Запуск в очереди и начнётся в ближайшие секунды.» и / или «Модель предлагает категории: обработано X из 3.» (между пакетами при работающем воркере — без слова «приостановлен») и заканчивается «Запуск завершён: …»; число «из N» — сколько товаров сейчас без категории; пакеты fake мгновенные, поэтому промежуточные строки могут не успеть показаться. На один опрос (не дольше 2 секунд) между пакетами может показаться «Модель предлагает категории: обработано X из 3. Воркер занят другим заданием.», хотя других заданий нет: сервер читает запуск и воркер двумя запросами, и воркер успевает взять следующий пакет между ними; следующий опрос это исправляет. Записи, предложенные пакетами, появляются в списке по мере опроса, не позже чем через 2–3 секунды после пакета. Остановить воркер (Ctrl+C).
   - **Пакет выполняется и остановка посреди запуска.** Перезапустить воркер с `--classification-fake-scenario pause` (пакет длится до остановки воркера) и нажать кнопку: «Модель предлагает категории: обработано 0 из N.» (N — число товаров без категории). Остановить воркер по Ctrl+C: без перезагрузки — «Запуск приостановлен: обработано 0 из N. Воркер распознавания не запущен: запуск продолжится, когда воркер запустят.» (запуск начат, но ни один товар не пройден), кнопка недоступна. Чтобы надолго увидеть «Запуск в очереди. Воркер занят другим заданием.», нужен новый запуск в очереди при воркере, занятом распознаванием фото; на этих данных не воспроизводится (кроме мгновения из предыдущего пункта). Закончить запуск проходами `--once --classification-fake-scenario mixed` (по одному на товар): «Запуск завершён: …», кнопка снова доступна.
   - **Воркер убит посреди пакета (не Ctrl+C).** В терминале 3 выполнить `$env:PRODUCT_CLASSIFICATION_TIMEOUT_SECONDS = "20"` (срок запроса к модели; lease пакета — срок + 60 с, то есть 80 с) и снова запустить воркер с `--classification-fake-scenario pause`. Нажать «Предложить категории»: «Модель предлагает категории: обработано 0 из N.». В четвёртом терминале найти процесс воркера и завершить его принудительно, без Ctrl+C: `Get-CimInstance Win32_Process -Filter "Name like 'python%' and CommandLine like '%recognition_worker%classification-fake-scenario pause%'" | Select-Object ProcessId, ParentProcessId`, затем `taskkill /T /F /PID <ProcessId первой строки>` (если QA-воркеров с `pause` на машине несколько — выбрать свой по пути в `CommandLine`; чужие не трогать). **Не перезагружая** страницу: ещё около 80 секунд строка остаётся «Модель предлагает категории: обработано 0 из N.» — сервер считает воркер занятым, пока жива lease, и клиент не может знать, что воркера уже нет; затем она сама сменяется предупреждением «Запуск приостановлен: обработано 0 из N. Воркер распознавания не запущен: запуск продолжится, когда воркер запустят.» (тем же стилем, что «Запуск в очереди. Воркер распознавания не запущен…»). Кнопка недоступна, сообщений об ошибке нет. Перезагрузка (F5) показывает то же предупреждение. Во вкладке, открытой до запуска, «Предложить категории» отвечает «Запуск уже в очереди или выполняется: новый не создан.» и показывает то же предупреждение. ## Заход 2 после проверки интерфейса (Ф3, 2026-10-07)

Проверка интерфейса вернула ветку: клиент считал неверным форматом запуск **между пакетами** — `queued` с заполненным `started_at`. Схема `api/product-classifications-schema.ts` требовала у `queued` пустой `started_at`, а сервер возвращает запуск в очередь после каждого пакета и время начала не очищает. Счётчики между собой не сравниваются.

## Заход 3 после проверки интерфейса (Ф4, 2026-10-07)

Проверка интерфейса вернула ветку: список ожидающих перечитывался только по окончании запуска, хотя сервер применяет предложения после каждого пакета. Счётчик «Ожидают подтверждения» рос, список оставался прежним, а при остановленном воркере это не проходило без перезагрузки.

Что теперь делает экран (подробно — [docs/frontend.md](../../../../docs/frontend.md#состояния), абзац «Состояние и список»):

- Список перечитывается, как только очередное чтение состояния показало новый результат: изменился «Ожидают подтверждения», вырос прогресс запуска либо запуск закончился. Это работает между пакетами, при «Запуск приостановлен», при любом фильтре и при записях одного товара. Опрос без изменений список не читает: запросов списка каждые 2 секунды нет.
- Состояние и список читаются независимо; если их числа не могут быть верны одновременно (например, страницу открыли ровно между двумя ответами), экран один раз перечитывает более старую сторону, затем один раз другую — и на этом останавливается.
- Во время сохранения действия ничего не читается; после действия оба запроса перечитываются по одному разу, как раньше.
- Перечитывание не закрывает открытую область, не сбрасывает поиск и выбранный вариант, не переводит фокус и ничего не объявляет. **Правило закрытия:** область помнит, что человек видел при открытии, — `version` записи, а для «Подтвердить все» набор пар «запись, версия», которые ушли бы в запрос. Запись после перечитывания та же — область остаётся. Запись исчезла из списка либо по ней больше нельзя действовать — область закрывается с текстом «Предложение уже решено либо записи больше нет в этом списке. Показано актуальное состояние.». У записи другая `version` — «Предложение изменилось. Данные обновлены: проверьте запись и повторите действие.» (тот же текст, что при отказе `classification_changed`). Набор группы изменился (пакет предложил тот же обобщённый продукт ещё одному товару, запись решена или изменилась) — «Состав группы изменился. Данные обновлены: проверьте группу и повторите действие.»; подтверждать в группе больше нечего — «В группе больше нет записей для подтверждения. Показано актуальное состояние.». Текст выводится в строке результата над списком; если фокус был в закрытой области, он переходит на этот текст, а фокус в другом месте не перехватывается. Область относится к тому списку, в котором открыта: другой фильтр, товар или страница начинаются без неё и без сообщения.

## Заход 4 после проверки интерфейса (Ф5, 2026-10-07)

Проверка интерфейса вернула ветку с тремя замечаниями; сервер и контракт не менялись.

1. **Запуск `running` без воркера выглядел обычной работой модели.** Если воркер падает посреди пакета (не Ctrl+C), сервер оставляет запуск `running`: пока жива lease пакета (срок запроса + 60 с), воркер показан занятым, затем — отсутствующим, и так до следующего прохода воркера. Экран в этом состоянии бессрочно писал «Модель предлагает категории: обработано X из N.». Теперь `running` без воркера — предупреждение «Запуск приостановлен: обработано X из N. Воркер распознавания не запущен: запуск продолжится, когда воркер запустят.», как у запуска между пакетами. Решены все сочетания «запуск × воркер» ([таблица](../../../../docs/frontend.md#запуск-и-воркер-все-сочетания)); пока lease жива, отличить убитый воркер от работающего клиент не может и ничего сверх «модель предлагает» не обещает.
2. **Смена фильтра, страницы или товара во время сохранения действия замораживала блок состояния.** Действия экрана создаются заново для каждого списка, а запрос состояния живёт всю страницу; прежние действия уничтожались, не сняв паузу чтений, которую поставили перед POST. Счётчики и строка запуска не обновлялись, опрос запуска стоял, «Повторить» блока ничего не делал. Теперь уничтожение действий с незавершённым запросом сразу возобновляет чтения, а сам POST не обрывается (обрыв не отменил бы его на сервере — только скрыл бы момент сохранения): когда он ответил, состояние и показанный сейчас список перечитываются ещё по одному разу. Ответ такого POST на экране не показывается — он относится к списку, которого уже нет. «Подтвердить все» из нескольких запросов после ухода дожидается текущего запроса и следующие не отправляет. Пауза снимается ровно один раз на каждом пути: успех, отказ, занятый каталог, устаревший токен, сеть, таймаут, неверный формат, отменённый запрос, уход во время POST, уход во время проверки записи после потерянного ответа, уход с экрана.
3. **Пункт `classification_changed` раздела «Дополнительно» описывал то, чего сервер не делает.** Смена обобщённого продукта товара в админке даёт `classification_resolved`. Пункт переписан; `classification_changed` человек воспроизводит переименованием **предложенного** обобщённого продукта (сверка обновляет снимок записи, `version + 1`, запись остаётся ожидающей) и устаревшей версией из второй вкладки. Все 14 шагов и «Дополнительно» сверены с контрактом и с QA-сервером; кроме этого пункта уточнён шаг 14 (когда именно закрывается запись удалённого товара), в шаг 8 добавлены два пункта — «Воркер убит посреди пакета» и «Другой фильтр, пока действие сохраняется».

Проверено без браузера на окончательном состоянии ветки (команды и числа — [docs/verification.md](../../../../docs/verification.md#фактические-результаты-заход-4-после-проверки-интерфейса-ф5-2026-10-07)):

Всего 55 файлов, 2091 тест.

Правки «в админке» (переименование предложенного обобщённого продукта, смена обобщённого продукта товара, удаление товара) выполнены тем же сохранением модели через ORM, без формы админки. Шаг 8 — до пункта «Постоянный воркер» включительно: при постоянном воркере строка прошла «Запуск в очереди и начнётся в ближайшие секунды.» → «Модель предлагает категории: обработано 0 из 3.» → … → «Запуск завершён: предложено 0, не распознано 1, пропущено 2.»; один раз на мгновение показалось «…обработано 2 из 3. Воркер занят другим заданием.» (см. пункт шага 8). Пункты шага 8, требующие браузера (открытая область, две вкладки, замедление сети), так не проверяются.

## Ограничения и непроверенное

- Работа React в браузере не проверялась: клики и ввод, фактический фокус и его возврат, клавиатура, screen reader, вёрстка на узком экране и при zoom 200%, Back/Forward, cookie-политика браузера для CSRF, опрос запуска по времени. Шаги 1–14 выше.
- Итоговая проверка И1 (2026-10-07) на окончательной ветке: 51 файл / 1934 теста, proxy-скрипт через dev и preview, воркер с fake (включая запуск между пакетами) и настоящая модель в QA — [docs/verification.md](../../../../docs/verification.md#фактические-результаты-и1-окончательная-ветка-2026-10-07). Строки ниже описывают, что проверялось в задаче Ф2.
- В задаче Ф2 воркер не запускался. В заходе 2 (Ф3) proxy-скрипт выполняет запуск настоящим воркером с fake по одному пакету: настоящим HTTP проверены состояния «в очереди, воркера нет», «между пакетами, воркера нет» и «завершён». Состояния при работающем воркере (`idle`, `busy`, `running`: «начнётся в ближайшие секунды», «Воркер занят…», «Модель предлагает категории…») в заходах 2 и 3 проверены только тестами клиента на эталонных ответах; в заходе 4 настоящим HTTP проверены ещё `running` / `busy` и `running` / `absent` после принудительного завершения воркера, а постоянный воркер (`queued` / `idle`, `running` / `busy`, между пакетами `queued` / `idle`) пройден разовым сценарием на QA. «Запуск в очереди. Воркер занят другим заданием.» настоящим HTTP не воспроизводился. Шаг 8.
- `classification_busy` на настоящем сервере не воспроизводился: нужен импорт чека или слияние в тот же момент. Проверен тестами Ф1 на эталонном ответе.
- Пометки каталога читают одну страницу до 200 ожидающих записей: при большем числе у части товаров значка не будет, пока записи не разобраны. Блок карточки этим не ограничен. Запросы пометок повторяются при каждом открытии списка и карточки, без кеша и без опроса: после решения на экране категорий пометка исчезает при следующем открытии каталога или карточки.
- Пометка зависит от двух независимых ответов (каталог и записи): между ними возможен короткий рассинхрон, который правило совпадения `generic.id` превращает в «без пометки», а не в ложную пометку.
- Удаление товара с ожидающей записью в админке и режим «только чтение» новых моделей проверены серверными тестами шагов С1–С3, в браузере — шаг 14.
- Реальная модель (`codex_cli`) не использовалась.
