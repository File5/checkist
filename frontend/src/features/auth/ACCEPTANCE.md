# К1: вход, сессия, модератор, моя / чужая покупка — приёмка

Экран входа на любом адресе, страница «Аккаунт» (`/account`: смена пароля, выход), шапка гостя и пользователя, разделы модератора каталога, столбец «Покупка» в истории цен и «Чужая покупка» в покупках группы дублей. Описание — [docs/frontend.md](../../../../docs/frontend.md#вход-сессия-и-разделение-пользователей-к1), проект разделения — [docs/multi-user.md](../../../../docs/multi-user.md), слой запросов — [src/api/README.md](../../api/README.md).

**Интерфейс в браузере агент не открывал**: автоматический обход UI в проекте запрещён. **Серверы, тесты, миграции, демо-команду и proxy-скрипт разработчик этой подзадачи не запускал** — это делает QA; таблица «Проверено без браузера» ниже перечисляет только то, что действительно выполнено. Визуальное и интерактивное поведение (cookie настоящего браузера, менеджер паролей, фокус, клавиатура, screen reader, узкий экран, Back/Forward) принимает человек по сценарию ниже.

## Запуск QA-сервера и клиента

Нужна **пустая** QA-база: `seed_accounts_demo` отказывает, если в ней есть товары, чеки, фото или группы слияния. Dev-базу не использовать. Для этой приёмки удобна отдельная база (ниже — `checkist_qa_accounts` в отдельном Compose-проекте со своими портами); если том `checkist_qa` пуст, подойдут и обычные значения из [docs/verification.md](../../../../docs/verification.md). PowerShell из корня репозитория; в каждом терминале — весь блок:

```powershell
$env:COMPOSE_PROJECT_NAME = "checkist_qa_accounts"
$env:POSTGRES_DB = "checkist_qa_accounts"
$env:POSTGRES_HOST = "127.0.0.1"
$env:POSTGRES_PORT = "25433"
$env:REDIS_PORT = "16380"
$env:CELERY_BROKER_URL = "redis://127.0.0.1:16380/0"
$env:CELERY_RESULT_BACKEND = "redis://127.0.0.1:16380/1"
$env:DJANGO_CACHE_URL = "redis://127.0.0.1:16380/2"
$env:VITE_API_BASE_URL = "/api"
$env:DEV_API_PROXY_TARGET = "http://127.0.0.1:18001"
$env:DJANGO_DEBUG = "1"
$env:CHECKIST_AUTH_MODE = "accounts"
$env:RECEIPT_OCR_PROVIDER = "fake"
$env:PRODUCT_MERGE_AUTO_DETECT = "0"
$env:PRODUCT_CLASSIFICATION_AUTO_SUGGEST = "0"
$env:DJANGO_CSRF_TRUSTED_ORIGINS = "http://127.0.0.1:15174,http://localhost:15174"
$env:MEDIA_ROOT = Join-Path $env:TEMP "checkist-qa-accounts-media"
$env:RECEIPT_OCR_TEMP_ROOT = Join-Path $env:TEMP "checkist-qa-accounts-scratch"
# Пароли придумывает QA: разные, не короче 8 символов, не из одних цифр, не распространённые.
# В репозиторий, отчёт и журнал их не записывать.
$env:ACCOUNTS_DEMO_MODERATOR_PASSWORD = "<пароль demo_moderator>"
$env:ACCOUNTS_DEMO_USER_PASSWORD = "<пароль demo_user>"
```

`CHECKIST_AUTH_MODE` задаётся явно: в `.env` из образца стоит `local_single`, а переменная процесса выше файла. Флаг `ALLOW_LOCAL_RECOGNITION_API` в режиме `accounts` не действует.

Терминал 1 — сервер (`.env` и `backend/.venv` подготовлены по [docs/development.md](../../../../docs/development.md)):

```powershell
docker compose -p checkist_qa_accounts up -d --wait --wait-timeout 90 postgres redis
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py migrate --noinput
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py seed_accounts_demo --moderator-password $env:ACCOUNTS_DEMO_MODERATOR_PASSWORD --user-password $env:ACCOUNTS_DEMO_USER_PASSWORD | Out-File -Encoding utf8 (Join-Path $env:TEMP "checkist-accounts-demo.json")
./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py runserver 127.0.0.1:18001 --noreload
```

Команда печатает одну строку JSON с идентификаторами (пароли в неё не входят); файл с ней нужен proxy-скрипту. Терминал 2 — клиент:

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd run dev -- --port 15174
# либо собранное приложение: npm.cmd run build; npm.cmd run preview -- --port 15174
```

Открыть `http://127.0.0.1:15174/`. Для шага 12 (вход через админку) один раз создать оператора: `./backend/.venv/Scripts/python.exe -X utf8 backend/manage.py createsuperuser`. Для шага 3 (задержка входа) срок можно сократить: `$env:AUTH_LOGIN_LOCK_SECONDS = "60"` в терминале сервера до его запуска (по умолчанию 900 секунд). После приёмки остановить свои `runserver` и Vite, затем `docker compose -p checkist_qa_accounts down` без `-v`.

## Ручной сценарий (человек)

Два профиля браузера (либо обычное и приватное окно): А — `demo_moderator`, Б — `demo_user`.

1. **Гость.** Профиль А, `http://127.0.0.1:15174/catalog/products/1?date_from=2026-09-01`: заголовок «Вход», поля «Имя пользователя» и «Пароль», кнопка «Войти»; в шапке только «Состояние сервисов» и «Войти». Адрес в строке браузера не изменился. `/health` открывается без входа и показывает состояние сервисов. В DevTools → Network на экране входа нет запросов каталога, чеков и статистики — только `/api/me/` с ответом 401.
2. **Неверный пароль.** Ввести `demo_moderator` и неверный пароль: у кнопки один раз «Неверное имя пользователя или пароль.», фокус остался на кнопке, поля не очищены, адрес прежний. Пустые поля: «Введите имя пользователя и пароль.» без запроса.
3. **Задержка входа** (в конце приёмки либо с `AUTH_LOGIN_LOCK_SECONDS=60`): пять раз подряд неверный пароль для одного имени, шестая попытка — «Слишком много попыток входа. Повторите через … минут» (срок округлён вверх до минут); верный пароль до конца срока тоже отклоняется. После срока вход проходит.
4. **Вход и возврат на адрес.** Верный пароль: открылась карточка товара №1 с тем же фильтром `date_from=2026-09-01`, фокус на заголовке страницы; в шапке «Каталог / Чеки / Статистика / Обработка / Состояние сервисов» и имя `demo_moderator`. Браузер предложил сохранить пароль. Back не возвращает на экран входа (у него нет своего адреса); Forward и перезагрузка оставляют пользователя вошедшим.
5. **История цен: моя / чужая.** Профиль А, `/catalog/products/1`: в «Истории цен» два наблюдения. Строка 21.09.2026 — «Чужая», без времени под датой и без ссылки; строка 07.09.2026 — «Моя · Чек №1», время под датой, ссылка открывает `/receipts/1`. Цены и магазин видны в обеих строках. Профиль Б (войти как `demo_user`), тот же адрес: зеркально — 21.09.2026 «Моя · Чек №2», 07.09.2026 «Чужая». `/catalog/products/2` в профиле Б: одно наблюдение «Чужая»; `/catalog/products/3` в профиле А — так же.
6. **Чеки, фото и статистика — только свои.** Профиль А: `/receipts` — один чек №1; `/receipts/2` — «не найдено», как для несуществующего номера; `/recognition/jobs` — одно задание №1, `/recognition/jobs/2` — «не найдено»; `/stats` — 6,66 EUR, один чек. Профиль Б: чек №2, задание №2, `/receipts/1` и `/recognition/jobs/1` — «не найдено», `/stats` — 7,74 EUR.
7. **Фото чужого чека по прямой ссылке.** Профиль А: открыть `/receipts/1`, скопировать адрес изображения чека (`/media/crops/…`). Вставить его в адресную строку профиля Б: пустая страница 404, картинки нет. В профиле А тот же адрес показывает картинку. В окне без входа — тоже 404.
8. **Модератор: разделы и покупки группы.** Профиль А: в разделе «Каталог» подразделы «Товары / Дубли / Категории». `/catalog/merges/1`: в «Покупках группы» две строки; у своей — ссылка «Чек №1» и «позиция 3», у строки `demo_user` — «Чужая покупка» без ссылки, название, количество, цена и сумма видны. В каталоге у товара №4 значок «Дубли: требует подтверждения» — ссылка на группу.
9. **Не модератор.** Профиль Б: подразделов «Дубли» и «Категории» нет. В каталоге у товара №4 «Дубли: требует подтверждения» — текст без ссылки; в карточке №4 блок «Предварительно объединено 2 написания…» без ссылки «Открыть группу дублей». `/catalog/products/5` — «Товар объединён с «Demo Haferkekse Schoko». Слияние ещё ждёт подтверждения.» и ссылка на товар №4 (не на группу). Прямые адреса `/catalog/merges`, `/catalog/merges/1`, `/catalog/classification`: заголовок «Раздел модератора каталога», текст «Раздел доступен модератору каталога.», ссылка «В каталог»; в Network нет запросов `product-merges` и `product-classifications` с этих экранов.
10. **Аккаунт и смена пароля.** Профиль Б, имя в шапке → `/account`: «Пользователь» `demo_user`, кнопка «Выйти», форма «Смена пароля» с тремя полями и списком четырёх правил. Неверный текущий пароль — «Текущий пароль неверный.», поле помечено. Новый пароль `12345678` — «Новый пароль не подходит. Пароль:» и только нарушенные правила. Несовпадающий повтор — «Новый пароль и его повтор не совпадают.» без запроса. Перед верной сменой войти тем же `demo_user` в третьем окне (ещё один профиль или приватное окно). Сменить пароль: «Пароль изменён. Вход на других устройствах завершён.», поля очищены, профиль Б остался вошедшим, менеджер паролей предложил обновить запись. В третьем окне любое действие (переход по разделу, перезагрузка) открывает вход с текстом «Сеанс завершён. Войдите снова.»; старый пароль там не подходит, новый подходит. Профиль А (`demo_moderator`) не затронут.
11. **Выход, другая вкладка, другой человек.** Профиль Б, две вкладки с `/receipts`. В первой: «Аккаунт» → «Выйти» — открылся вход без текста про завершённый сеанс, в шапке «Войти». Во второй вкладке: при возврате на неё (или при любом действии) вместо списка чеков — вход; чек №2 на экране не остаётся. В той же вкладке войти как `demo_moderator`: виден чек №1, данных `demo_user` (чек №2, 7,74 EUR, «Моя · Чек №2») нигде нет; после перезагрузки — то же. Менеджер паролей подставляет сохранённые имя и пароль.
12. **Вход через админку.** Новое окно: `http://127.0.0.1:18001/admin/`, войти созданным оператором. Cookie сессии привязана к хосту, а не к порту: `http://127.0.0.1:15174/` в этом же окне открывается без экрана входа, в шапке имя оператора, подразделы модератора видны (суперпользователь имеет право), чеков нет. «Выйти» в приложении завершает и сеанс админки.
13. **Право отозвано посреди сеанса.** Профиль А открыт на `/catalog/merges/1`. В админке у `demo_moderator` убрать право `catalog | product | Can moderate the shared catalog` (User permissions) и сохранить. В профиле А нажать «Отменить слияние»: действие не выполнено, страница заменена на «Раздел доступен модератору каталога.», подразделы «Дубли / Категории» исчезли. Вернуть право — после возврата во вкладку либо перезагрузки разделы появляются снова.
14. **Режим без входа.** Остановить `runserver`, выполнить `$env:CHECKIST_AUTH_MODE = "local_single"; $env:ALLOW_LOCAL_RECOGNITION_API = "1"` и запустить снова. Экрана входа, имени в шапке, «Аккаунт» и «Выйти» нет; `/account` — «Страница не найдена»; «Дубли» и «Категории» видны. Чеков нет (демо-чеки принадлежат двум пользователям, запросы идут от пользователя `local`); в истории цен товара №1 обе строки — «Чужая». Интерфейс остальных экранов прежний. Вернуть `accounts` и перезапустить.
15. **Клавиатура, адаптив, диктор.** Вход и «Аккаунт»: Tab по полям и кнопкам, Enter в поле отправляет форму, видимая рамка фокуса, во время запроса кнопка «Входим…» / «Сохраняем…» / «Выходим…» остаётся в фокусе и не отправляет второй запрос; сообщение об отказе появляется один раз рядом с кнопкой и читается диктором (`aria-live`), неверные поля объявляются как invalid; единственный `h1`; фокус после входа и после выхода — на заголовке. Ширины 320 / 768 / 1280 px и zoom 200 %: формы не шире экрана, страница не прокручивается по горизонтали, поля и кнопки не ниже 44 px. Таблица истории цен со столбцом «Покупка» прокручивается внутри своей области. Только светлая тема.

Дополнительно:

- **Сеть при входе.** DevTools → Offline, «Войти»: «Нет ответа сервера. Проверьте соединение и повторите вход.»; повтор — только новым нажатием после Online.
- **Сервер недоступен при открытии.** Остановить `runserver` и перезагрузить страницу: «Вход не проверен» с кнопкой «Повторить»; после запуска сервера кнопка открывает вход либо страницу. `/health` при этом показывает отказ сервисов и от `/api/me/` не зависит.
- **Пароль не попадает в адрес и хранилища.** После входа и смены пароля: в адресной строке, History state, `localStorage` / `sessionStorage` и консоли паролей нет; cookie `sessionid` помечена HttpOnly.

## Проверено без браузера

Windows, Node 24.18.0. Выполнено разработчиком этой подзадачи на окончательном состоянии ветки, без серверов:

| Команда | Exit | Результат |
| --- | --- | --- |
| `node --check` для семи `frontend/scripts/check_*_proxy.mjs` | 0 | синтаксис верен |
| `node frontend/scripts/check_accounts_proxy.mjs` без аргументов | 1 | `Accounts check FAILED: Usage: …`; все адаптеры клиента (`session.ts`, `auth-signal.ts`, каталог, чеки, распознавание, слияния, статистика) импортируются в Node без `window` |
| то же с `CHECKIST_AUTH_MODE=local_single` | 1 | отказ до первого запроса: «set CHECKIST_AUTH_MODE=accounts in this terminal and in the terminal of the API…» |
| то же с `accounts`, файлом JSON в UTF-16 и адресами, на которых никто не слушает | 1 | файл прочитан, отказ «unavailable; start the QA API and Vite…» |
| то же с неполным JSON | 1 | «unexpected shape; pass the whole JSON line printed by seed_accounts_demo» |
| `check_stats_proxy.mjs dev …` и `check_product_merges_proxy.mjs …` без `CHECKIST_AUTH_MODE` | 1 | отказ до первого запроса: «This script needs a server without a sign-in: set CHECKIST_AUTH_MODE=local_single…» |

**Не запускалось** (делает QA): frontend-тесты, lint и build; backend-тесты и миграции; `seed_accounts_demo`; сам сценарий `check_accounts_proxy.mjs` на настоящем сервере; шесть прежних proxy-скриптов на сервере `local_single`.

### Proxy-скрипт двух сессий

При запущенных сервере и Vite из блока выше, из корня репозитория, в терминале с тем же окружением:

```powershell
node frontend/scripts/check_accounts_proxy.mjs dev http://127.0.0.1:15174 (Join-Path $env:TEMP "checkist-accounts-demo.json")
# после npm.cmd run build и npm.cmd run preview -- --port 15174 — на той же базе:
node frontend/scripts/check_accounts_proxy.mjs preview http://127.0.0.1:15174 (Join-Path $env:TEMP "checkist-accounts-demo.json")
```

Ожидается exit 0, двенадцать строк `PASS`, строка JSON с `"result": "passed"` и `browser_ui: not tested`. Скрипт вызывает настоящие адаптеры клиента через Vite proxy и ведёт по отдельной «банке» cookie (`csrftoken`, `sessionid`) на каждого участника; в каждом JSON-ответе он ищет `receipt_id`, ссылки и пути файлов чужого чека. Сценарий: Vite в названном режиме отдаёт клиент входа и `/account`, proxy = Django; гость (health открыт, `/api/me/` — 401 без сигнала, остальное — `aborted` и сигнал, MEDIA — 404); неверный пароль один раз; вход двоих и вторая сессия `demo_user`; чеки, фото, задания и вырезки только свои, чужой id — 404; история цен зеркально, `last_observed_at`; покупки группы у модератора и у пользователя; `403` не-модератору на `detect`, `confirm` и запуск предположений категорий; статистика; MEDIA своего и чужого; слабый новый пароль, смена пароля гасит вторую сессию, пароль возвращается; выход, повтор старой cookie — 401.

Каталог скрипт не меняет; пароль `demo_user` меняет и возвращает, поэтому его можно повторять на одной базе. Если прогон оборвался между сменой и возвратом, скрипт пробует вернуть пароль сам и сообщает итог; при неудаче — пересоздать базу. Каждый прогон добавляет одну неудачную попытку входа в счётчик адреса (порог — 50 за 900 секунд).

Шесть прежних скриптов (`check_catalog_proxy.mjs`, `check_recognition_proxy.mjs`, `check_review_proxy.mjs`, `check_product_merges_proxy.mjs`, `check_product_classifications_proxy.mjs`, `check_stats_proxy.mjs`) работают только с сервером без входа: в их терминале и в терминале сервера нужен `$env:CHECKIST_AUTH_MODE = "local_single"`, иначе скрипт отказывает до первого запроса с объяснением.

## Ограничения и непроверенное

- Работа React в браузере не проверялась: cookie и SameSite в настоящем браузере, менеджер паролей, фактический фокус и его возврат, клавиатура, screen reader, вёрстка на узком экране и при zoom 200 %, Back/Forward, вторая вкладка. Шаги 1–15 выше.
- `429 login_throttled` на настоящем сервере скриптом не воспроизводится (пять отказов блокируют вход на 900 секунд): текст и срок проверяются тестами адаптера и формы на эталоне `login_throttled.json` и шагом 3.
- Отзыв права посреди сеанса и вход через `/admin/` — только вручную (шаги 12–13).
- 401 посреди сеанса снимает страницу целиком: несохранённые правки формы `needs_review` теряются, как при перезагрузке (серверного черновика нет).
- Отдельного адреса у экрана входа нет; параметра `next` и перенаправлений нет. Ссылка «Чек №N» из истории цен открывает чек без контекста возврата: на чеке будет «К чекам».
- Поведение за настоящим HTTPS-прокси (Secure-cookie, заголовки прокси, один адрес клиента на всех при задержке входа) этой приёмкой не покрыто — см. [docs/deployment.md](../../../../docs/deployment.md).
- Ссылки на `/admin/` в шапке нет: Vite её не проксирует.
