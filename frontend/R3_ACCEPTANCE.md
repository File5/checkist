# R3: аудит runtime-схем и история с position=0

История принимает `position=0` как неотрицательное безопасное целое, отдельно от положительных ID. Ответ сохраняется целиком; Node-render подтверждает три строки для пар `(12, 0)`, `(12, 1)`, `(13, 0)` и разные React-ключи `12:0`, `12:1`, `13:0`. Единственное использование позиции в экранах — ключ в `src/features/product/PriceHistory.tsx:38`, без truthiness или подстановки значения.

Аудит также исправил ограничения кодов справочников, проверку размера страницы при разных SQL-снимках COUNT/выборки и обработку документированного health HTTP 400. Новых механизмов пропуска строк нет: одна невалидная обязательная точка остаётся `invalid_response` всего блока. Backend, миграции, зависимости, Compose, env и общие документы не изменялись; обновлён только разрешённый `docs/frontend.md`.

## Проверено и не прошло

- Первый целевой прогон `npm.cmd run test -- src/api/catalog.test.ts src/api/prices.test.ts src/api/stores.test.ts src/features/product/product-markup.test.tsx` — **exit 1**, 20 failed /179 passed. До правки production-схем 19 регрессий воспроизвели отклонение position=0, нестандартных справочных кодов и вставки между COUNT/выборкой. Ещё один отказ — ошибочное новое SSR-ожидание `2,00 EUR`: существующий форматтер убирает лишние нули и отдаёт `2 EUR`. Исправлено ожидание, форматтер не менялся. Повтор — 199/199, exit 0.
- `npm.cmd run test -- src/api/health.test.ts` до правки health — **exit 1**, 1 failed /50 passed: документированный HTTP 400 invalid_request возвращал inconsistent-response вместо http. Исправлено; окончательный общий прогон включает эту регрессию и проходит.
- Первый `npm.cmd run lint` — **exit 1**, `no-irregular-whitespace` в новой строке SSR-теста: буквальный NBSP внутри template literal. Заменён на явный `\u00a0`; повтор lint — exit 0. Правило ESLint не отключалось.

Оставшихся отказов обязательных проверок нет.

## Не проверено и почему

- Реальный QA backend/БД, HTTP/proxy и ввод position=0 через admin в этом прогоне не запускались: изменения ограничены клиентом, все сетевые ответы тестов подставлены. SQL-гонка COUNT/выборки установлена по коду, её допустимый JSON воспроизведён mocks; настоящий конкурентный ввод не исполнялся.
- Визуальная, интерактивная, клавиатурная приёмка и screen reader — **человеком**. Автоматический обход browser UI запрещён. Node-render проверяет текст/структуру/React-ключи, не поведение браузера. Скриншоты, локальное превью с реальным QA и статические макеты не создавались. Этот markdown — реальный отчёт и сценарий передачи, не изображение интерфейса.
- Модели Country/Currency не проверяют ISO-формат при вводе, а query требует ISO-синтаксис и uppercase. Эти разные ограничения backend не исправлялись. `blank=False` и choices обходятся прямой ORM-записью: заведомо неверные пустые коды/enum по-прежнему ошибка клиента. Это не новый механизм тихого пропуска.
- Merge, publish, deployment и release не выполнялись.

## Ручной сценарий для человека

1. Подготовить свободную изолированную QA по [verification.md](../docs/verification.md#изолированная-qa-среда): полный environment-блок в каждом терминале, БД `checkist_qa`, API 18000, Vite 15173, отдельные контейнеры/тома. Не вводить данные в dev. Пользователя admin человек создаёт командой `manage.py createsuperuser` в QA. Запустить QA API и `npm.cmd run dev -- --port 15173` из `frontend/`.
2. Через `http://127.0.0.1:18000/admin/` подготовить вымышленные сопоставленные данные: товар, магазин, чек продажи с двумя строками этого товара, position **0** и **1**, quantity=1, unit=pcs, discount_amount=0. Задать различимые цены/суммы, например 2 и 3. В другом чеке добавить тот же товар с position=0 и ценой 4. При правке использовать свободные позиции; освобождение занятой позиции сохраняется отдельным POST. Если QA-набор уже подходит, использовать его без дублирования.
3. `curl.exe --fail-with-body --max-time 15 http://127.0.0.1:18000/api/products/<id>/prices/` должен содержать все три пары receipt_id/position. Открыть `http://127.0.0.1:15173/catalog/products/<id>`: история видна целиком, три строки с различимыми ценами присутствуют, карточка и сводка остаются. В Network ответ history — HTTP 200 с position=0; ошибка «Ответ сервера имеет неожиданный формат» отсутствует. Позиция сама не является видимой колонкой, строки сверяются по данным чека/ценам.
4. Перезагрузить страницу, сменить фильтры/период и вернуться назад. Нулевые позиции не теряются, старый ответ не заменяет новый. Для товара без покупок видны отдельные пустые состояния; пустой фильтр даёт сообщение и сброс. Фильтры по стране/валюте вводить допустимыми ISO-кодами.
5. При необходимости проверить новый случай кодов: только в QA создать короткую/строчную страну или валюту через admin и связать с вымышленным магазином/чеком. Без фильтра нестандартный код отображается и не ломает блок. Такой код не проверять как успешный query-фильтр: backend его отвергает по отдельному правилу.
6. В DevTools временно подставить ответ history с одной position=-1 (Local Overrides), сохранив остальные поля. Должна появиться локальная ошибка истории с «Повторить», без молчаливого пропуска строки; карточка/сводка сохраняются. Удалить override, повторить — история восстанавливается. Отдельно проверить Offline → Online → повтор и Slow network → быстрая смена фильтров. Не изменять backend ради некорректного JSON.
7. Tab/Enter/Space: формы, повтор, пагинация, видимый фокус; Tab до региона таблицы и стрелки для горизонтальной прокрутки. На ширинах 320/375/768/1280 и zoom 200% строки и действия доступны; горизонтальная прокрутка внутри таблицы, вертикальная у страницы. Проверить подписи, caption и сообщения со screen reader. Общий сценарий товара — [MANUAL_CHECK.md](src/features/product/MANUAL_CHECK.md#ручной-сценарий-после-подключения-f5); общий health и admin — [verification.md](../docs/verification.md#ручная-ui-приёмка-человеком).
8. Остановить только созданные для этой приёмки API/Vite процессы и выполнить `docker compose -p checkist_qa down` без `-v`. Чужую QA не останавливать, данные томов сохранить.
