# Checkist

Перед работой прочитай [AGENTS.md](AGENTS.md) и нужные [architecture](docs/architecture.md), [data-model](docs/data-model.md), [api-contract](docs/api-contract.md), [development](docs/development.md), [verification](docs/verification.md). Сверяй с кодом, compose.yaml и .env.example. Разделение пользователей (владелец чеков и фото, вход, доступ, общие цены) реализовано; разработчики его не запускали, QA прогнал 2026-10-08 — тестовые наборы красные из-за ошибок в самих тестах, повторный прогон впереди (статус ниже): решение и отличия от проекта — [multi-user](docs/multi-user.md), сервер — [deployment](docs/deployment.md).

Django/DRF + PostgreSQL, Redis/Celery для health, React/Vite SPA: health, каталог, цены, загрузка фото/задания и чеки подключены к API (docs/frontend.md). Stores/catalog/receipts и admin реализованы. Recognition: фото/MEDIA, PostgreSQL queue, host recognition_worker рядом с Codex CLI или явным fake, detect/crop/recognize/import, cancel/retry, локальный upload/jobs/receipts API со всеми строками. Новые магазины/товары создаются автоматически; SHA-256 replay и повторные фото не дублируют совместимые чеки/строки, заполненные значения не перезаписываются. Needs_review сохраняет результат и причины; человек исправляет и подтверждает такую вырезку: `POST /api/recognition/receipt-images/{id}/confirm/` (правки + подтверждение одной транзакцией через тот же импорт, `recognition/review.py`), форма в карточке вырезки на `/recognition/jobs/{id}`. Отказ ничего не сохраняет (`review_invalid` с issues, `invalid_parameter` с fields, `review_unavailable`/`review_resolved`/`review_busy`/`job_active`); повтор — по содержимому тела; найденный существующий чек не перезаписывается; миграций нет. Промпт v5 просит налоговые evidence: ставка и налоговый итог импортируются только с подтверждением чтения, иначе чек сохраняется без них с замечаниями.

Доступ — режим `CHECKIST_AUTH_MODE`, правила только в `backend/accounts/access.py` (`mode`, `request_user`, `owner_q`, `is_moderator`, `SignedIn`, `LocalOrSignedIn`, `Moderator`); вью не читают `request.user`. `local_single` (образец `.env`, QA, тестовый раннер; только при DJANGO_DEBUG=1, иначе ImproperlyConfigured): без входа, все запросы — пользователь `local`, прежние правила — 13 GET открыты, остальное DEBUG + ALLOW_LOCAL_RECOGNITION_API=1 + loopback, CSRF даже анониму. `accounts` (по умолчанию, сервер): сессия Django, общая с `/admin/`; без входа `401 not_authenticated` на всё, кроме health, `/api/auth/csrf/` и запасного 404; флаг, DEBUG и адрес не читаются. Старые 13 GET/health сохраняют контракт. Vite dev/preview: /api и /media на один Django; точный Origin клиента включить в DJANGO_CSRF_TRUSTED_ORIGINS. Native Codex .exe/auth на host, Celery не запускает OCR. `executor.state` idle/busy/absent: простаивающий воркер виден API по его advisory-блокировке (`pg_locks` своей БД), `available` = не absent. API и worker используют одну DB/MEDIA, scratch отдельно.

Категории новых товаров: `classification` спрашивает модель о товарах из «Не разобрано» и сразу приписывает их к предложенному обобщённому продукту и категории с пометкой «требует подтверждения» (журнал прежнего значения и созданных записей каталога); `/api/product-classifications/` — список, запись, confirm (тот же либо другой обобщённый продукт), reject, массовый confirm, status, runs с доступом recognition; отклонение возвращает товар в «Не разобрано», убирает созданное пустое и повторно тот же вариант не предлагает; содержательный или подтверждённый товар автоматика не меняет. При подтверждении слияния дублей ожидающая запись поглощённого товара переходит к оставляемому, только если тот до слияния был в «Не разобрано» и получил предложенное значение из этого предположения (`after_merge_confirmed(..., target_generic_before)`); иначе запись закрывается `superseded` / `merged`, товар не трогается; сверка запись не переносит никогда. Своя ожидающая запись оставляемого товара закрывается так же (`superseded` / `merged`), если слитый с ним дубль имел то же значение от человека; это решает сверка по журналу слияний. Отказы поглощённого товара переходят к оставляемому (`before_merge_confirmed` перед удалением поглощённых — вторая вставка в `merges/services.py`; страховка в сверке `_inherit_rejections` восстанавливает потерянное, в том числе по прежним слияниям). Отклонение и `cancel-pending` не меняют значение, которое было у товара до предположения либо выставлено человеком. Запуск ставит кнопка либо импорт при `PRODUCT_CLASSIFICATION_AUTO_SUGGEST` (по умолчанию 0); импорт дополняет за курсором ожидающий запуск любого `scope`, включая ручной `all` (сверх лимита — `remaining`), исполняет `recognition_worker` пакетами (текстовый вызов Codex без изображения либо fake); сбой модели не трогает чек и каталог. Команды `product_classifications suggest [--dry-run]` / `reconcile` / `cancel-pending`; перед `migrate classification zero` — `cancel-pending`.
